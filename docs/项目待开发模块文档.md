## M1. 可移植特征契约 v4 与在线门禁（P0-1）

> 状态（2026-09-29）：已由路线 B 取代原“v3.2 + `ct_state_ttl` codebook”方案。本节只保留摘要，设计、任务、测试与验收以路线 B §3、§4、§7～§9 为准。

### 现状
`feature-contract/unsw-nb15-flow-v3.1.json` 的 `ct_state_ttl` 没有可审计的 codebook：训练端直接读取 UNSW-NB15 CSV 的现成列，从未产生“原始字段 → 编码值”的映射。`sttl`、`ct_state_ttl` 属于靶场环境特征，`ct_*` 依赖 UNSW 网络级观测点，均不能直接移植到单主机软件传感器。Feature Builder 在缺少 codebook 时 fail-closed，合格记录不发布 outbox。

### 设计（摘要）
- v3.1 契约与 `unsw-binary-2026.09.0` 保持不可变，只用于 UNSW CSV 离线回放与历史对照，永不开启在线门禁；不为 v3.1 编造或推导 codebook。
- 新契约 `unsw-nb15-flow-v4`：17 个数值 + 2 个类别字段（删除 `sttl`、`ct_state_ttl`、`sloss`、`sjit`、`djit`、`dinpkt`、`ct_flw_http_mthd`、`ct_dst_sport_ltm`、`ct_dst_src_ltm`），7 个 `ct_*` 按单主机视角由训练端与传感器同一定义重算，`service` 只按响应方端口映射（路线 B §4.2、§4.3 D1～D13）。
- 契约由资源文件驱动并校验 SHA-256；类别**识别规则**属于契约，类别**词表**来自激活模型的 `preprocessing.json`。
- 推理前要求“记录契约 = 传感器已批准配置契约 = 激活模型 manifest 契约”，不一致返回稳定错误码 `FEATURE_CONTRACT_MODEL_MISMATCH`，不切换模型。
- 契约只冻结一次：先做传感器可行性探测（路线 B §7.0）再冻结规格，之后真实数据再训练只换模型与 manifest（路线 B §4.4、§4.5）。

### 执行步骤（对应路线 B 阶段）
1. 阶段 1：本机 Mac 被动探测 + 全量特征审计 + 消融，G1 冻结字段集，产出 `docs/特征规格-unsw-nb15-flow-v4.md`。
2. 阶段 2：训练端按 v4 重训，交付 `unsw-binary-2026.10.0` 与 golden fixtures（新 holdout 种子 `20261001`）。
3. 阶段 3：后端契约改造——契约注册表/校验器/Feature Builder 契约驱动，模型运行时按 manifest 读取输入维度，UNSW 回放增加 v4 映射。
4. 迁移 V11（V9、V10 已分别被查询索引与 M2 消费台账占用）：为 `source_mapping`、`sensor_config` 追加 `feature_contract_sha256`；`source_mapping` 当前没有契约列，v4 本身不需要为“允许 v4”做 schema 迁移。

### 验收
见路线 B §9.3：UNSW CSV 回放（v4 映射）时合格记录进入 outbox，拒绝原因可查询；golden fixtures 100% 通过；v3.1 在线路径仍然 fail-closed。

## M2. 异步消费链路（P0-2）

> 状态（2026-09-29）：已实现并通过专用 MySQL schema 与 RabbitMQ 测试 vhost 集成测试（重复投递只交接一次、5 次 TTL 重试后死信、未 ack 消息在消费者恢复后重投且只处理一次）。默认关闭；M3 提交端口未实现时 fail-closed 进入死信。

### 设计
- 拓扑：exchange `cyber-security.ingest.events`（topic，durable）→ 队列 `q.ingest.batch.received`（durable，绑定 `ingest.batch.received`）→ 死信 exchange `cyber-security.dlx` → `q.ingest.dead`。
- 消费者 `IngestBatchConsumer`：手动 ack，prefetch 10；按 `outbox_event.event_key` 做幂等（新表 `consumed_message(consumer, message_key, consumed_at)`，唯一键）。
- 处理：读取批次中合格记录 → 提交推理任务（M3）。事务内写 `consumed_message` 与业务结果，提交后 ack。
- 失败：可重试错误 nack 进入延迟重试（最多 5 次，指数退避，经 TTL 队列实现）；不可重试错误直接死信并记录原因。

### 执行步骤
1. 迁移 V10：`consumed_message` 表。
2. `RabbitTopologyConfig` 声明队列、绑定、DLX（仅在 relay 启用时声明）。
3. 实现消费者与幂等守卫，中文 Javadoc 说明至少一次语义。
4. 集成测试（临时 vhost）：重复投递只处理一次；异常进入重试再到死信；应用重启后未 ack 消息重新处理。
5. 默认仍关闭，`OUTBOX_RELAY_ENABLED=true` 且消费者就绪才启用；README 更新启用步骤。

## M3. 在线推理服务（P0-3）

> 状态（2026-09-29）：完成（路线 B §10.3）。`LocalInferenceTaskSubmitter` 接入 M2 消费事务；V12 补齐结果快照列；`GET /api/v1/inference-requests`、`POST /api/v1/inference/dry-run` 已开放。与下文设计的差异：超时沿用既有状态 `timed_out`（错误码 `INFERENCE_TIMEOUT`）；manifest 无 `threshold_policy` 字段，阈值策略版本取 `fixed:<model_version>`；dry-run 权限名为 `model.replay.run`，限 `source_type='replay'` 的数据源。本机开发库已迁移到 V12 并激活 `unsw-binary-2026.10.0`；结果传给 M4 属阶段 5。

> 路线 B 差异（阶段 4）：输入维度与字段顺序一律读取激活模型 manifest 的 `feature_contract.inputs`，并与 ONNX 图输入形状交叉校验；删除 `OnnxModelRuntime.NUMERIC_FEATURE_COUNT = 26` 等固定维度假设。首个在线模型为 v4 契约下的 `unsw-binary-2026.10.0`；`2026.09.0`（v3.1）保持 `candidate`、只做离线回放。记录 `viewpoint`/地址族不在 manifest 声明范围内时记为 `not_in_model_scope`，不推理、不算拒绝。详见路线 B §10。

### 设计
- 接口 `InferenceService.infer(recordBatch)`，内部调用激活版本 `OnnxModelManager`。
- 每条记录写 `inference_request`（`request_key` 唯一、`model_version_id`、`contract_version`、`deployment_mode=local`、`status`、`latency_ms`、`error_code`）。
- 前置校验：激活模型存在；模型 manifest 的特征顺序、维度、单位、契约版本与记录及传感器已批准配置一致；否则 `status=rejected`，错误码 `FEATURE_CONTRACT_MODEL_MISMATCH`，并转规则/人工。
- 超时：单批次 2 秒可配置，超时标记 `timeout`，不切换模型、不降级为默认结果。
- 输出：概率/类别 + 阈值策略版本（来自 manifest `threshold_policy`），传给 M4。
- 管理 API（只读 + 受控触发）：`GET /api/v1/inference-requests`、`POST /api/v1/inference/dry-run`（仅回放数据，需 `model:replay` 权限）。

### 执行步骤
1. 批量张量构造按 manifest 特征顺序与维度（不使用固定 26 维常量）；预处理参数来自 manifest，不在线重新拟合。
2. 会话并发：`OrtSession` 线程安全调用，版本切换加读写锁。
3. 测试：与训练端导出的参考输入/输出比对（误差 ≤1e-5）；版本不符拒绝；超时显式失败；无激活模型时拒绝。

## M4. 检测研判：告警生成与事件关联（P0-4）

> 状态：已完成（路线 B 阶段 5，§11.1、§11.2；V13、V14）。下文按实际实现描述。

### 实现
- 触发：`DetectionService` 在 M2 消费事务内、推理之后执行；是否生成模型告警以数据库中 `succeeded` 且标签为 `Attack` 的推理行为准，不依赖推理函数返回值。
- 告警生成（`AlertGenerator`）：模型告警 `alert_key = model:<记录 ID>:<制品 SHA-256>`，规则告警 `alert_key = rule:<规则 ID>:<记录 ID>`；`alert_key` 唯一键保证重复投递不产生重复告警。`severity` 由 `detection_policy` 中当前 active 的分级映射决定，告警记录所用策略版本。
- 规则引擎（`RuleCondition`）：`detection_rule` 中已批准的确定性规则，条件为受限结构（字段限 `features.*`/`metadata.*`，不允许脚本）。规则经 `/api/v1/detection-rules` 登记为 pending，须由登记人以外的用户批准，批准后旧 active 版本退役。
- 事件关联（`EventCorrelator`）：按“同资产 + 关联时间窗（默认 900 秒，按记录事件时间）”并入 `security_event`，不含对端 IP（v4 不入库地址，见路线 B §21）。风险评分公式 `min(1, severityWeight*criticalityWeight + min(repeatCap, repeatStep*(alertCount-1)))`，参数与计算依据随事件保存。
- 事件状态机：`open → investigating → contained → resolved | false_positive | closed`，与 V1 CHECK 一致，每次迁移写审计与时间线。
- 前端：告警/事件列表与详情展示告警来源（模型/规则）、契约版本与评分依据；事件关联告警与时间线服务端分页。

### 验证
`LocalInferenceIntegrationTest`（端到端：重复投递不重复告警、范围外用户看不到事件）、`DetectionRulesAndPoliciesTest`、`DetectionRuleServiceTest` 覆盖告警生成、规则条件与关联；开发库 UNSW 原始 CSV 回放已跑通“接入 → 推理 → 告警 → 事件”（路线 B §11.2）。

### 遗留
- 同一资产窗口内来自不同对端的独立攻击会并入同一事件，由分析员在时间线区分。
- 时间窗聚合规则（端口扫描、登录失败、路径探测、UDP 突发）尚未补齐，见文末“后续执行计划”第 2 项。

## M5. 真实软件传感器（P1-1）

> 状态：macOS 部分已完成（路线 B 阶段 6，§12.6～§12.8）：G2 Go/Java 对拍通过（合成 fixtures + 真实 en0 流量 331 条，一致率 100%），本机登记上报冒烟通过，并已用于阶段 7 影子运行。Windows（Npcap 构建与补测）未开始，需另行授权。与下文设计的差异：抓包权限改为“sudo 启动、打开 BPF 后立即降到调用者”（`internal/privdrop`），不注册 launchd、不建 `access_bpf` 组；Go 组流器按规格独立实现，以 Java 参考组流器 `ingest.packet` 对拍，不复用 `BidirectionalFlowEngine`；队列满时丢弃新批次并计数。

### 设计
- 独立工程 `sensor/`，使用 Go（已确定），单二进制分发，不放入后端模块。
- 依赖：`github.com/google/gopacket`（pcap 绑定，macOS 链接系统 libpcap，Windows 链接 Npcap SDK，需 cgo）；版本在 `go.mod` 中固定，并用 `go.sum` 校验。
- 模块划分：`capture`（网卡/pcap 文件读取，BPF 过滤）、`flow`（双向流表，超时与 FIN/RST 导出，按后端 Java `ingest/flow` 语义移植）、`feature`（契约 v4 字段集计算，字段、公式、窗口与封流规则见阶段 1 冻结的 `docs/特征规格-unsw-nb15-flow-v4.md`）、`uplink`（HTTPS 批次上传、序号、重试）、`agent`（登记、心跳、配置拉取）、`keystore`（凭据存储）。
- 语义一致性：流聚合和特征计算以后端 Java 实现为准。用同一份 UNSW CSV/pcap 夹具生成“黄金输出”，Go 与 Java 两端比对，字段逐项一致才能联调。
- 采集：macOS 使用 libpcap；本机 `/dev/bpf*` 为 root 0600 且无 `access_bpf` 组，按路线 B §4.3 D13 由 launchd 以 root 启动抓包辅助进程，打开 BPF 设备、设置过滤器与 snaplen 后立即降权，不安装 ChmodBPF、不永久修改设备权限。Windows 使用 Npcap（安装驱动，管理员权限）。只解析到传输层头部，snaplen 限制在头部长度，不读取载荷（D8）。
- 处理：双向流聚合 → 按 v4 封流规则导出（TCP 空闲 60 秒 / UDP·ICMP 30 秒 / 强制 60 秒，D7）→ 按契约 v4 计算 raw feature（IPv4/IPv6 分窗、TSO/LSO 分段归一化、排除多播广播回环，D10～D12）→ 批次签名上传。
- 身份：使用已有一次性设备凭据登记后获得机器凭据；凭据存系统钥匙串（macOS Keychain / Windows DPAPI）。
- 配置：定期拉取批准配置（采集网卡、BPF 过滤、批次大小），心跳上报健康窗口。
- 离线缓冲：本地有界队列（例如 50MB），满则丢弃最旧并计数上报。

- 前置：`capture`、`flow`、`uplink`、`agent`、`keystore` 骨架可与路线 B 阶段 2～5 并行；`feature` 模块依赖阶段 1 冻结的特征规格，不依赖 M1 后端改造完成。Go/Java 一致性为决策门 G2（路线 B §12.3）。

### 执行步骤
1. `go test ./...` 覆盖流表、特征、上传重试；交叉编译 `darwin/arm64`、`windows/amd64`（Windows 需在 win-dev 上用 Npcap SDK 构建）。
2. 先实现 pcap 文件读取模式（使用公开数据集 pcap），跑通与后端的契约一致性；再接实时网卡。
3. 影子运行：实时采集只入库不告警至少 7 天，比较特征分布与训练集差异，出报告。
4. 测试：权限不足时明确报错退出；后端不可达时缓冲与重传不重复（批次序号）。

### 验收
两台授权主机实际上报；报告中说明仅覆盖本机可见流量。

## M6. 响应策略管理 API（P1-2）

> 状态：已完成（提交 `cd32b8d`，V15，路线 B §14.1）。下文按实际实现描述。

### 实现
- V15 为 `response_policy` 追加起草人、派生来源、变更理由、内容 SHA-256、提交/审批/退役字段；CHECK 约束起草人≠批准人、active 必须有批准人；生成列 `active_key` + 唯一键保证同一策略键至多一个 active。
- 生命周期：`draft → pending → active | rejected`；起草人可撤回本人 draft/pending（记为 `retired`）；批准即生效，旧 active 版本在同一事务退役；active 版本可由审批人退役。版本不可原地修改，变更一律新建版本。V1 遗留的 `approved` 状态值仍在 CHECK 中，新流程不再使用。
- 权限：`response.policy.draft`（授予 `security_analyst`）、`response.policy.approve`（授予 `response_approver`）、`response.policy.read`；`response.policy.manage` 不授予任何角色。
- API：`GET /api/v1/response-policies[/{id}]`，`POST /api/v1/response-policies`、`/{id}/versions`、`/{id}/submit`、`/{id}/withdraw`、`/{id}/decision`、`/{id}/retire`。
- 校验：只开放 `temporary_block`；受限 JSON Schema（未知关键字加载失败）；TTL 上限 3600 秒；目标只允许单播 IPv4；没有经验证的回滚证据时拒绝 `auto_execute`。起草与审批时都重新校验，审批时核对内容哈希。V15 前缺起草人的历史策略不能经接口审批（409 `POLICY_AUTHOR_UNKNOWN`）。
- 已退役版本不能再被动作申请引用，引用它的待审批动作也不能被批准；每次状态迁移写带 `after_hash` 的追加审计。
- 前端策略页提供状态、详情抽屉、起草/新版本表单及提交、撤回、批准、驳回、退役操作；按钮可见性只是提示，授权以后端为准。

### 验证
`ResponsePolicyIntegrationTest` 覆盖生命周期、职责分离、版本取代、退役引用与数据库约束。

## M7. 处置执行器与主机防火墙适配器（P1-3）

> 状态：未开始。前置为 G3 通过（路线 B §14.2），第一轮 G3 未通过，当前不启动。执行端点仍固定返回 `503 ACTION_EXECUTION_UNAVAILABLE`，不调用适配器、不写 `action_execution`。

### 设计
- 执行流程：审批通过 → 写 `action_execution`（`idempotency_key` 唯一，`status=queued`）→ outbox → 执行消费者 → 适配器 → 结果写回 → 到期自动撤销。
- 执行前再次校验：资产登记、授权未过期、策略仍为 active（M6 起批准即生效）、目标不在保护名单（管理地址、网关、后端地址、DNS）。任一失败 fail-closed。
- 适配器接口：
  ```java
  interface HostFirewallAdapter {
      Capability capability();              // 已验证的动作与 OS
      ExecutionResult apply(BlockSpec spec); // 追加窄范围规则
      ExecutionResult revoke(String rollbackRef);
      VerifyResult verify(String rollbackRef);
  }
  ```
- 适配器运行在传感器侧的独立最小权限进程，通过后端下发的签名任务执行；后端不持有主机凭据，模型不能直接调用。
- macOS：pf 独立 anchor（例如 `com.xyh.cyber/block`），只写入带 TTL 的 table 条目，不修改主规则集。
- Windows：`New-NetFirewallRule` 创建带统一前缀 `CYBER-TTL-` 的出入站阻断规则，只作用于指定远端 IP。
- TTL：适配器本地调度撤销，后端也有兜底扫描；撤销后调用 `verify` 确认规则已不存在。
- 状态：`queued → running → applied → revoking → revoked`，失败为 `failed`/`timeout`，任何失败都触发撤销尝试并告警人工。
- 限速：不实现，适配器 capability 中明确标记不支持。

### 执行步骤
1. 实现后端执行编排（替换当前 503 路径），默认 `EXECUTION_ENABLED=false`。
2. 在隔离靶场虚拟机上开发并验证两个适配器，记录回滚证据。
3. 测试矩阵：越权、过期授权、未知目标、保护名单命中、重复请求、执行超时、适配器故障、撤销失败、审计完整性。
4. 只有回滚验证通过的动作才允许在策略中设置 `auto_execute=true`。

## M8. 漂移计算与人工反馈闭环（P2-1）

> 状态：后端与前端已完成（路线 B 阶段 7，§13.6；V16）。`DriftMetricJob` 按 UTC 整点小时写 `drift_metric_window`（默认关闭，`CYBER_DRIFT_ENABLED=true` 开启）；基线来自 manifest `feature_baseline_stats`（`unsw-binary-2026.10.1` 起提供）。反馈改为按告警标注：`POST /alerts/{id}/feedback`，第二人经 `POST /feedback-samples/{id}/review` 复核后才置 `training_eligible=true`；数据源影子报告 `GET /data-sources/{id}/shadow-report` 按 G3 阈值逐项判定。与下文的差异：PSI 分级在代码中为 `warning`/`alert` 两级，阈值取自基线块；漂移只用于报告与候选流程，没有独立的漂移告警接口。

### 设计
- 定时任务每小时按数据源与模型版本计算 `drift_metric_window`：各特征 PSI、分数分布、拒绝率、人工反馈统计；PSI > 0.2 标记 `drift_status=warning`，> 0.3 为 `alert`。
- 基线分布来自 manifest 附带的训练集统计，不在线更新。
- 反馈：研判员在事件详情标注告警为真/误报 → `feedback_sample`（`label_source=analyst`，`reviewed_by`），默认 `training_eligible=false`，需第二人复核才置 true。
- 漂移只触发通知与候选流程，不改阈值、不改权重。

### 执行步骤
1. manifest 增加 `feature_baseline_stats`（训练端配合）。
2. 实现计算任务与只读接口（接口已存在，补数据写入）。
3. 前端 `ModelsView` 展示漂移趋势；`EventDetailView` 增加标注与复核。
