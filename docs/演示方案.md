# 实时攻击演示方案

更新于 2026-10-17。状态：**DEMO-1—DEMO-7 源码实现与离线回归已完成；未部署、未启动演示、未完成现场彩排**。用户已授权本次实现及中文提交推送（D-A1），明确不现在启动演示；其他准备/现场动作不由此获得授权。入口与完整操作说明见 [scripts/demo/README.md](../scripts/demo/README.md)。2026-10-19 起，只告警的 inbound 规则触发演示按[规则演示任务单](任务/规则演示任务单.md)推进（lab + alert_only 组合、控制通道单连接、S1 扫描端口扩到 64 个、报告输出规则事实），PF 封禁演示仍按本文另行推进。本文不构成采集、发包、root、PF 动作、业务库写入或部署授权。能力口径仍以[能力与局限说明](能力与局限说明.md)为准，不新增已验证现场能力。

## 0. 背景与目标

- 项目主线是“模型接入 → 实时监测与识别 → 处置”。本机真实入站流量绝大多数为良性，现场 30 分钟样本中模型因方向未知全部不适用（[能力说明 6.4](能力与局限说明.md#64-w4p1r-8-现场模型适用性诊断2026-10-16)），无法靠自然流量展示模型能力。
- 已有可用演示：`scripts/p8/lab_demo.py` 在 Mac 回环 lab 回放 CIC 原始 PCAP，经真实模型判定、PF 封禁与 TTL 清理（P1R-4 通过）。它证明链路，但流量是回放而非现场实时攻击。
- 本方案目标：由第二台主机**实时发起**受控攻击，Mac 传感器实时采集，后端模型识别并由 PF 执行器封禁攻击源，到期自动解封；控制台同步展示。
- 复用目标：一次性准备（资产、组合、ACL、工具、代码）只做一次；之后每次运行只更新运行参数并申请短期授权，跑完复位到可再次运行的状态。不能出现“演示一次就消耗一个组合或一段预算、下次要重做准备”的情况（现有 `lab_demo.py` 收尾暂停组合，W4 中 r5、r5′ 因此各消耗一次）。

## 1. 方案选择

| 方案 | 结论 | 原因 |
|---|---|---|
| 传感器部署在 Windows，后端经 Tailscale/SSH 监测 | **不采用** | Windows 实时抓包未验证（仅离线提取与 ONNX 对拍）；Windows/WFP 执行器已按 A10 放弃，只能演示告警、不能演示处置；后端本就由传感器 mTLS 主动上传，SSH 不承担监测 |
| **Mac 为被保护主机，win-dev 为攻击机，经 Tailscale 互通** | **采用** | Mac 已有实时采集、持续托管与真实 PF 执行器；Tailscale 接口与日常 `en0` 流量天然分离；新发起的攻击连接带起始 SYN，方向可判为 inbound，模型适用 |
| 仅回放 PCAP（现有 `lab_demo.py`） | 作为**保底层** | 稳定可复现，但不是实时攻击 |

## 2. 拓扑与数据流

```
win-dev（攻击机，Tailscale 100.x）
   │  受控攻击脚本：只允许目标 = Mac 的 Tailscale 地址 + 登记端口
   ▼
Mac utun 接口（Tailscale）── 靶服务（测试 FTP/SSH/HTTP，非真实服务）
   │  guardlive：接口 = utun，范围 = lab，对端 = win-dev 的 100.x 地址
   ▼
后端：观察 → 多分类推理 → 来源汇总 → 决策 → ActionCommand
   ▼
PF 执行器：按 peer_inbound / peer_service 封禁 win-dev → TTL 到期清理 → 回执
   ▼
控制台：实时态势、事件研判、处置记录
```

- 传感器链路类型：utun 为 `DLT_NULL`，`sensor/internal/hostguard/input.go` 的 `supportedLink` 已支持；实际 utun 编号与地址在执行前逐项确认，不硬编码。
- 演示只用 Tailscale 接口，不包含 `en0`、其他虚拟网络或全 LAN；日常良性流量不进入演示资产，也不会被演示组合封禁。

## 3. 演示场景编排

| 段 | 类别 | 攻击机工具（与 CIC-IDS2017 训练来源对齐） | Mac 靶服务 | 预期处置 | 把握 |
|---|---|---|---|---|---|
| S0 | normal | 浏览、`curl`、一次正常登录 | 测试 HTTP/FTP | 不告警、不封禁 | 中（现场良性未测） |
| S1 | port_scan | `nmap -sS`，限端口范围与速率 | 无需专门服务 | `peer_inbound` 封禁 win-dev，TTL 到期解封 | 较高 |
| S2 | brute_force | patator `ftp_login` / `ssh_login`，固定字典与并发 | 测试 FTP 或独立端口 SSH，**不用真实 sshd** | `peer_service` 只封该端口 | 较高 |
| S3 | dos_slow | slowloris / slowhttptest，单对端并发慢连接 | 测试 HTTP | `peer_service` 封禁 | **低**：L3 受控慢速 0/29 |
| S4 | dos_flood | Hulk / GoldenEye，严格限速限时 | 测试 HTTP | **只告警**（按冻结策略） | 中 |

- 每段之间留足 TTL（60 秒）与预算冷却（命令 expired 后连续健康、无攻击至少 120 秒，见第 6.4 节），段首段尾写入带时间戳的场景标记，便于报告对齐。
- 场景定义（工具、参数、速率、时长、预期处置）写在场景文件中，不写死在脚本里；每次运行可选子集（如只跑 S1、S2），未登记的场景不能运行。
- port_scan 的 `peer_inbound` 会切断 win-dev 到 Mac 的全部入站连接；攻击脚本须在 win-dev 本地按计划自行运行，不依赖演示中途经同一路径的 SSH 控制。
- 识别不理想的类别演示时降为只告警说明，**不为演示调阈值**；需要调整即属于新发布组合，按[验证与验收](验证与验收.md)重新评价与审批。

## 6. 复用设计

### 6.1 一次性准备与每次运行的分界

| 类别 | 内容 | 何时重做 |
|---|---|---|
| 一次性准备 | DEMO-1—DEMO-7 代码；win-dev 攻击工具安装；Tailscale ACL；lab 资产、接口与对端登记；演示组合导入、封存、独立批准（含 platform/canary，如 P-5 需要）；私有配置文件；第一次通过彩排的基线 | 只在第 6.5 节列出的变更发生时 |
| 每次运行 | 填写运行参数、申请本次授权（第 6.7 节）；业务库整库备份；新建 ≤ 30 分钟授权并激活绑定；启动靶服务与采集；执行场景；冷却与收尾；生成运行记录 | 每次彩排、答辩或之后的演示 |

每次运行不新建资产、不导入新组合、不重签报告、不改 ACL；如果某次运行发现必须做这些，说明前提已变，按第 6.5 节处理，不在运行中临时补。

### 6.2 配置外置

- 仓库只提交 `scripts/demo/demo.example.json` 与场景文件 `scripts/demo/scenes.json`；实际配置放在仓库外的私有目录（目录 0700、文件 0600），不写进 Git、plist 或命令行，秘密仍只在 Keychain。
- 配置项至少包括：Mac 与 win-dev 的 Tailscale 地址、靶服务端口、保护集、assetId、executorId、组合 ID 与 subject、TTL、授权时长、业务库与后端地址、运行目录根。utun 编号不写入配置，每次预检按 Tailscale 地址现场解析并记录。
- 场景文件每段含：编号、类别、工具与参数、速率/并发/时长上限、目标端口、预期处置（告警/`peer_inbound`/`peer_service`/只告警）、段间冷却。win-dev 与 Mac 读取同一份场景文件，并在启动时互相核对其 SHA-256，不一致即拒绝运行。

### 6.3 每次运行的生命周期

1. **生成运行号**：`demo-YYYYMMDD-HHMM-<序号>`；运行目录为新目录（已存在即拒绝），所有输出只写入该目录，不覆盖历史运行。
2. **预检**：第 6.4 节的复位项逐项核对通过；记录第 6.5 节的基线指纹并与上次通过的基线比较。任一项不通过即停止，不进入任何写操作。
3. **准备**：业务库整库备份并核验可恢复；新建并独立批准本次授权；激活绑定；启动靶服务与 utun 采集；等待健康链出现新鲜 `healthy`。
4. **执行**：按场景文件逐段运行，段首段尾写标记；段间等待命令 expired 和冷却完成。
5. **收尾（正常）**：停止攻击 → 等全部命令 TTL 自然到期为 expired → 保持采集，连续健康且无攻击至少 120 秒，确认预算恢复事件已登记 → 停止采集与靶服务 → 撤销授权、挂起绑定 → 核对 PF、`en0` 持续监测恢复 → 写运行记录。
6. **收尾（异常）**：任一步失败或人为中断，先撤销授权、停止攻击与采集，保证 PF 无残留，再记录未完成的冷却；安全优先，接受下次运行前需要按第 6.4 节恢复预算。
7. 收尾可单独重跑：`run.py --teardown-only <运行号>` 按该运行目录中记录的准确对象逐项收尾，已完成的项跳过；不按前缀或模糊匹配清理。

### 6.4 运行之间的状态复位

下一次运行的预检逐项要求：

| 项 | 要求 | 不满足时 |
|---|---|---|
| 组合与绑定 | 组合 active；绑定 suspended；无未撤销的演示授权 | 组合已暂停即不可复用，按第 6.5 节换组合 |
| 攻击源预算 | win-dev 的 `peer_inbound` 与各 `peer_service` 稳定目标处于新预算周期，无本周期撤销墓碑 | 上次未完成冷却：在新授权下先只采集、不攻击，连续健康 120 秒以上等待自动恢复；仍不恢复则走人工核对与审计流程（P-10），不换对端地址或预算身份绕过 |
| PF | 执行器专属 anchor 零规则、别名为空，无项目外规则变化 | 停止并报告，不自动清理非本项目规则 |
| 靶服务与端口 | 靶服务未运行，登记端口未被占用 | 按上次运行目录记录的 PID 停止，不按名称批量结束进程 |
| 采集 | utun 采集未运行；`en0` 持续监测按 P-7 的决定处于正常状态 | 停止并报告 |
| win-dev | 无残留攻击进程；工具版本与基线一致 | 停止并报告 |
| 业务库 | 上次运行的备份与运行记录已保存；本次备份可恢复 | 不进入写操作 |

演示产生的观察、告警、命令与审计按业务库既有规则追加保留，不删除、不回滚历史运行的事实；各次运行靠运行号、lab 资产与时间段区分，统计时与真实主机数据分开。

### 6.5 基线固定与变更影响

每次运行记录基线指纹：仓库提交、后端 release 与 JAR SHA-256、传感器/执行器 release、组合 ID/subject 与模型/策略哈希、场景文件 SHA-256、win-dev 工具版本、Tailscale 与 macOS 版本。与上次通过的基线不同的运行标记为“非同基线”，答辩前须用答辩基线再完整彩排两次。

| 变更 | 需要做的事 |
|---|---|
| 场景参数、工具版本、Tailscale/系统小版本 | 重新彩排（只告警 + 真实 PF 各一次以上），不需要新组合 |
| Tailscale 地址或 utun 链路类型变化 | 更新配置、ACL 与对端登记；新对端是新的预算身份；重新彩排 |
| 执行器代码变化 | 按 P-5 确认是否需重签 platform/canary；重新彩排 |
| 模型、阈值或类别策略变化 | 属于新发布组合，按[验证与验收](验证与验收.md)重新评价、封存与审批，不在演示流程中处理 |
| 组合被暂停（异常收尾或误操作） | 不能再激活，需新组合（同 subject 时参照 P1R-4 的 r5″ 流程）；记录消耗原因 |

### 6.6 运行记录模板

每次运行在运行目录生成 `record.json`（机读）与 `record.md`（可读），字段：

- 运行信息：运行号、用途（彩排-只告警 / 彩排-PF / 答辩 / 其他）、执行人、开始/结束时间、基线指纹、授权 ID 与窗口、备份文件与核验结果。
- 逐段结果：

| 段 | 开始/结束标记 | 预期处置 | 首条告警类别与时延 | 命令 ID / 范围 | applied / expired 时间 | 预算事件 | 结论 |
|---|---|---|---|---|---|---|---|
| S0—S4 | | | | | | | 符合 / 不符合 / 降级 |

- 收尾：PF 零规则、别名清理、root 清理核验、授权已撤销、绑定 suspended、组合 active、预算已恢复、`en0` 持续监测恢复，均为 true/false；任一 false 即本次运行不通过。

## 7. 安全约束

- 攻击只发往 Mac 的 Tailscale 地址与登记端口；脚本内置白名单，Tailscale ACL 再限制一层。不扫描或攻击任何第三方、LAN 或公网地址。
- 只封禁 win-dev 的 Tailscale 地址；保护集包含 SSH 管理、后端 18080/18082、Tailscale 控制流量；不接管默认放行策略，不覆盖既有 PF 规则。
- 封禁带 TTL（60 秒）和目标累计预算（120 秒）；演示结束核对 PF 无项目规则残留，任一清理项为 false 即停止并报告。
- root 只在用户在场时由系统密码框输入；授权窗口逐次申请，过期即撤销。
- 规则来源保持 `autoEligible=false`；真实主机（`authorized`）组合 r6 不受本方案影响，仍只告警。
- 演示结果只报告、不作为模型现场成绩或误报率，不改写 G3 与既有证据。

## 8. 验收标准（彩排）

1. 只告警彩排：S0 无告警；S1、S2、S4 各产生对应类别的模型来源告警；S3 如实记录检出与否。
2. 真实 PF 彩排：S1、S2 至少各一次命令 applied → TTL 到期 expired → 执行器零规则 → root 清理核验通过；S0 期间 0 封禁。
3. 全程 `en0` 无封禁、PF 无项目外规则变化、持续监测在演示后恢复。
4. 收尾各项为 true，并按第 6.4 节复位后**不做任何一次性准备**即可直接开始下一次运行。
5. 同一基线下连续两次完整彩排按第 6.6 节判定一致，才进入答辩使用；同时录屏留作现场备份。

## 9. 答辩现场流程与降级

答辩当天与彩排走同一条第 6.3 节流程，只是运行号用途记为“答辩”、场景子集取彩排一致的段；提前完成预检与授权申请，现场只从“执行”开始。

1. 开场：控制台实时态势，说明被保护主机、攻击机与隔离范围。
2. S0 正常流量 → S1 扫描封禁与解封 → S2 暴力破解端口级封禁 → S3/S4 视彩排结果展示或只说明。
3. 收尾：处置记录中展示命令、回执、到期清理与审计。
4. **降级顺序**：实时某类未识别 → 该类改为说明；实时链路整体异常 → 切换到 `lab_demo.py` PCAP 回放（保底层）→ 再不行播放彩排录屏。注意 `lab_demo.py` 现有收尾会暂停组合，每用一次消耗一个组合，因此只作为最后的实时保底，不作为日常复用路径。
