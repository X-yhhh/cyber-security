### 2.1 P1R-5：只告警形态的 D2 重启验收

本次 D2 对象是五个用户 LaunchAgent（`backend/targets/recovery/executor/sensor`），没有 PF executor/recovery LaunchDaemon。验收时点为**整机重启并由原用户登录后**；重载服务、换 PID 或重启应用均不能代替整机重启。系统域 PF 模式的“先清旧规则再收新命令”继续适用原恢复流程，本次 observer 不领取命令，不能据此声明该 PF 恢复能力通过。

| 检查 | 本部署形态的通过条件 |
|---|---|
| 主机与启动 | 重启前后绑定同一本机；`kern.bootsessionuuid` 改变，`kern.boottime` 晚于重启前封存时刻；保存实际启动时间与证据摘要 |
| 服务自动恢复 | 五个定义完整且与重启前封存字节一致；登录后 backend、targets、recovery、executor 自动运行，PID、程序路径与发布摘要对应；验收器不得 bootstrap/kickstart 这些服务掩盖失败 |
| sensor 不续采 | 定义保持 `RunAtLoad=false/KeepAlive=false`，登录后未运行、`runs=0`；没有新采集子进程、boot/spool、观察批次或现场心跳/健康窗口。保留已撤销授权与 suspended 绑定，不延长采集期限 |
| observer | 配套部署 P1R-3 recovery/run 后，两个新鲜脉冲的身份和 PID 与 launchd 一致；进程 bootId 均改变，后端唯一 observer 的 bootId 与 run 相同且心跳新鲜。只证明存活，后端原始 unknown 与 PF 未检查状态照实保留 |
| 后端与依赖 | 原 JDK 25、JAR、托管前端和外部配置摘要不变；仅监听回环 18082，私有 CA 验证的 TLS 1.3、live/ready/actuator 均通过，MySQL/RabbitMQ 就绪；relay/consumer 开启，automation 关闭 |
| 无旧规则 | 重启前后分别以系统授权只读核对 PF 状态、根/Apple/用户/hostguard 锚点及 lab 回环别名；没有本项目残留规则、PF 账本或 root 执行器，也不安装 PF 守护进程、不启用 PF、不新建阻断 |
| 数据与恢复 | 保留精确恢复证明及原生效/生成 plist；admin、凭据、权限、模型/阈值/策略/组合、Flyway 与已有业务事实不变。仅允许启动审计、登录会话、observer 心跳/幂等等运行投影变化；真实资产命令仍为 0 |

重启前封存私有证据、程序与配置摘要、数据库备份及恢复入口，准备一次性登录验收器，先验证其当前 boot 下不会误判通过。验收器只读等待依赖，不启动采集、不修正服务状态；失败留下日志和待验收状态，不自动回退业务库、不宣称通过。通过后才回写状态及执行已授权的中文提交/推送，并核对远端 SHA。一次性验收入口完成后移除，原配置、账本、发布、备份和运行证据保留。

## 4. 业务库备份和恢复演练

### 4.1 每次切换前

1. 确认准确主机、schema=`cyber_security`、MySQL 8、现有 admin/用户、当前 Flyway 版本（2026-10-16 已 V27）和对应发布组合；记录进程/监听，不把预览 schema 当成业务库。
2. 暂停本次服务的写入入口、relay、consumer 和采集上传，处理已接收但未完成的任务；确认无本次或其他客户端连接业务库。不能证明停写时暂停切换。
3. 在仓库根运行：

   ```sh
   sh executor/python.sh -B scripts/p8/backup_restore.py
   ```

4. 脚本从 Keychain 读取本机 DB 凭据，不回显；`mysqldump --single-transaction --routines --triggers --events --hex-blob --set-gtid-purged=OFF --no-tablespaces` 保存完整库。
5. 恢复到本次随机 schema，比较所有表的有效结构、行数及按主键对应的逐行 SHA；dump 前后业务库也须一致。DOUBLE/FLOAT 按 IEEE 位检查。MySQL 8.0.42 的 JSON 文本解析可能改变浮点末位：脚本同时生成 `json-double-fidelity.sql`，在恢复库以 SQL DOUBLE + JSON_SET 还原原精度；源库不改，逐行校验不放宽。结构摘要仅归一化冗余字符集声明和 AUTO_INCREMENT 下一个序号。
6. 全部通过后只删除该随机库，保留 `database.sql`、`json-double-fidelity.sql`、`source-before.json`、`restored.json`、`restore-proof.json` 和 `result.json`。要求 `passed=true`、`temporarySchemaDeleted=true`；用 `shasum -a 256` 分别核对两份 SQL 与恢复证明中的哈希。失败不得进入业务切换。

DB-9 的 `register_alert_only.py` 内置相同备份/恢复流程，另要求业务开始状态、输入和最终表增量与演练相同。已 approved 的 r6 不重复登记。命令见 [脚本说明](../scripts/p8/README.md)。

### 4.2 实际恢复（另一次有目标的操作）

1. 先停写并停止准确服务，保存失败现场的独立备份和日志；选定已验证 dump、源 schema、时间点和恢复目的。明确恢复会丢失该时间点之后的业务状态；获得对应恢复授权后才执行。
2. 先再次恢复到新随机库验证，再决定覆盖原库或切换到恢复库；当前工具只提供随机库演练，不提供一键覆盖业务库。不得把 DROP/TRUNCATE 直接用于业务库试错。
3. 恢复时密码通过受控环境或文件供 mysql 客户端使用，不使用 `-p明文`。先导入 `database.sql`，再向同一目标库导入已校验的 `json-double-fidelity.sql`；缺失补充 SQL 时该备份不满足精确恢复要求。恢复完成后核对所有表、Flyway 校验和、admin 哈希、审批链、组合/能力/报告引用、幂等记录、待处理消息和动作恢复事实。
4. MySQL 与 RabbitMQ 无跨系统原子快照。恢复后旧消息按幂等键重新校验；暂停来源不明或与恢复点冲突的消息，保留死信与审计。禁止通过清空共享队列“修好”状态。

## 5. 启动和切换顺序（待 P8 实际执行）

2. 若只需程序回退，恢复上一已验证 JAR 与受控配置；保持自动化 false、上传暂停。迁移只能向前追加，不能篡改已执行 Flyway；数据库版本不兼容时停在人工核验，不强行启动旧程序。

### 9.0 目标与口径

**目标**：在用户自有的远端 Ubuntu 服务器上**持续运行**传感器（开机自启、异常自动恢复），采集该主机的全部入站 TCP，经 mTLS 上传到本机后端。后端用 r6′ 只告警组合产生观察、推理、规则事实与告警，在控制台可见。

**范围**：
- **只采集、只告警**。不开发 Linux 执行器，不登记任何执行能力，不做拦截。真实拦截要等模型训练完善后，另行开发 Linux 执行器、完成验收并重新授权，不在本单范围。
- 远端主机按**真实资产**登记：`platform=linux`、`environment=authorized`、采集范围 `all_inbound_tcp`。组合复用 Mac 真实资产当前使用的 r6′，不新建策略，不改模型、阈值和规则。

**只新增，不修改既有 Mac 链路**：
- 以下内容一律不改：`sensor/` 的 Go 源码、`scripts/p8/`（`sensor_service.py`、`enroll.py`、`status.py`、`observer_executor.py`、`launchd.py`、`capture_permission.sh`）、`executor/`、后端 `ManagedSensorLifecycle` 与机器接口、Mac 的常驻服务配置、en0 传感器的二进制与配置。
- Linux 部分全部是新文件，放在新目录 `scripts/linux/`。远端使用的 `guardlive` 是**同一份 Go 源码**在 Ubuntu 上的 cgo 构建，`sensor_service.py` 和 `observer_executor.py` 原样复用。

**硬前提：不得影响远端现有 NewAPI 服务**（用户 2026-10-21 同意 D-R2、D-R3 时提出，优先于本节其他所有要求）：

### 9.0.1 设计依据（代码事实）

| # | 事实 | 采用的做法 |
|---|---|---|
| F1 | `guardlive` 的持续模式（`-duration 0`）要求一个真实的直接父进程通过 `-parent-pid` 托管（[managed.go](../sensor/cmd/guardlive/managed.go)）。Mac 上这个父进程是后端（`ManagedSensorLifecycle` → `sensor_service.py --parent-pid` → exec `guardlive`） | Linux 上新增一个**常驻托管进程** `scripts/linux/supervisor.py`，由 systemd 拉起，扮演 Mac 后端的父进程角色，原样调用 `sensor_service.py --parent-pid <自身 PID> --backend-url https://127.0.0.1:18082`。`guardlive` 与 `sensor_service.py` 不用改 |
| F2 | `sensor_service.py` 只在 `localAddressSource=interface` 时读接口地址，用的是 `/sbin/ifconfig`，Ubuntu 默认没有 | 远端配置使用静态 `localAddresses`（R0 确认服务器地址固定），不设 `localAddressSource`，因此不会走到 ifconfig。地址变化时由 Linux 托管进程检测并停止，需重新登记配置 |
| F3 | `--backend-url` 和 `observer_executor.py` 都只接受回环 HTTPS（`127.0.0.1`） | 远端通过 **SSH 反向隧道**把服务器的 `127.0.0.1:18082` 转发到 Mac 的 `127.0.0.1:18082`。回环约束和服务端证书的 IP SAN 都不用改，后端也不暴露到网络 |
| F4 | 上传器在连接失败时按退避重试；健康窗口每秒一个，内存队列上限 4096（约 68 分钟），超过就以 `HEALTH_QUEUE_OVERFLOW` 致命退出；观察批次写入按 bootId 隔离的磁盘 spool；`guardlive -drain` 可续传某个 bootId 未确认的批次（[uploader.go](../sensor/internal/guardup/uploader.go)、[main.go](../sensor/cmd/guardlive/main.go)）。`GuardIngest.heartbeat/batches` 中，心跳会把 `sensor_agent.guard_boot_id` 改为心跳的 bootId，批次要求 bootId 与该值一致 | 当前 boot 的断连重试由上传器处理；健康队列容量不是断线续传保证。溢出后托管进程换新 bootId 重启，旧 boot 只在没有采集子进程时、每次启动和重启采集之前用 `-drain` 补传，失败保留至下一次启动/重启前重试。运行中每 5 分钟只清理；并行补传会覆盖当前 bootId，使当前采集被拒为 `BOOT_ID_MISMATCH`，托管进程以退出码 3 停机。只改托管进程，不改 Go |
| F5 | 上传遇到不可重试错误（身份、范围、授权）时 `guardlive` 退出，`report.json` 的 `upload.fatalCode` 记录原因 | 托管进程读取 `fatalCode`：属于授权或身份类时停止且不重启（退出码 3，systemd 单元配置 `RestartPreventExitStatus=3`）；其他故障与 Mac 后端一样，30 秒退避后重启 |
| F6 | 后端资产、传感器、执行器登记原先只接受 `macos`/`windows`（`guard/GuardAdministration.java` 的 `asset()`、`machine()`）；`GuardCatalog` 原先只有 `peer_inbound` 限定 `macos`，`peer_service` 能力登记没有平台校验，激活只看能力等级、不看平台；运行时 `GuardEligibility` 要求能力平台等于执行器平台 | A1 在 `GuardAdministration` 追加 `linux`，并按用户 2026-10-21 批准的范围，仅在 `GuardCatalog.capability()` 增加 `macos`/`windows` 平台白名单，在 `activate()` 增加 Linux 资产的非 `alert_only` 策略拒绝检查；`peer_inbound` 既有逻辑及 `GuardEligibility` 不动 |
| F7 | `enroll.py` 写死 `platform='macos'` 和旧 r6 组合常量；`status.py` 会检查本机 launchd 与 PF | 新写 `scripts/linux/enroll.py` 与 `scripts/linux/status.py`，调用同一组 v2 接口；旧脚本不动 |
| F8 | 组合激活按资产处理，只挂起**所列资产**原有的 active 绑定（`GuardCatalog.activate`） | 为新资产单独激活 r6′，理论上不影响 Mac 绑定；仍须克隆演练证明（B4） |
| F9 | `all_inbound_tcp` 的 BPF 保留一端为登记地址的全部 TCP，不接受端口白名单（[live.go](../sensor/internal/hostguard/live.go)） | 远端 22（含隧道）和 443（NewAPI 客户）流量都会被采集，见 D-R2 |
| F10 | `lab_peer_tcp` 才有 `utun` 与 Tailscale 地址限制；采集文件锁已支持 `linux`（[lock_unix.go](../sensor/cmd/guardlive/lock_unix.go)）；实时采集入口的构建条件是 `cgo` | 在 Linux 容器中装 `libpcap-dev` 后用 cgo 构建。B2 预演发现唯一的平台问题是 `go.sum` 缺 `x/net`，由 A0 解决；其余问题停止并报告，不顺手修改共享代码 |

**停止条件**：

| 情况 | 处理 |

## 10. 本机 en0 持续监测（2026-10-17 起）

本节由原《传感器持续监测》并入（2026-11-01 文档整理），记录当前 Mac `en0` 的现行采集方式。用户已明确授权当前 Mac `en0` IPv4 入站 TCP 在本项目后端运行期间持续监测。完整实施与验证见[实施记录 6.55](系统实施记录.md#655-后端托管网卡传感器与持续监测2026-10-17)。本补充更新该主机的现行采集方式，以上既有短窗口验收及历史授权记录保留；其他资产不因此获得持续采集或执行授权。

当前 18080（IDEA local）与 18082（deploy）都启用托管，唯一捕获由持锁后端负责。最终运行 release 为 `20261017-managed-heartbeat-163138`，同时修正默认 15 秒心跳与控制面 10 秒陈旧判定不匹配的问题；8 次连续完整巡检通过。旧 sensor LaunchAgent 不再启动采集；重启验收中的历史“不续采”结论不适用于本次用户明确授权的持续模式，当前模式尚未另做整机重启验收。

2026-10-17，用户明确要求“后端启动就一直监测，跟随后端一起结束”。本次接入当前 Mac 的 `en0`，被动观测该接口可见、登记本机 IPv4 地址的入站 TCP，使用既有 r6 只告警组合。不能据此声称覆盖其他主机、整个局域网或已经取得现场模型准确率。

### 10.1 使用与生命周期

- 日常在 IDEA 启动 `CyberSecurityApplication` 即可，后端就绪后自动启动 `guardlive`，停止后端时自动结束采集；不再每 30 分钟手工启动。
- 前端入口仍为 `http://127.0.0.1:5173`，实时态势位于 `/console/overview/live`。已接入的本机后端改用回环 TLS，Vite 通过受信私有 CA 代理至 18080。
- 当前另有部署后端 18082。两份后端共享文件锁，同一时刻只有一个采集进程；拥有采集的后端退出时，其采集子进程退出，另一份仍运行的后端可以自动接管。需要完全停止监测时，应停止两份后端，或在控制台撤销本机观测授权。
- 普通模式仍限制在 1 秒至 30 分钟；持续模式必须同时指定 `-duration 0`、真实直接父进程 `-parent-pid`、`authorized/all_inbound_tcp` 和上传配置。research、lab 和文件回放不能使用此模式。
- 父进程正常关闭时先发送 SIGTERM、等待封口与上传，最多等待 8 秒；即使父进程被强制结束，采集程序也检查 PPID 变化并停止。启动器的第二把跨 exec 文件锁覆盖旧采集进程退出前的间隔。
- 异常退出后由后端重试；启动失败至少退避 30 秒。配置、证书、构建哈希、授权或 BPF 权限不满足时显式失败，不降级成模拟采集。
- 上传器默认每 5 秒发送心跳，与控制面 10 秒陈旧阈值衔接；健康窗口持续排队时也先检查到期心跳，避免采集窗口健康而存活状态周期性陈旧。

### 10.2 授权与配置

既有授权接口要求 `validUntil` 非空。本次通过原有申请人/独立审批人接口登记可撤销的持续观测授权，`9999-12-31T00:00:00Z` 是该必填字段的兼容上界，实际采集时段仍由后端生命周期和服务端有效授权共同限制。旧短窗口授权及撤销记录保留，后端不会自行批准或续签授权。

配置、密钥和账本均位于仓库外服务目录 `~/Workspace/development/services/security/cyber-security/`。`config/local-sensor.properties` 只在完成登记的本机存在，引用既有受控部署配置提供数据库、RabbitMQ、TLS 和签名材料，不在仓库保存秘密。`cyber.sensor.enabled/root/release/python` 控制托管开关、服务根目录、已核验运行版本和解释器入口。

持续观测沿用 rc.2 特征和 1.0.0 现场采集健康协议，新的 `guardlive` 构建 SHA 已通过原传感器配置审批。模型、阈值及策略不变；自动化关闭、执行能力为空，不授予 PF 权限。此次没有数据库迁移、新增权限键或人工/机器 API。

### 10.3 macOS 权限与本地文件

已通过 macOS 管理员授权安装 `com.xyh.cyber-security.capture-permission` LaunchDaemon。root 拥有的辅助脚本只检查登记用户的本项目 Java 后端 PID，为该用户临时开放 `/dev/bpf0` 的 0600 访问；后端不在或身份不符时恢复 root:wheel 0600。辅助程序不采集数据、不运行用户命令、不配置防火墙，`guardlive` 以普通用户运行。

持续模式的观察副本和头部轨迹各按 8 MiB 轮转，保留 3 份备份；轮转后的局部轨迹不能当作完整回放证据。未确认批次与已确认回执的原字节 spool 不由此轮转删除，业务库和 spool 仍需按实际使用量规划容量。原始地址与轨迹仅留在受控本地目录。

当前 IPv4 地址取已登记的本机配置；换网、地址变化或 `en0` 不可用时，应重新核对本机地址与采集范围，不能仅凭进程存活认定观测完整。系统休眠、断网以及不同平台的重新接入未作为此次验收结论。

### 10.4 验证与停用

实际完成 89 表备份及隔离恢复的逐行、结构核验；随后验证 IDEA 启动、真实 BPF 句柄、mTLS 心跳、现场健康窗口、观察与推理记录入库、停止后子进程消失与设备权限回收、重启新 bootId，以及两份后端之间的唯一采集保护。

当前现场观察的方向仍可能为 `unknown`；本次抽查的新会话推理返回 `MODEL_NOT_APPLICABLE`。这类记录按既有契约保留，不伪造方向或模型得分；规则研判与告警链路继续使用既有策略。健康通过不等于模型适用或准确率验证通过。

### 10.6 本机地址经常变化（2026-10-18）

授权与传感器配置只绑定接口 `en0`、地址族和采集范围，不绑定具体 IP。受控配置 `sensor.json` 设置 `"localAddressSource": "interface"` 后：

- `scripts/p8/sensor_service.py` 每次启动采集前用 `ifconfig` 读取 `en0` 当前 IPv4（排除链路本地 169.254/16 与回环），写入本次会话配置；没有可用地址（断网、关闭 Wi-Fi）时返回 `INTERFACE_ADDRESS_UNAVAILABLE`，不启动采集。
- `guardlive` 每 5 秒核对接口地址；与本次会话地址不一致（换网、DHCP 重新分配、接口无地址）即正常收尾、上传排空后以退出码 3 结束，日志写明“采集接口地址已变化”。
- 后端 `ManagedSensorLifecycle` 每 5 秒检查子进程，退出后最迟约 30 秒用新地址开启新会话（新 bootId，新的会话目录）。地址变化前后属于不同会话，健康链在两者之间断开，不会把旧会话的统计接到新地址上。
- 该选项只允许后端托管的 `authorized` + `all_inbound_tcp`；短窗口、lab 与回放仍使用配置中的固定地址。
