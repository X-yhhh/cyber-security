## 0. 目标与口径

**演示内容**：win-dev 通过 Tailscale 向 Mac 实时发起受控流量；Mac 在 utun 上采集；后端按**与真实资产 r6′ 相同的策略**（窗口规则只对 inbound 观察适用）判定，同时产生模型告警和 inbound 规则告警；正常段不产生任何告警。只告警，不封禁。

**口径**：
- 演示资产为新登记的 lab 资产（utun 接口）。组合为 `lab + alert_only`，直接复用 r6′ 已审查的策略 `68a57070-df9f-51fe-9837-daa0858f68c1` 和模型 `f7734c7c-1c9a-52dd-8e89-79f36b2f3815`，阈值、规则不变，不新建策略。后端已支持：`alert_only` 组合封存只要求 final，激活时不检查执行能力等级（`GuardCatalog.seal/activate`，开发路线 Q5）。
- 真实资产（`cb7e844b…`、r6′ 绑定 `54dd1707…`）与 en0 持续监测**不得受任何影响**。
- 不做 PF 封禁。原演示方案中的封禁演示（auto 组合、platform/canary、后端自动化开关）另行推进，不在本单范围。
- C1b 暂缓（开发路线 Q12）：本单不改提取契约和 `contexts.*` 字段。
- 不改模型、阈值、冻结策略和规则。规则命中只作为演示事实报告，不作为模型成绩或误报率。

## 1. 本单修正的三处既有设计问题

1. **控制通道污染攻击对端的上下文**：`run.py` 在场景执行期间约每秒调用一次 `remote.state()`，每次都是一条新的 `ssh win-dev`。`win-dev` 解析到 Tailscale 地址，也就是攻击对端，且没有开 ControlMaster。传感器把这些本机发起的连接计入该对端的上下文，`contexts.*` 既是规则字段也是模型特征，于是 S0 会误触发 brute-starts/slow-starts，模型输入也被抬高。修正见 A1。
2. **S1 只扫 16 个端口**，scan-ports 需要 5 秒内 ≥39 个，规则不会触发。修正见 A2。
3. **`report.py` 只统计模型告警**，无法证明 inbound 规则触发。修正见 A3。

### A1 控制通道复用单连接

- **位置**：`scripts/demo/remote.py`、`scripts/demo/run.py`、`scripts/demo/test_demo.py`
- **做法**：
  1. `Remote` 的每次 ssh 调用都增加 `-o ControlMaster=auto -o ControlPath=<私有根>/locks/ssh-%C -o ControlPersist=yes -o ServerAliveInterval=5 -o ServerAliveCountMax=3`；ControlPath 的私有根从配置 `root` 传入，`locks` 目录为 0700。展开后的路径超过 100 字节时拒绝启动（macOS unix socket 上限为 104）。
  2. 新增 `Remote.open()`：`ssh -O check` 不通就建立主连接（执行一次 `utc()` 即可），返回建立时间。`Runner.execute()` 必须在 `preflight.inspect()` 之前、也就是 utun 采集启动之前调用它，并把 `controlMaster.openedAt` 写入 state。
  3. 新增 `Remote.close()`（执行 `ssh -O exit`），在 teardown 中 `captureStopped` 之后调用；`--teardown-only` 也调用。重复调用应当安全；失败只计入 `cleanupErrors`，不阻止其他清理项。
  4. worker 的本地时限、STOP 与断连期间自主运行的逻辑不变。
- **验收**：
  - 单测断言：所有 ssh 调用的参数都带上述选项；`open()` 早于 sensor 进程启动（用假 `Processes` 记录顺序）；teardown 调用了 `-O exit`；ControlPath 过长时拒绝。
  - 现场验收在 C0：每段内 Mac 发往 win-dev 的新建连接 ≤ 1，由 A3 的 `controlConnections` 字段给出。
- **禁止**：改走局域网地址或其他接口来绕过问题（会改变管理路径和 ACL 证明）；关闭 `BatchMode`。

### A3 报告输出规则事实与规则结论

- **位置**：`scripts/demo/control.py`（`facts`）、`scripts/demo/report.py`、`scripts/demo/test_demo.py`
- **做法**：
  1. `facts.decisions` 增加 `ruleId`（取自 `evidence_json->>'$.ruleId'`）和 `direction`（关联 `guard_episode.direction`）。
  2. `facts` 增加 `ruleEvaluations`：本资产、本时间范围内 `guard_rule_evaluation` 按 `(rule_id, family, applicable, matched, 观察 direction)` 计数，并给出每条规则 `matched=1` 的最早 `created_at`。观察方向关联 `guard_observation.direction`。只读，在同一快照内查询。
  3. 增加观察方向计数（inbound/unknown/outbound），以及每段的 `controlConnections`：从本次运行的 `observations.jsonl` 中取 `direction=outbound`、对端为 win-dev 的观察，**按连接去重**计数。
  4. `report.py` 每段输出 `ruleHits`（每项含 ruleId、family、direction、count、firstAt、latencyMs），并把 `modelConclusion`（沿用现有模型判定）和 `ruleConclusion` 分开。期望规则用常量 `RULE_EXPECTATIONS = {'S1': {'scan-ports'}, 'S2': {'brute-starts'}}`，不改场景文件格式。
     - S1、S2 的 `ruleConclusion` 判为符合，需要同时满足：期望规则在 inbound 观察上至少命中 1 次；该段非 inbound 规则命中为 0；该段 `controlConnections` ≤ 1。
     - S0 的 `ruleConclusion` 判为符合，需要满足：无任何规则命中，且 `controlConnections` ≤ 1。
  5. 新增运行级 `ruleDemo.passed`，需要同时满足：S0 无任何来源的告警；S1、S2 的 `ruleConclusion` 都符合；全程非 inbound 规则命中为 0；规则来源命令为 0；收尾各项全部为 true。原有的 `passed`（模型口径）保留原逻辑并单独报告，两者都写进 `record.md`。
  6. `--compare` 增加逐段规则 ID 集合一致的比较。
- **验收**：单测覆盖以下情形均判为不符合：S1 只有 brute-starts、没有 scan-ports；出现非 inbound 规则命中；S0 出现规则告警；某段 `controlConnections=3`；两次运行的规则集合不同（compare 判不一致）。
- **禁止**：把规则告警计入模型 `detected`；改变“只告警运行不得签发命令”的判定。

### A6 演示用第二 BPF 设备 helper

- **位置**：新增 `scripts/demo/capture_permission_demo.sh`、LaunchDaemon 模板 `scripts/demo/com.xyh.cyber-security.demo-capture-permission.plist`（只是模板，不安装）、`scripts/demo/run.py`、测试
- **背景**：现有 `scripts/p8/capture_permission.sh` 只在常驻后端 java 进程存活时把 `/dev/bpf0` 交给 en0 采集，`/dev/bpf1`—`bpf3` 为 root 0600，因此预检报 `SECOND_BPF_PERMISSION_REQUIRED`。
- **做法**：
  1. 新 helper 只管理 `/dev/bpf1`，不碰 `bpf0`。它每秒读取 `<私有根>/locks/demo-run.pid`：要求该文件属于采集用户且不是软链接，指向的进程由该用户拥有，命令行为配置中的 python 运行 `scripts/demo/run.py --config <私有根>/config.json`。条件满足时把 `bpf1` 改为该用户可读写；否则以及退出、收到信号时，恢复 `root:wheel 0600`。
  2. `run.py`：在 `execute()` 的第一步、预检之前，原子写入 pid 文件，并等待 `/dev/bpf1` 可读写（最多 5 秒，超时报 `SECOND_BPF_PERMISSION_REQUIRED`）；teardown 最后删除 pid 文件。
- **验收**：用假 `ps`/`stat` 测试授权与撤销的各分支（pid 文件不存在、是软链接、属主不符、进程不符、进程退出）；`sh -n` 语法检查通过。
- **禁止**：修改现有 `capture_permission.sh` 或其 LaunchDaemon；授予 `bpf0`；执行任何用户传入的命令。

### A7 文档同步

## 7. 停止条件与回退

| 情况 | 处理 |
|---|---|
| 真实资产任何对象变化（r6′ 绑定、en0 采集 PID/配置/boot、真实资产授权） | 立即停止，执行 `run.py --teardown-only <运行号>`，由 Claude 核对并恢复 |
| PF 出现任何规则或 anchor 变化（只告警运行不应发生） | 立即停止，不自动清理非本项目规则，报告用户 |
| 业务库写入前的备份或恢复核验失败 | 不进入写操作 |
| 流量目标不在白名单，或 win-dev 有残留进程 | 停止，按运行号精确收尾 |
| 非 inbound 规则命中 > 0，或出现规则来源命令 | 停止，作为缺陷分析 |
| S0 出现告警 | 停止彩排，用 `ruleHits` 和 `controlConnections` 区分是规则计数还是模型判定；不调阈值 |
| 某段 `controlConnections` > 1 | A1 未生效，回到 A 阶段修复 |
| S1 没有 scan-ports | 先查 nmap 实际发包速率与端口覆盖（`nmap-S1.log`），按 B6 的结论切换 `connect_scan`；不改阈值 |
| 模型对 S1、S2 漏检 | 不停止，记为降级并汇报 |

| 对象 | 回退方式 |
|---|---|
| B3 信任变更 | 恢复原 `deploy.properties` 并重启常驻后端 |
| B4 helper | `launchctl bootout`，删除 plist，确认 `bpf1` 恢复 root 0600 |
| B5 ACL | 用户用导出的备份恢复 |
| B7/B8 业务库对象 | 不删除；组合可退役（retire），资产可停用；保留审计事实 |
| 单次运行 | 执行 `run.py --teardown-only <运行号>`，撤销授权、挂起绑定，组合保持 approved/active 以便复用 |
