# 开发路线

更新于 2026-10-07，host-guard v5 唯一实施路线。**P1、P2 已完成并收口；P3-A（A1–A6）已完成，A7 可选未执行。P3-B 已收口（负责人书面调整累计拟合上限为 33，单次复现与 v3 候选逐位一致，B5 完整框架对拍通过）；P3-C 未开始。P4 后端与数据库已完成，需为多分类和来源汇总做接入改造；P5 执行器代码已推进，平台验收未完成。** 当前实现边界见 [现状与迁移](现状与迁移.md)。

## 1. 目标与架构

系统持续监测授权主机的入站流量，识别 4 类攻击（端口扫描、暴力破解、洪泛 DoS、慢速 DoS），并对确认的攻击来源实施限时、可撤销的本机防火墙封禁。各组件分工如下：

| 组件 | 只负责 | 主要阶段 |
|---|---|---|
| 传感器（Go） | 抓包、组流、计算特征并上报，不做判断 | P2（已交接） |
| 检测（后端 ONNX 推理） | 对每个快照输出攻击概率与类别，不决定是否封禁 | P3、P4 |
| 规则引擎（后端） | 基于观察字段的阈值规则，作为第二条检测来源 | P3、P4 |
| 决策（后端） | 按来源汇总模型与规则结果，决定告警或封禁候选，检查白名单、授权与预算 | P4 |
| 执行器（Python） | 校验签名命令，安装/清理 PF 或 WFP 规则并回执 | P5 |

验收采用 3 道硬门槛：G1、G2 衡量模型，G3 衡量闭环。另有类别自动资格，定义见 [验证与验收](验证与验收.md)。

## 3. 统一规则

- 机器结构维持 `host-guard/5.0.0-rc.2`。决策版本 `host-guard-decision/2026-10-06.1`、评价版本 `host-guard-evaluation/2026-10-07.1`、类别映射 `host-guard-class-map/1`、标签规则 `host-guard-label/2`、规则引擎 `host-guard-rules/1`；定义见 [检测与处置契约](检测与处置契约.md)、[数据与模型方案](数据与模型方案.md)。
- 需要改变机器结构的项（新封禁范围、多类策略字段）登记为 rc.3 变更，随 P4/P5 代码一起升级 Schema、示例和测试，见 [契约目录](contracts/README.md#下一版结构变更)。
- P3-A 仅为准备与封存处理原件、标签；冻结后先锁定模型、阈值和策略，P6 才读取 test 做评估。模型分数、离线判定和实际 OS 动作分别报告。
- docs 只保存当前规范与计划；run 清单、模型和报告放受控产物目录。

## P3 数据准备与多分类模型

任务、步骤和出口见 [P3 执行文档](p3/README.md)，概括为：

1. **P3-A 数据准备**：从 CIC-IDS2017 原始 PCAP 多视角提取特征（含网页正常流量补充），按 CNS2022 逐流关联打 5 类标签，按时间块冻结切分；L2/L3 只作测试。
2. **P3-B 训练与选型**：XGBoost/LightGBM 多分类，在 validation 上选模型与阈值，设定规则阈值，导出 ONNX 并对拍。
3. **P3-C 冻结候选**：冻结模型、阈值与策略参数，登记 P6 评估计划。

L1 test 在 P3-A 冻结后至 P6 前不读取，也不用于训练、选型或调阈值。所有拟合都计入 run 外只追加台账；本轮 P3-B 上限经负责人书面调整为 33 次，已用尽，不再新增拟合。

## P4 后端、数据库与决策

### 已完成

JDK 25 下的 v2 控制面和机器接口、机器身份与范围校验、不可变观察/推理/episode/案件事实、ONNX 运行时校验、策略和发布组合、稳定目标预算、撤销、命令领取与回执/核对台账。`V19`、`V20` 迁移已在隔离 MySQL 8 schema 验证；未迁移真实业务库，未连接真实 RabbitMQ broker。

### 待实施

1. **多分类推理**：运行时接受 `attack_score` 与 `family_scores` 两个输出，按 manifest 的 `familyScoreOrder` 解析类别；推理事实保存各类分数。现有代码只接受单一 `attack_score` 且要求 `familyScoreOrder` 为空。
2. **来源汇总决策**：按 [契约第 8 节](检测与处置契约.md#8-证据与策略判定) 在同一来源、同一类别上汇总多个连接的证据。端口扫描的汇总不按服务端口拆分。
3. **v5 规则引擎**：用 v5 观察字段实现 `host-guard-rules/1`，结果与模型证据分别记录。
4. **版本对齐**：决策版本从 `2026-10-05.x` 升到 `2026-10-06.1`、评价版本升到 `2026-10-07.1`；rc.3 结构变更与 P5 同步。
5. **部署前验证**：RabbitMQ broker 的发布确认、重试和死信流转；真实业务库迁移前核验实例、备份与恢复。

### 出口

用固定 ONNX 夹具和合成观察，验证多类输出解析、来源汇总、规则证据、告警与封禁候选、授权/预算拒绝和撤销闭环。真实模型在 P7 接入。

## P5 执行与恢复适配器

### 当前实现

已有独立 Python 执行/恢复入口、PF/WFP 适配代码、本地密钥与 IPC 身份工具、Go guardtargets 服务及命令/回执/实态对接；范围限 IPv4/TCP 入站 `peer_service`。已完成固定命令故障回归、真实 TLS/Go IPC、Java/Python 签名摘要一致性和隔离 MySQL API 验证；未安装常驻服务，未完成两平台实机故障矩阵。用户本轮要求不重启主机，重启验收暂缓。

### 待实施

1. 新增 `peer_inbound` 范围：封禁指定来源到本机全部 TCP 端口的入站连接，供 `port_scan` 使用；保护清单与预算规则同样适用。
2. 按 [动作与恢复场景](验证与验收.md#8-动作与恢复场景) 在 Mac 实机完成全部“必需”项；“补充”项能做则做，未做的在报告中列为未验证。
3. 输出真实清理时刻供 P4 预算核验；恢复器故障时暂停对应资产自动能力，并提供人工清理路径。

### 出口

Mac 上“必需”场景全部通过。Windows 未完成时保持不可自动，不影响 Mac 的 G3。

## P6 冻结离线评估

### 入口

P3 已冻结候选，P6 评估计划在读取 test 前冻结，计划包含数据集、切分、类别映射、阈值、策略参数、版本和代码哈希。

### 实施与出口

- 在 L1 test 上计算 G1、G2 与各类指标，判定 [类别自动资格](验证与验收.md#5-类别自动资格)。
- 在 L2、L3 上运行同一冻结组合，报告跨数据集与受控流量成绩。
- 在 Windows 与 Mac 核验 ONNX 实际加载与推理一致。
- test 最多评估 3 次，规则见 [验收第 7 节](验证与验收.md#7-失败处理与测试集使用)。
- 出口：G1、G2 通过，候选及各类资格登记完成。

## P7 联合闭环

### 入口

P4 待实施项完成、P5 在 Mac 上“必需”场景通过、P6 通过；登记 lab 隔离、canary 映射、期限与试验授权。

### 实施

1. 传感器以 1 倍速读取冻结 PCAP 文件，时间平移一次，经真实模型、规则、决策和执行器完成闭环；不向网卡注入攻击报文。
2. 每个攻击类至少 1 段场景，另配累计 ≥ 30 分钟正常场景。
3. 记录攻击原始起点、首次告警、命令签发、规则生效与清理时刻。

### 出口

G3 通过后，对通过的类别登记 `lab_auto`。模型或数据问题回 P3，后端问题回 P4，执行问题回 P5。

## P8 自用部署与交付

把冻结模型与配置导入 Mac 后端，核对运行程序、模型/profile/policy/bundle 哈希、真实加载与拒绝行为；采集器、执行器、恢复器和控制面按实际部署方式配置最小权限、起停、日志、健康和恢复路径。

自动启用只绑定明确授权的资产、接口、服务、期限和已通过 G3 的类别；`authorized_auto` 还需目标平台短时良性任务和独立批准。达不到时交付告警或 lab 能力，明确剩余项。完成前验证启用/停用、授权撤销、模型不可用、断连、规则清理和回退。v4 兼容路径保留到代码与历史制品依赖迁移完成后再退役。

## 4. 阶段完成记录

每阶段 run 记录输入与版本哈希、实际操作、验证结果、未支持范围、失败原因及恢复证据，保存在受控产物目录；当前状态回写本路线与对应入口文档。计划能力不得写成已部署能力。
