# 数据库设计

版本：host-guard v5 数据模型，更新于 2026-10-10。P4 当前实现由 `V19__host_guard_v5_foundation.sql`、`V20__host_guard_case_and_trial.sql`、`V21__host_guard_multiclass_sources.sql` 和 `V22__guard_capability_scope_binding.sql` 向前追加；本文仍保留 P5/P7 的目标扩展与约束。多分类与来源汇总变更见第 10 节，平台能力绑定见第 11 节。保留全部已执行 Flyway 迁移、业务数据及 admin 行/口令哈希，只从实际最新迁移向前追加。

P4 已在隔离 MySQL 8 schema 将 V1—V21 迁移、V20→V21 升级、旧账号哈希保留和 guard 约束做定向验证，共 38 张 guard 表；本机 `cyber_security` 也已在备份/恢复演练后从 V20 升级到 V21（2026-10-07），再升级到 V22（2026-10-09，见第 11 节）。V19 提供 v2 外部 ID、修订版本、guard 事实和权限映射，V20 补充案件、反馈与受控试验资格，V21 增加多类概率、来源投影与规则事实；迁移不启用真实 OS 动作。

## 1. 基本约束

MySQL 8 是业务、授权、动作和审计事实源。RabbitMQ负责至少一次通知，Redis可选且可重建。业务持久化使用MyBatis，不在控制器或领域对象直接运行SQL。

新表统一 `id BIGINT` 内部主键、`public_id CHAR(36)` 外部UUID唯一键、`created_at DATETIME(6)` UTC；可变投影增加revision与updated_at，不可变证据不提供UPDATE业务接口。哈希为CHAR(64)，范围/状态/时间/外键使用独立列，JSON只保存冻结快照与结构化扩展。

下表省略公共字段；所有引用在实现时采用内部外键并由API转换为UUID。删除策略默认为RESTRICT；退役不物理级联删除审计。需要历史快照的版本引用禁止ON DELETE CASCADE。

观察与目标引用可存在先后到达，接受观察不等于接受自动引用。由服务端将机器声明绑定实际身份、配置和环境；同一targetRef绑定变化拒绝并审计。expires_at可以凭同绑定且last_packet_at推进的新观察续证，最晚为last_packet_at+15秒，旧动作快照不变。

健康窗口最多5秒、实时接收延迟上限10秒；用机器身份、序号/前序哈希、捕获域与计数证明连续性，不相信客户端healthy或reset字段。特征引擎重置不删除健康链。健康证据不进入模型表/特征；预算恢复须从不可变健康事实及规则核对联合推导。

## 5. 对象证据与决策

| 新表 | 关键字段 | 约束 |
|---|---|---|
| guard_episode | asset_id,sensor_id,boot_id,peer_key,key_epoch,direction,transport,service_port,family,scope,source,rule_id,bundle_id,bucket_start,status | 身份、范围、来源、规则与UTC固定30秒桶联合唯一；service_port_key生成列归一化null，防止唯一键绕过 |
| guard_episode_evidence | episode_id,parent_connection_id,observation_id,inference_id,score,family,source,rule_id,rule_matched,family_scores_json,as_of | 每episode+parent+source+rule唯一贡献；更新所选快照留下追加审计，不增加独立流数；模型与规则不能混计 |
| guard_decision | episode_id,bundle_id,decision_revision,decision_contract_version,decision,reason_codes,budget_target_id,budget_revision,health_proof_sha256,evidence_sha256,evidence_ref,decided_at | unique(episode_id,decision_revision)，追加不可变；evidenceRef按guard-evidence/1绑定快照、目标和预算事实 |
| guard_event_episode | event_id,episode_id | 联合唯一；可用于人工案件合并，不能改变执行目标 |

更新episode投影时锁定其唯一行，按 `(asOf,snapshotIndex,id)` 在同asset/sensor/boot/parent中选择最新观察，跨桶的新观察也使旧投影失效；新观察尚未消费时不得领取基于旧快照的命令。降分、改类和规则未命中不能沿用旧最高分；已有动作的不可变依据不改写。旧risk_score只用于排序；自动资格取guard_decision及绑定发布包。原始peerKey不能跨asset、boot/keyEpoch混合。

运行episode的UTC桶仅用于业务索引；离线评价按[验证与验收](验证与验收.md)的连接与活动口径计算，两者不得混称；更换桶不刷新动作预算。

`desired_state`为active/revoked，`observed_state`遵循[动作状态机](检测与处置契约.md#10-动作状态与恢复)。过了block_until但没有删除证明时保持uncertain或recovery_failed，不宣称expired。已签发动作的撤销API只改变desired并发outbox，receipt或核对证明后才能更新observed；pending从未签发的动作可在同一锁行事务终止，不生成空commandId的撤销任务。

主机本地恢复账本是执行所必需的受控持久文件/SQLite，不放业务仓库。保存真实端点、所属规则、签名命令哈希、固定到期和恢复标识；权限最小化、崩溃前fsync。它不替代中央业务审计；断连期间暂存回执，重连按幂等补传。

### 6.1 稳定目标预算事实

| 新表 | 关键字段 | 不变量 |
|---|---|---|
| guard_budget_target | asset_id,environment,stable_target_token,resolver_executor_id,scope_digest,identity_status | unique(asset_id,environment,stable_target_token)；public_id为budgetTargetId，真实端点映射仅在本机；token不同于轮换peerKey |
| guard_target_binding | target_ref,budget_target_id,executor_id,executor_boot_id,sensor_id,collector_boot_id,capture_scope_id,peer_key,key_epoch,scope_digest,expires_at,content_sha256 | target_ref唯一且绑定不可改变；授权机器注册，不由模型或人工请求任意指定 |
| guard_target_budget | budget_target_id,charged_ms,last_block_end_at,last_evidence_at,health_anchor_at,revision | budget_target唯一；跨boot/capture/keyEpoch/活动/策略保留，120秒硬上限 |
| guard_budget_interval | budget_target_id,action_id,reserved_start,reserved_end,verified_end,status,proof_ref | action_id唯一；用有效/未核实预留区间并集核算累计，不按命令条数累加 |
| guard_asset_budget | asset_id,last_monotonic_at,revision | 每资产锁行保护未终结动作≤10及滚动60秒新动作≤5，所有能力共享 |
| guard_budget_event | budget_target_id,event_kind,old_revision,new_revision,before_json,after_json,proof_ref,proof_sha256,recorded_at | 预留、撤销墓碑、实态核对和reset均追加审计；无清零/健康证明不能reset |

实际规则消失只更新规则事实，不自动删除已消耗时长。恢复累计预算必须：无活动/uncertain规则，认证健康链覆盖最后规则结束至当前，且从max(last_block_end_at,last_evidence_at)起连续健康无新合格证据≥120秒。合格证据即使被预算拒绝仍更新last_evidence_at；不读取评估真值。恢复核验、revision推进和reset审计同事务提交，重复证明不能重复释放。

E3 控制面撤销墓碑复用 V19 的追加事件表，不新增或改写迁移。`event_kind=revoked` 的 `proof_json` 记录 `actionId/reasonCode/cycleStartedAt`，资产→目标锁下推进预算 revision，不修改计费；最新撤销事件的周期与当前 `guard_target_budget.cycle_started_at` 相同即拒绝新动作。未签发动作也保留墓碑。reset 只开启新周期，不删除历史事件；已计费为零的撤销仍须先通过相同健康证明。签名 keyId、策略版本和短期引用不属于预算身份。

stable_target_token由本机持久预算密钥对真实目标作用域生成HMAC；密钥/地址不入中央库。新peerKey或boot映射到原budgetTargetId；密钥轮换须保留经审计的旧新关联。无法证明连续身份时拒绝自动动作，不通过新注册获得空预算。人工恢复也要明确核对与批准，不提供任意清零快捷路径。

## 7. 事务边界与竞争

| 事务 | 原子内容 | 失败处理 |
|---|---|---|
| T1接入 | 主体/版本核验、幂等、batch/observation/rejection、outbox | 不完整则回滚，不发孤立消息 |
| T2检测 | consumed_message、inference、episode证据、decision、通知outbox | 暂态失败有限重试；过期只保存结论，不签命令 |
| T3动作创建 | 锁asset预算、binding/授权revision、稳定target预算；核验健康/范围，预留区间、action、budget_event及outbox | 任一失败全回滚；同幂等键返回原action，不重复预留 |
| T4命令领取 | 再验当前授权、签发lease、持久化不可变command、dispatched | 只有事务提交后返回签名命令；发送失败可重领原内容 |
| T5回执 | 去重receipt、合法状态投影、事件时间线、audit | 迟到回执不逆转终态；矛盾转核对 |
| T6撤销/暂停 | 授权revision或stop、desired_state/revision、revocation、outbox | 不声称OS已恢复，等待receipt/reconciliation |
| T7预算恢复 | 锁asset/target预算，核验无未终结规则、健康链、最后证据与120秒冷却；旧新revision、reset事件及审计 | 缺口/未知/重复证明拒绝；与新动作预留串行，不能二次释放 |

锁顺序统一 asset/asset_budget→binding/authorization→target_budget→episode/action，避免死锁。资产额度按数据库已创建及未确认终结动作与滚动窗口计数，目标累计按区间并集计时；两者不是同一计数。控制面时钟回退不得重开窗口。相同ruleHandle多个action不得互相删除，回执/核对与预算变更均需幂等审计。

## 8. 保留、查询与隐私

建议默认：观察payload 7天、健康30天、评估小型报告/动作/审计180天；实际保留期由部署前配置并批准，不据本文自动删除现存数据。仍被预算、规则恢复、评估或审计引用的健康证明/区间不得因短保留期删除；稳定目标账本不能按缓存TTL清空。原始PCAP不入业务库，清理前归档必要证据与哈希。

targetRef中央投影到期后不能继续作为执行依据；动作保留冻结的非明文目标摘要。peerKey资产内带keyEpoch，脱离该作用域无意义。未审查标签不能用于模型发布；反馈读取需模型/资产双范围。

## 9. 迁移步骤

1. P4先读取真实schema、Flyway历史和行数，不沿用旧环境快照。记录JDK25、MySQL8和目标实例。
2. 备份schema/data及受控恢复方式，独立测试schema验证迁移和备份恢复；不覆盖唯一可用副本。
3. 向前追加guard表/权限/外部ID映射，现有v1读写继续工作；禁止修改已执行迁移的校验和。
4. 通过新API写入隔离数据，证明v2 FK/唯一键/状态约束与JSON语义一致。
5. v5新模型、新配置、新bundle分别登记，不把旧active或旧approved迁成自动批准。
6. 获得部署范围后按资产切换；失败暂停v5绑定，v4只保留原历史能力，不能无提示代替v5自动执行。
7. 旧表、旧契约运行时和v1接口的物理删除另行审查，不在本次文档清理中执行。

所有CHECK在目标MySQL版本验证实际执行效果；应用服务仍负责跨表授权和时间约束，数据库唯一键/CHECK作第二道防线。没有真实迁移证据时只写设计完成。

## 10. 多分类路线的 V21 变更

以下变更已随 P4 代码以 V21 向前追加并在隔离 schema 验证；V19/V20 原文件不变：

| 对象 | 变更 |
|---|---|
| guard_inference | 保存 `family_scores`（按 `familyScoreOrder` 的各类分数）与模型判定类别；`family` 列沿用 |
| guard_episode | 新增 scope/source/rule_id；入站扫描的 `peer_inbound` 端口为null，其他路径按服务归并；生成列及 CHECK/唯一键限制范围与来源 |
| guard_decision / guard_episode_evidence | 不可变决策证据快照记录family/source/ruleId/scope；选中投影记录概率、规则命中和最新类别，模型与各规则分别计数 |
| guard_action / guard_budget_target | 复用现有范围字段/JSON，不额外改表；后端支持 `peer_inbound`，其目标明确入站、服务端口为null；预算身份不随episode更新 |
| guard_rule_evaluation | 新表追加 `host-guard-rules/1` 的命中、未命中与字段不适用事实及冻结规则快照 |

迁移仍遵守第 9 节：先在隔离 schema 验证，不改已执行迁移的校验和。

## 11. B1 平台能力绑定的 V22 变更

V22 只向前追加，已在集成测试的隔离 schema 执行并验证；本机业务库于 2026-10-09 获 A5 明确授权后完成备份、隔离恢复演练及 V21→V22 迁移。86 张表的数据、admin 整行/口令哈希及 V1—V21 Flyway 历史均保留；新增三列与 CHECK 已核验，失败迁移 0，迁移当时能力记录为 0。JDK 25.0.2 定向 `GuardMigrationIntegrationTest` 1 项通过、0 跳过；备份在 MySQL 服务 `backups/20261009-cyber-security-v22/`，脱敏结果在 `.cache/r8-t37-t38-20261009/a5-migration-result.json`。未激活动作或切换服务。之后经正式接口登记了 8 条能力：2026-10-09 T3.8a 的 4 条 research `peer_service`（评价用，在 lab/authorized 永不匹配自动路径），以及 2026-10-10 T3.8b 附签名平台/豁免报告的 4 条 lab_auto（port_scan 为 `peer_inbound`，其余为 `peer_service`）。lab_auto 只表示平台执行能力，不授予类别自动资格；Flyway 仍为 V22。

| 对象 | 变更 |
|---|---|
| guard_capability | 新增 `scope`（默认 `peer_service`）、`protection_set_sha256`、`exemption_evidence_sha256`；CHECK `ck_guard_capability_scope` 要求 `peer_inbound` 两个摘要都非空、`peer_service` 都为空。V22 前的能力行一律迁为 `peer_service`，不能借迁移取得全入站资格 |

`protection_set_sha256` 为全入站豁免依据的保护文件 JCS 摘要，签发时还须等于策略 `protectionSetSha256` 与当前保护文件；`exemption_evidence_sha256` 为登记时已验签的 E1—E3 豁免报告摘要。数据库只保证字段成对出现，五条件放行由 `GuardEligibility` 判定。

### 2026-10-07 本机迁移核验

- 实例为本机 MySQL 8.0.42。迁移前业务库已有 V1 baseline、V2—V20 成功历史及 85 张表；本次没有创建 baseline，也没有运行 repair。
- 业务库与旧 V19 冲突测试库均先备份。业务备份在独立 schema 恢复，逐表行数/数据摘要、账号哈希、完整历史及结构核对一致；V20 结构与当前源码新建参考库一致。
- 恢复库先演练、业务库后追加 V21；迁移后 86 张表（含 Flyway 历史表）、38 张 guard 表，全部 CHECK TABLE 通过，186 个外键无孤儿记录。13 个账号（含唯一 admin）及口令哈希、所有旧表行数和旧历史完整保留；结构与 V21 参考库一致。
- V21 改动的三张既有 guard 表在本机迁移前均为空；有历史 guard 数据时仍须针对该实例重新演练，不能套用本机结论。
- 历史固定测试库执行过另一分支的 `V19__offline_training_jobs.sql`，与当前 guard V19 语义不同，保留原库及历史。测试按类创建随机库，结束时先关闭应用上下文，再只删除自身成功创建的库，避免再次复用旧分支。
- 升级前后备份及核验证据保存在本机 MySQL 服务的私有 backups 目录，未提交 Git。恢复应先导入独立新库并核验，再单独批准服务切换，不向现有业务库直接覆盖导入。应用服务尚未切换或重启。
