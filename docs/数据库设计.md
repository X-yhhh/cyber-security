# 数据库设计

版本：host-guard v5 目标逻辑模型。本文件不包含可执行迁移，本次不改数据库。现有 Flyway V1—V18、业务数据及既存 admin 账号/哈希完整保留；后续只从实际最新迁移版本向前追加。

## 1. 基本约束

MySQL 8 是业务、授权、动作和审计事实源。RabbitMQ负责至少一次通知，Redis可选且可重建。业务持久化使用MyBatis，不在控制器或领域对象直接运行SQL。

新表统一 `id BIGINT` 内部主键、`public_id CHAR(36)` 外部UUID唯一键、`created_at DATETIME(6)` UTC；可变投影增加revision与updated_at，不可变证据不提供UPDATE业务接口。哈希为CHAR(64)，范围/状态/时间/外键使用独立列，JSON只保存冻结快照与结构化扩展。

下表省略公共字段；所有引用在实现时采用内部外键并由API转换为UUID。删除策略默认为RESTRICT；退役不物理级联删除审计。需要历史快照的版本引用禁止ON DELETE CASCADE。

| 现有对象 | v5处理 |
|---|---|

| asset / asset_authorization | 复用；补external UUID、authorization revision、捕获/执行scope分离和有效期 |
| sensor_agent / sensor_config / api_client及scope | 复用；补v5配置/捕获域引用，机器type增加executor，禁止sensor与executor混用 |
| audit_log / audit_resource_scope | 复用；新对象资源范围必须进入关联表，查询SQL先过滤再分页 |
| outbox_event / consumed_message | 复用实际表结构，新增guard事件类型；幂等事实不能只存Redis |
| security_event / event_timeline / feedback_sample | 复用研判语义；通过新episode链接，不以原asset关联键驱动自动动作 |
| model_version / model_deployment / response_policy / action_execution | 旧v4台账保持只读历史；v5新命名对象独立落库，迁移期不混用状态和manifest |

具体旧列/索引以P4迁移前的数据库和DDL审计为准，不能仅凭旧设计表名执行迁移。新增UUID后分批回填并核对唯一性；不在业务升级中重建现存库。

candidate bundle的模型/策略/profile/extractor哈希及拟评估能力存不可变subject_json/subject_sha256。先创建candidate，再运行引用它的evaluation；报告引用subject_sha256。通过后单独生成sealed_manifest_ref/sha256，将subject和验收报告哈希一起封存，才可批准；不把报告哈希反向写入subject导致循环。补充报告生成新封存版本，不篡改已批准发布材料。开发评估可由离线runner先生成同格式subject和报告，P4统一登记。

## 4. 采集、目标与推理

| 新表 | 关键字段 | 约束/索引 |
|---|---|---|
| guard_capture_scope | asset_id,sensor_id,scope_key,interface_ref,address_family,config_id,status | unique(sensor_id,scope_key)，本地接口白名单；不保存接口秘密 |
| guard_observation_batch | sensor_id,boot_id,batch_id,sequence,config_id,request_sha256,status,accepted_count,rejected_count | unique(sensor_id,boot_id,sequence)及batch_id；同键内容不可变 |
| guard_observation | batch_id,sensor_id,asset_id,boot_id,capture_scope_id,flow_id,parent_connection_id,snapshot_index,profile,as_of,last_packet_at,close_reason,received_at,peer_key,key_epoch,direction,transport,service_port,environment,contract_id,payload_json,content_sha256,quality_status | unique(sensor_id,boot_id,flow_id,snapshot_index)，索引(asset_id,as_of)、(peer_key,as_of)均带sensor/epoch限定 |
| guard_ingest_rejection | batch_id,observation_external_id,reason_code,field_names,content_sha256 | 保存拒绝事实，不回显原始请求秘密 |
| guard_target_ref | target_ref,sensor_id,asset_id,boot_id,capture_scope_id,peer_key,key_epoch,direction,transport,service_port,address_family,expires_at,status | target_ref唯一；仅短期中央元数据，无原始地址；research不能登记真实目标 |
| guard_inference | observation_id,model_id,status,score,family,applicability,manifest_sha256,started_at,completed_at,error_code | unique(observation_id,model_id)；只有succeeded+supported才有score |

观察与目标引用可存在先后到达，接受观察不等于接受自动引用。由服务端将机器声明绑定实际身份、配置和环境；同一targetRef绑定变化拒绝并审计。expires_at可以凭同绑定且last_packet_at推进的新观察续证，最晚为last_packet_at+15秒，旧动作快照不变。

## 5. 对象证据与决策

| 新表 | 关键字段 | 约束 |
|---|---|---|
| guard_episode | asset_id,sensor_id,boot_id,peer_key,key_epoch,direction,transport,service_port,family,bundle_id,bucket_start,status | 上述字段联合唯一，bucket_start为UTC固定30秒桶 |
| guard_episode_evidence | episode_id,parent_connection_id,observation_id,inference_id,score,as_of | 每episode+parentConnection唯一贡献；更新所选快照留下追加审计，不增加独立流数 |
| guard_decision | episode_id,bundle_id,decision_revision,decision,reason_codes,evidence_sha256,evidence_ref,decided_at | unique(episode_id,decision_revision)，追加不可变；evidenceRef绑定被选快照 |
| guard_event_episode | event_id,episode_id | 联合唯一；可用于人工案件合并，不能改变执行目标 |

更新episode投影时锁定其唯一行，按asOf处理已有证据，不对已发出动作追溯改依据。旧risk_score只用于排序；自动资格取guard_decision及绑定发布包。原始peerKey不能跨asset、boot/keyEpoch混合。

## 6. 执行与租约

| 新表 | 关键字段 | 约束/说明 |
|---|---|---|
| guard_executor | asset_id,api_client_id,platform,adapter_version,capability_hash,boot_id,status,last_heartbeat | 机器client_type=executor，单独身份 |
| guard_action | decision_id,asset_id,executor_id,target_ref,bundle_id,authorization_id,authorization_revision,mode,desired_state,desired_revision,observed_state,idempotency_key,target_snapshot,block_until,created_by,approved_by | mode=auto/manual；target快照无原始IP；幂等键唯一；manual需独立批准 |
| guard_command | action_id,command_id,executor_boot_id,payload_json,payload_sha256,key_id,signature,issued_at,apply_by,lease_expires_at,status | command_id唯一；同action初次应用一条命令，重领不改时间 |
| guard_authorization_lease | command_id,authorization_id,revision,issued_at,expires_at,status | command唯一，期限不超过授权有效期；可撤销但网络断开有传播窗口 |
| guard_action_receipt | receipt_id,command_id,revocation_id,executor_id,status,observed_at,received_at,rule_handle,effective_block_until,error_code,state_digest,content_sha256 | receipt_id唯一，追加；相同ID不同内容拒绝 |
| guard_revocation | action_id,command_id,executor_id,desired_revision,payload_json,content_sha256,status | public_id为revocationId，unique(action_id,desired_revision)；领取后保持pending，清理回执才confirmed |
| guard_reconciliation | executor_id,boot_id,observed_at,owned_state_sha256,report_ref,error_count | 代理实态核对，不用控制面旧状态强盖OS |
| guard_automation_stop | asset_id,bundle_id,scope_json,reason,requested_by,requested_at,revoke_existing,status | 新命令即时拒绝；清理结果异步确认 |

`desired_state`为active/revoked，`observed_state`遵循[动作状态机](检测与处置契约.md#10-动作状态与恢复)。过了block_until但没有删除证明时保持uncertain或recovery_failed，不宣称expired。已签发动作的撤销API只改变desired并发outbox，receipt或核对证明后才能更新observed；pending从未签发的动作可在同一锁行事务终止，不生成空commandId的撤销任务。

主机本地恢复账本是执行所必需的受控持久文件/SQLite，不放业务仓库。保存真实端点、所属规则、签名命令哈希、固定到期和恢复标识；权限最小化、崩溃前fsync。它不替代中央业务审计；断连期间暂存回执，重连按幂等补传。

## 7. 事务边界与竞争

| 事务 | 原子内容 | 失败处理 |
|---|---|---|
| T1接入 | 主体/版本核验、幂等、batch/observation/rejection、outbox | 不完整则回滚，不发孤立消息 |
| T2检测 | consumed_message、inference、episode证据、decision、通知outbox | 暂态失败有限重试；过期只保存结论，不签命令 |
| T3动作创建 | 锁asset binding/授权revision/动作预算、action、outbox | 权限/时效冲突拒绝；同幂等键返回原action |
| T4命令领取 | 再验当前授权、签发lease、持久化不可变command、dispatched | 只有事务提交后返回签名命令；发送失败可重领原内容 |
| T5回执 | 去重receipt、合法状态投影、事件时间线、audit | 迟到回执不逆转终态；矛盾转核对 |
| T6撤销/暂停 | 授权revision或stop、desired_state/revision、revocation、outbox | 不声称OS已恢复，等待receipt/reconciliation |

锁顺序统一 asset→binding/authorization→episode/action，避免死锁。所有预算按数据库已创建及未确认终结动作计算，不能按消息次数计算。相同ruleHandle多个action不得互相删除；续封归属和累计时长在P5实现前明确验证。

## 8. 保留、查询与隐私

建议默认：观察payload 7天、健康30天、评估小型报告/动作/审计180天；实际保留期由部署前配置并批准，不据本文自动删除现存数据。原始PCAP不入业务库。审计和评估结果清理前归档哈希清单及必要法定/项目保留记录。

targetRef中央投影到期后不能继续作为执行依据；动作保留冻结的非明文目标摘要。peerKey资产内带keyEpoch，脱离该作用域无意义。未审查标签不能用于模型发布；反馈读取需模型/资产双范围。

## 9. 迁移步骤

1. P4先读取真实schema、Flyway历史和行数，不沿用旧环境快照。记录JDK25、MySQL8和目标实例。
2. 备份schema/data及受控恢复方式，独立测试schema验证迁移和备份恢复；不覆盖唯一可用副本。
3. 向前追加guard表/权限/外部ID映射，现有v1读写继续工作；禁止修改V1—V18校验和。
4. 通过新API写入隔离数据，证明v2 FK/唯一键/状态约束与JSON语义一致。
5. v5新模型、新配置、新bundle分别登记，不把旧active或旧approved迁成自动批准。
6. 获得部署范围后按资产切换；失败暂停v5绑定，v4只保留原历史能力，不能无提示代替v5自动执行。
7. 旧表、旧契约运行时和v1接口的物理删除另行审查，不在本次文档清理中执行。

所有CHECK在目标MySQL版本验证实际执行效果；应用服务仍负责跨表授权和时间约束，数据库唯一键/CHECK作第二道防线。没有真实迁移证据时只写设计完成。
