## 3. deploy 配置清单

`application-deploy.yml` 导入 `file:${DEPLOY_CONFIG_FILE}`。入口只需在进程环境设置 `SPRING_PROFILES_ACTIVE=deploy` 和 `DEPLOY_CONFIG_FILE` 的绝对路径；其余 `DEPLOY_*` 可放在该受控 `.properties` 文件中。不得同时激活 local/lab 等其他 profile，不在命令行传秘密。

| 配置 | 含义 |
|---|---|
| `DEPLOY_DB_URL/USERNAME/PASSWORD` | 本机 MySQL JDBC URL（不内嵌凭据）及受控账号；正式运行账号按最小权限准备 |
| `DEPLOY_LOGIN_THROTTLE_HMAC_KEY` | 至少 32 字符的私有 HMAC 材料；沿用受控秘密管理 |
| `DEPLOY_WEB_ROOT` | 前端 dist 绝对目录，目录 0700、文件不向组/其他用户开放，包含 index.html；只在 deploy profile 托管 SPA，API/运维路径不回退，首页 no-store、带哈希资源长缓存 |
| `DEPLOY_TLS_CLIENT_CA` | 已批准的机器客户端 CA PEM，0600；监听器 client-auth=want，机器路径额外强制已验证客户端证书；与 enrollment 生成的 machine-tls.properties 对齐 |
| `DEPLOY_TLS_CERTIFICATE/KEY` | PEM 证书与私钥路径，证书 SAN 覆盖实际入口；TLS 1.3、secure cookie |
| `DEPLOY_SIGNING_KEY_ID/FILE` | 已审查的 Ed25519 身份和 DER 私钥路径；配置存在不授予动作资格 |
| `DEPLOY_REPORT_TRUST_FILE` | 正式评价报告信任公钥文件 |
| `DEPLOY_PROTECTION_FILE` | `protectedBudgetTargetIds`、`protectedServicePorts` 的 JSON |
| `DEPLOY_ARTIFACT_ROOT/LEDGER_ROOT` | 制品根与受控账本根；后者用于启动权限检查，不替代执行器自身的账本配置 |
| `DEPLOY_QUEUE_PREFIX` | v5 guard 独占队列前缀 |
| `DEPLOY_INGEST_QUEUE/INGEST_DEAD_LETTER_QUEUE/INGEST_RETRY_QUEUE_PREFIX` | v1 ingest 独占队列名称；不得与其他实例共享消费队列 |
| `DEPLOY_RABBITMQ_VHOST/USERNAME/PASSWORD` | 专属 vhost 和受控凭据；禁止默认 `/` vhost |
| `DEPLOY_RABBITMQ_EXCHANGE/RABBITMQ_DEAD_LETTER_EXCHANGE` | 专属 topic / dead-letter exchange |
| `DEPLOY_OUTBOX_RELAY_ENABLED/CONSUMER_ENABLED` | 初次启动 false；受控切换检查完成后显式设 true 并重启本次服务 |
| `DEPLOY_SERVER_PORT` | 预定回环监听端口，默认 18080；先核对占用，不能抢占预览实例 |
| `DEPLOY_RABBITMQ_HOST/PORT/CONFIRM_TIMEOUT_MS` | 默认 `127.0.0.1` / 5672 / 5000；启动自检要求回环 host |

**现有 v4 记录的兼容启动**：当前业务库仍含历史 active model_deployment。外部配置文件还须明确设置 `cyber.model-artifact.root` 为已有、校验通过的模型交付根（当前受控 `Workspace/deliveries`），否则旧运行时恢复会以 `MODEL_ARTIFACT_ROOT_NOT_CONFIGURED` 拒绝就绪。这只是恢复既有内存模型引用，不启用 v4 消费、不改历史记录，也不让 v4 接管 v5。DB-9 的临时后端已显式注入该属性。

自动化、bootstrap 报告和 local admin 引导均关闭。命令行或外部配置覆盖自动化为 true、缺变量、属主/权限错误会在数据源、Flyway、业务监听器装配前失败。启动审计记录 `guard.deploy.startup`，资源标识为外部配置 SHA-256，详情仅含公开配置摘要；审计失败不就绪。

## 4. 业务库备份和恢复演练

### 4.1 每次切换前

1. 确认准确主机、schema=`cyber_security`、MySQL 8、现有 admin/用户、当前 Flyway 版本（2026-10-16 已 V27）和对应发布组合；记录进程/监听，不把预览 schema 当成业务库。
2. 暂停本次服务的写入入口、relay、consumer 和采集上传，处理已接收但未完成的任务；确认无本次或其他客户端连接业务库。不能证明停写时暂停切换。
3. 在仓库根运行：

   ```sh
   sh executor/python.sh -B scripts/p8/backup_restore.py
   ```

4. 脚本从 Keychain 读取本机 DB 凭据，不回显；`mysqldump --single-transaction --routines --triggers --events --hex-blob --set-gtid-purged=OFF --no-tablespaces` 保存完整库。
5. 恢复到本次随机 schema，比较所有表的有效结构、行数及按主键对应的逐行 SHA；dump 前后业务库也须一致。DOUBLE/FLOAT 按 IEEE 位检查。MySQL 8.0.42 的 JSON 文本解析可能改变浮点末位：脚本同时生成 `json-double-fidelity.sql`，在恢复库以 SQL DOUBLE + JSON_SET 还原原精度；源库不改，逐行校验不放宽。结构摘要仅归一化冗余字符集声明和 AUTO_INCREMENT 下一个序号。
6. 全部通过后只删除该随机库，保留 `database.sql`、`json-double-fidelity.sql`、`source-before.json`、`restored.json`、`restore-proof.json` 和 `result.json`。要求 `passed=true`、`temporarySchemaDeleted=true`；用 `shasum -a 256` 分别核对两份 SQL 与恢复证明中的哈希。失败不得进入业务切换。

DB-9 的 `register_alert_only.py` 内置相同备份/恢复流程，另要求业务开始状态、输入和最终表增量与演练相同。已 approved 的 r6 不重复登记。命令见 [脚本说明](../scripts/p8/README.md)。

### 4.2 实际恢复（另一次有目标的操作）

1. 先停写并停止准确服务，保存失败现场的独立备份和日志；选定已验证 dump、源 schema、时间点和恢复目的。明确恢复会丢失该时间点之后的业务状态；获得对应恢复授权后才执行。
2. 先再次恢复到新随机库验证，再决定覆盖原库或切换到恢复库；当前工具只提供随机库演练，不提供一键覆盖业务库。不得把 DROP/TRUNCATE 直接用于业务库试错。
3. 恢复时密码通过受控环境或文件供 mysql 客户端使用，不使用 `-p明文`。先导入 `database.sql`，再向同一目标库导入已校验的 `json-double-fidelity.sql`；缺失补充 SQL 时该备份不满足精确恢复要求。恢复完成后核对所有表、Flyway 校验和、admin 哈希、审批链、组合/能力/报告引用、幂等记录、待处理消息和动作恢复事实。
4. MySQL 与 RabbitMQ 无跨系统原子快照。恢复后旧消息按幂等键重新校验；暂停来源不明或与恢复点冲突的消息，保留死信与审计。禁止通过清空共享队列“修好”状态。
5. 若存在尚未撤销的执行器规则，先按原授权恢复器流程核验账本、TTL 和清理事实，再开放入口；默认关闭自动化不能替代规则恢复证明。本轮 r6 不产生命令，此项不构成本次 PF 操作授权。

## 5. 启动和切换顺序（待 P8 实际执行）

B3 生成顺序为 backend → targets → recovery → executor → sensor。r6 采用 `--mode alert-only`，执行/恢复入口为普通用户的零能力观察进程。PF lab 用 `--mode pf`，仅生成需 root 的两个 LaunchDaemon，管理员独立安装。sensor 不自动启动/重启，批准窗口内显式启动，每次新 boot/spool；安装器先等后端 TLS 就绪。卸载按相反顺序，PF 必先清理并核验，清理失败保留恢复器/账本；不自动 sudo。

1. 确认 A8 的目标主机、接口、账号、服务标签、目录、端口、窗口和恢复责任人；真实采集需要独立明确授权。先保留旧程序和配置。
2. 检查 MySQL 进程、127.0.0.1:3306 监听、连接和备份；检查 RabbitMQ 节点、专属 vhost、权限及队列声明。按 BE-14c 的两组证据核对确认、超时、重试、死信、幂等和独立节点恢复。
3. relay/consumer 均关闭，以 JDK 25 的绝对路径启动 deploy JAR；验证实际 PID、程序/JAR 哈希、监听仅回环、证书、TLS 1.3、`/actuator/health` 为 UP，以及启动审计中的配置 SHA。不得仅凭启动日志宣称部署成功。
4. 按 P8 授权登记真实资产和有效授权，激活 approved r6；复核 subject、policy、模型、profile、extractor、协议、报告与封存哈希。此步不得使用 r5 代替 r6。
5. 显式开启本实例 relay/consumer 并重启，确认 outbox 可发布、确认超时会保留重试状态、消费幂等、死信可见；随后在明确接口上启用已授权的传感器，核对健康 1.0.0 和同源特征契约。
6. 现场验证输入产生 alert，action/command 为 0，人工动作请求拒绝且执行器能力摘要为空；故障、模型不可用、协议错误或断连必须显式报错/暂停，无静默回退模型。
7. 执行器/恢复器若为其他已授权 lab 工作常驻，先核对其独立授权和恢复能力，不能因为 r6 部署而自动接入真机动作。整机重启与恢复验证仅在 A8 窗口执行。

## 6. 回退与停止条件

启动自检失败、健康非 UP、哈希不符、消息去重失效、未知授权/目标、出现意外 action/command 或无法证明数据恢复一致时，立即暂停本次接入和切换，保存请求关联号与脱敏证据。

1. 停止本次采集上传和业务入口，关闭 relay/consumer；只停止运行记录绑定的 PID/服务标签，不按进程名批量 kill。
2. 若只需程序回退，恢复上一已验证 JAR 与受控配置；保持自动化 false、上传暂停。迁移只能向前追加，不能篡改已执行 Flyway；数据库版本不兼容时停在人工核验，不强行启动旧程序。
3. 切回默认 profile 时移除 `SPRING_PROFILES_ACTIVE=deploy`，明确注入默认 profile 的 DB/TLS/guard 引用，显式 `OUTBOX_RELAY_ENABLED=false`、`INGEST_CONSUMER_ENABLED=false`、`CYBER_DRIFT_ENABLED=false`、`cyber.guard.automation-enabled=false`。默认 profile 是暂停运行入口，不代表 v4 可以接管 v5。
4. v4 不读取/接管 v5 资产绑定、发布资格或动作账本；恢复器仍使用原协议和账本恢复已有规则。不能证明安全恢复时持续暂停并人工处理。
5. r6 登记停在 approved 时无需通过删除策略/组合“回滚”；保留审批和报告事实。撤销、退役或恢复数据库需对应范围授权，审计追加保留。
6. 回退后重新验证 PID、端口、health、配置/JAR 哈希、数据库行与待处理消息，确认无意外动作；结果写入系统实施记录，未完成项逐项标明。

**采集权限前置**：`guardlive` 目前没有可直接承诺的常驻提权/降权启动链，旧 `privdrop.FromSudo` 也不能直接当成 root LaunchDaemon 方案。P8 须先验证非 root 用户对必要 BPF 设备的最小访问方式及撤销路径；授权中须列明涉及的系统权限变化。不能证明最小权限就停止在未采集状态，不以 root 常驻整个传感器绕过。每次进程使用新 bootId 与独立 spool；重启不会延长授权，过期后拒绝打开接口。现有单次采集上限 30 分钟，拟申请一次 30 分钟现场观察；长期监督与更长观察需后续明确范围。

### 8.2 申请范围与重启预算

- **目标**：本机 Mac 的一项新登记 `authorized` 资产；只激活 r6 `aa35ae6e-3b41-461d-8b54-cb4bb4726349`（approved、revision 3、alert_only）。登记前再次核对完整 subject、策略、模型与制品；现场 action/command 必须始终为 0。
- **范围待确认**：候选物理接口 `en0`（仅依据当前默认路由），地址族及本机地址须执行前逐项确认，不包含其他接口、Tailscale/虚拟网络或全 LAN。拟采用 `all_inbound_tcp`，仅处理传感器实际可见的授权本机入站 TCP。授权有效期、执行日期、30 分钟观察起止及恢复责任人须由用户明确；未填齐则不采集。
- **拟数据库动作**：切换前备份/恢复演练；登记所需真实资产、授权、传感器身份/配置、r6 资产绑定与激活，追加审计。保留既有账号哈希、r3—r5 和 Flyway V25；本申请不包含权限重建迁移。整库恢复不作为默认动作，仍按 4.2 节另获准确目标授权。
- **整机重启：1 次计划额度**，用于 D2 验收。任何第二次重启须说明原因并重新确认。执行前保存本机工作、核查现有服务和远程连接；此次重启会中断共享 MySQL、RabbitMQ、预览后端及其他本机进程，不能只视为新服务影响。
- **服务起停**：后端初次启动 1 次；完成受控核验后开启 relay/consumer 计划重启后端 1 次；整机重启再恢复 1 次。失败时允许先停用，再按已批准范围回退启动旧制品 1 次；超出这些次数、需要改动共享服务或扩大权限时停止并补充确认。传感器按批准的观察窗口启动 1 次，到期停止；重启后默认保持未采集，用户确认的新窗口才可再启。
- **硬性验证**：PID/程序身份、回环监听、TLS、health、配置与制品哈希、数据库状态、outbox/消费幂等、只告警拒绝动作、启动/停止审计及重启后状态均须留证。传感器故障、授权失效或未知计数不得伪装为 healthy。30 分钟中的告警率/质量比例只作样本报告，不推导现场准确率。

### 8.3 可执行的回退顺序

1. 切换前保存原运行程序、受控配置、服务定义和每份 SHA；制作新的整库备份并完成随机库逐表恢复核对。首次安装无上一部署版本时，把“移除本次服务入口、恢复安装前状态”作为回退基线，不能称旧预览 JAR 为已验证部署版本。
2. 异常时先停止本次采集监督入口与上传，关闭本次 relay/consumer 和外部写入口，按执行记录中的准确标签卸载本次用户域任务。保存 spool、账本、审计、日志和失败现场；不删除共享 vhost、队列或业务数据。
3. 如只是程序/配置问题且数据库仍兼容，恢复留存版本及匹配配置，保持自动化关闭与采集暂停，再验证 PID、端口、TLS/health、数据库引用与消息状态；首次安装则保持新服务停用，现有预览配置原样保留。
4. 真实资产授权撤销或 r6 停用按已有受控 API 追加审计；不直接删除策略、组合或审批行。若需要整库恢复，保存故障点新备份，按 4.2 节申请并验证后执行；不反向改 Flyway、不清共享消息来消除冲突。
5. 本次不配置真机动作服务，因此不以试运行 PF 作为回退步骤。如发现历史未清规则，只记录并中止切换，依原 lab 授权/恢复流程处理，不能扩大本申请权限。
6. 回退完成后记录恢复的版本、服务状态、未完成项与重新申请条件。程序回退原则上无需再次整机重启；不能证明安全时保持停用，第二次重启另行确认。

**批准入口**：用户需确认上述目标/服务清单、精确采集范围与期限、1 次整机重启窗口，以及允许的系统采集权限变更。批准后才进入 P8；本次仅完成申请材料和准备代码合入。
