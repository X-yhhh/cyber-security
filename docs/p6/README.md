## 2. 结果

### 2.1 慢速类：检出依赖并发与对端数量

validation 中有 434 条 dos_slow 连接、3,167 个快照。

| 变体 | 连接检出率 | 攻击分数中位数 |
|---|---:|---:|
| 原样 | 94.47% | 0.999998 |
| 压到 L3 形态（同源 ≤4 条流，主机只有 1 个对端） | **0%** | 0.000102 |
| 同源 ≤20 条流，主机只有 1 个对端 | 0% | 0.094964 |
| 只压对端维度（≤4 条流，字节按比例缩小） | 15.90% | 0.006559 |
| 只把主机侧改为 1 个对端（`hostDistinctPeers=1`，`hostFlowStarts=peerFlowStarts`） | **0%** | 0.753156 |

validation 中 dos_slow 的 30 秒同源新建连接数中位为 71（第 5 百分位为 5），30 秒同源 SYN 数中位为 168，主机侧对端数中位为 4。

该模型 validation 攻击检出率 98.02%、macro-F1 0.9906（candidate-v2 为 98.60%、0.9931）。它只是研究制品，不是冻结候选：类别输入仍为 float32，不符合契约的 int64；run 中没有原生模型和 train 框架概率，无法直接完成冻结对拍。

### 2.4 L3 的采集形态

据 [受控采集授权](../p3/controlled-attack-authorization.json)，L3 的慢速攻击为：回环接口、只有一个对端（`127.0.0.2`）、每组最多 4 条并发连接、每组 65–95 秒、发送间隔 5–11 秒。冻结的慢速规则要求 30 秒内同源新建连接 ≥21 条，在这种形态下按设计不可能触发。

## 3. 结论

1. **L3 0/29 的原因有两层。** 一层是模型：它对慢速类的判断依赖“同源高并发”和“主机同时有多个对端”，并不依赖“慢”本身。另一层是 L3：它只有单对端、≤4 条并发，规则不可触发，这个形态也不代表真实的慢速 DoS。所以 L3 结果不能简单写成“模型实测检不出慢速攻击”，也不能用 L1 的 99.5% 抵消。
2. **dos_slow 的能力表述。** 当前候选的能力只能写成“在多对端主机环境中，识别同源高并发的 HTTP 连接占用”。它不覆盖低并发慢连接，单对端主机上的能力也未证明。
3. **主机上下文捷径影响 G3。** CIC2017 的受害服务器同时能看到多个背景对端，模型学到了这种环境特征。Mac lab 通常只有攻击来源一个对端，当前候选进入 G3 时，预计洪泛和慢速检不出、暴力破解约一半检不出，四类告警这一要求无法满足。**G3 场景不得为迁就模型而人为加入背景对端。** P3-B 的“去掉主机上下文”消融是另训的模型，影响小只说明换了特征仍能在 CIC 上分类，不能反驳本诊断。
4. **阈值放大了捷径效应。** 主机只有一个对端时，dos_slow 分数中位数仍有 0.75，但全局阈值高达 0.99992，所以全部落在阈值以下。单独降低阈值会改变已冻结的误报表现，属于新的发布组合，不能作为修复手段直接套用。
5. **L2 的定位。** 本诊断已经解释了 L3 的矛盾，L2 不再是唯一的解释手段。L2 仍是跨数据集泛化的参考，建议只对修复后的候选评估一次。
6. **rc.3 断层的更正。** 按当前 Schema 校验，候选 manifest 只有 `contractVersion` 1 处不符；对历史修订 `efcbd12` 的 Schema 则为 0 处。候选里的 `decision-policy.json` 是 P3 的研究格式，对 `efcbd12` 历史 Schema 有 20 处不符，对当前 rc.3 有 21 处不符；P6 只校验了 manifest。因此 P7 前要做的不是“迁移旧策略”，而是生成一份合规的契约策略：类别阈值等冻结值原样带入，保护集、TTL、预算等部署侧字段只能取自 P4 现行配置，不能从候选推断，取不到时拒绝生成（fail-closed）。
7. **局限。** 反事实只改了特征字段，衡量的是模型的敏感性，不是真实流量下的表现。port_scan 的稳健同样只是敏感性结论。

|---|---|---|

| M2 | G3 自动封禁部分：具备离线资格的类别完成真实封禁与恢复 | M1、P5 Mac 必需场景通过 |

M1 与 M2 紧接执行，不推迟到项目整体完工后。拆分只是执行顺序，G3 的定义与标准不变。
