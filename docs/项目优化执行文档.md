## O1. 本机 admin 初始密码哈希不一致

### 现状
README 记录：`database/init.sql` 中 `admin` 的 BCrypt 哈希未通过 `admin` 密码校验；启动过程不会重置既存哈希，因此本机账号可能无法登录。

### 目标
新建库时 `admin/admin` 可登录；既存库哈希不被自动覆盖；该凭据仅限本机。

### 执行步骤
1. 写一个仅在测试中运行的校验：用 Spring Security `BCryptPasswordEncoder.matches("admin", <init.sql 中的哈希>)`，先确认当前为 false，作为回归基线。
2. 使用与后端一致的 cost（查 `SecurityConfig` 中 encoder 配置，若未指定为 10）在本机离线生成新哈希，替换 `init.sql` 中的值。不要在日志或提交说明中输出明文以外的派生信息。
3. 将步骤 1 的测试改为断言 true，放入 `backend/src/test/java/.../database/`，读取 `database/init.sql` 文本解析哈希，防止未来被误改。
4. 既存本机库：提供独立说明（README 小节），由用户在确认本机后手工执行 `UPDATE sys_user SET password_hash=? WHERE username='admin'`；不写入 Flyway 迁移，避免覆盖他人环境。
5. 增加启动检查：当 `spring.profiles.active` 非 `local` 且存在 `admin` 账号使用初始哈希时，输出 WARN（不输出哈希），可选拒绝启动。

### 验收
- 新测试通过；空库执行 `init.sql` + Flyway 后浏览器登录成功。
- 既存库未被启动流程修改（对比 `updated_at`）。
- `git diff` 中无明文密码以外的敏感值。

## O4. 响应模块负向测试补齐

### 现状
`ResponseService`（约 660 行）实现申请、审批、查询与执行拒绝。CLAUDE.md 第 7 节要求覆盖：越权、过期授权、未知目标、策略冲突、重复请求、执行超时、适配器故障、审批分离、撤销/回滚、完整审计。当前执行器尚未实现，但前六类中与申请/审批相关的场景现在就可以测。

### 测试矩阵（集成测试，连独立 MySQL 测试 schema）
| 用例 | 期望 |
| --- | --- |
| 用户无目标资产范围权限提交申请 | 403，无 `approval_task` 写入，有审计 |
| 资产授权 `expires_at` 已过 | 拒绝，错误码稳定 |
| 资产授权 scope 不含该 actionType | 拒绝 |
| assetId 不存在 / 不属于该事件 | 404/422，不泄露资产是否存在于其他范围 |
| policy 状态非 approved、版本不匹配、参数超出 `max_duration_seconds` 或 `risk_limit` | 拒绝 |
| 同 Idempotency-Key 相同载荷重放 | 返回原结果，不新增行 |
| 同 Idempotency-Key 不同载荷 | 409 |
| 申请人自己审批 | 拒绝（审批分离） |
| 已决审批再次决策 | 409，状态不变 |
| 并发两次审批同一任务 | 只有一次成功（验证 `FOR UPDATE` 行锁） |
| 审批期间授权被撤销再批准 | 拒绝批准 |
| 事件已关闭后申请 | 拒绝 |
| 调用执行端点 | 503 `ACTION_EXECUTION_UNAVAILABLE`，`action_execution` 无新增，审计有记录 |
| 每个拒绝路径 | 审计记录包含 request/correlation ID，且不含敏感参数 |

### 执行步骤
1. 在 `backend/src/test/java/.../response/` 建测试夹具构建器（事件、资产、授权、策略、用户角色），避免每个用例手写 SQL。
2. 并发用例用 `CountDownLatch` + 两个线程，各自独立事务。
3. 用 `mvn -Dtest=Response*` 运行，确认使用 JDK 25（`mvn -v` 输出核对）。

### 验收
矩阵全部实现并通过；为 O5 重构提供安全网。

## O5. ResponseService 职责拆分

### 现状
单类混合：幂等处理、策略匹配、授权校验、资产范围权限、事件状态校验、快照生成、审批决策、查询分页、执行拒绝；直接使用 `JdbcTemplate`，与项目 MyBatis 基线不一致。

### 目标结构（包 `response`）
```
response/
  api/ResponseController.java           协议适配
  application/ActionRequestService      申请编排（事务边界）
  application/ApprovalDecisionService   审批决策（事务边界）
  application/ResponseQueryService      只读查询
  domain/PolicyGuard                    策略匹配（纯函数，可单测）
  domain/AuthorizationGuard             资产授权有效性与 scope
  domain/ActionSnapshotFactory          请求快照
  domain/ApprovalStateMachine           pending→approved/rejected/expired 合法迁移
  infra/ResponseMapper(.xml)            MyBatis 替代 JdbcTemplate
  infra/IdempotencyStore
```

### 执行步骤
1. 前置：O4 全部通过。
2. 先抽纯函数：`policyMatches`、`authorizationScopeAllows`、`actionSnapshot` 移入 domain 类，补单元测试。
3. 引入 `ApprovalStateMachine`，所有状态更新走 `UPDATE ... WHERE id=? AND status=?` 并检查影响行数。
4. 将 SQL 逐个迁移到 MyBatis mapper，保持 SQL 文本一致（含 `FOR UPDATE`）。
5. 拆分应用服务，控制器改为注入三个服务。
6. 每步运行 O4 测试；最后删除旧类。
7. 为执行器预留接口 `ActionExecutor`（仅接口与中文 Javadoc，不实现），避免后续再改结构。

### 验收
O4 全部通过；行为与错误码无变化；单类不超过约 250 行。

## O7. 运维可观测性

### 现状
`ops` 只有 `HealthController`（依赖不可用返回 503），缺少业务运行指标。

### 执行步骤
1. 引入 `spring-boot-starter-actuator` + Micrometer，仅绑定 `127.0.0.1`，暴露 `health`、`metrics`、`prometheus`，并要求 `platform_admin` 或独立管理端口。
2. 指标：
   - outbox：`pending`、`failed`、`dead_letter` 数量，最老 pending 年龄，发布延迟直方图。
   - 传感器：在线数、心跳超时数（超过配置周期 3 倍）、批次拒绝率。
   - 接入：`ingest_record` rejected 比例（按原因码）。
   - 模型：当前激活版本、推理耗时与失败数（上线推理后）。
   - 登录：限速触发次数。
3. 健康分级：`liveness` 只看进程；`readiness` 看 MySQL，RabbitMQ 仅在 relay 启用时纳入。
4. 控制台概览页 `OverviewView.vue` 读取一个聚合只读接口展示上述数值（不扩展视觉设计，沿用现有组件）。
5. 日志：统一 MDC 字段 `requestId`、`principal`、`sensorId`，JSON 格式；确认日志中不出现凭据与原始载荷。

### 验收
指标可查询；停掉 RabbitMQ 时（relay 启用状态）readiness 变为 DOWN；日志抽样无敏感值。
