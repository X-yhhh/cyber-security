# 功能模块设计

版本：host-guard v5，状态核对于 2026-10-12。P1—P6 已完成，P4 本地后端、规则、数据库、lab 会话与 G3 编排已实现，Mac P5 执行器真实 PF 通过；P7 G3 进行中（文件回放健康口径方案 B 实施中），P8 未开始；前端不列为阶段任务。阶段见[开发路线](开发路线.md)，对象见[数据库设计](数据库设计.md)。

| M02 资产与能力授权 | 资产/接口/环境 → 观察权与执行租约；撤销拒绝新动作并请求清理 | P1、P4 |

| M04 数据与标签登记 | 公开 PCAP → 5 类标签账本、时间块切分清单；排除类型与来路不明流量不造标签 | P3（复用P1/P2） |
| M05 训练与选型 | train/validation → XGBoost/LightGBM 多分类候选、阈值与策略参数；Windows 离线训练 | P3 |
| M06 模型登记与运行时 | ONNX/manifest/评估 → 冻结本机推理；激活不启用阻断 | P3、P4 |
| M07 接入与检测 | 观察 → 推理（攻击分数与各类分数）；幂等、期限、容量保护 | P4 |

| M09 策略与发布包 | 模型/策略/评估/能力 → 冻结发布组合；独立审批 | P3、P4、P7 |
| M10 执行与恢复 | 签名命令 → 规则/回执；TTL、幂等、断连重启恢复 | P1、P5 |

## 2. 角色与权限

下列 v2 权限已由 P4 的 V19 显式映射到角色模板；迁移不向既有用户自动增加角色或重置账号。角色同时受 asset/model/dataset/report 范围约束。所有人工角色共有范围内的 `resource.read`，只用于非敏感对象元数据；敏感查询仍需表列专门读权限，写权限不隐式授予全部读取。同一版本起草人与批准人必须不同；服务账号不能代替独立批准。

| 角色 | 目标权限 | 边界 |
|---|---|---|
| platform_admin | `iam.manage`, `asset.manage`, `sensor.manage`, `authorization.request`, `ops.read` | 不默认拥有模型/策略批准权限 |
| security_reviewer | `authorization.approve`, `bundle.approve`, `policy.approve`, `evaluation.read`, `detection.read`, `action.read`, `action.revoke`, `automation.stop` | 不自批，不越过执行硬约束 |
| model_operator | `dataset.manage`, `model.manage`, `model.validate`, `evaluation.run`, `evaluation.read`, `policy.draft`, `bundle.request` | 不操作防火墙、不在线训练 |
| security_analyst | `detection.read`, `event.manage`, `feedback.label`, `action.read`, `action.request` | 不指定任意地址或 shell |
| evidence_reviewer | `feedback.review`, `evaluation.read`, `detection.read` | 不复核自己标签 |
| auditor | `audit.read`, `evaluation.read`, `action.read` | 只读 |
| sensor_agent | `machine.observation.write`, `machine.sensor.read`, `machine.sensor.health` | 不能领命令 |
| executor_agent | `machine.target.bind`, `machine.command.claim`, `machine.receipt.write`, `machine.executor.health` | 可信本机目标绑定与动作/恢复；不能提交模型观察或标签 |

单人开发可完成研究和测试身份隔离；测试身份只证明程序约束，不等于实际第二人发布审核。没有独立审批不能伪造 authorized_auto。

## 3. 状态与协作

### 3.1 观察和推理

观察为 `accepted / rejected / duplicate`，推理为 `succeeded / not_applicable / rejected / failed / expired`。不成功的推理不带攻击概率。接收成功不等于推理成功，两者分别查询。

上下文不足时记录覆盖时长，不因此丢弃合法单流；模型 manifest 决定是否适用。数据缺失不能伪装成低风险。

### 3.2 检测与事件

结论为 `observe / alert / block_candidate`。事件为 `open / investigating / contained / resolved / false_positive / closed`。只有确认规则生效才记录 contained；到期解除不自动宣称攻击已解决。

执行证据 episode 按 `(assetId, sensorId, bootId, peerKey, keyEpoch, direction, transport, servicePort, family, scope, source, ruleId, bundleId)` 和固定 30 秒桶归并，按 parentConnectionId 去重；模型及不同规则编号独立计数，续段也不能重复计数。入站 `port_scan` 的 `peer_inbound` 汇总端口为null，出站扫描仅按服务记录告警，不能获得全入站作用域（rc.3，见[契约第 8 节](检测与处置契约.md#80-来源汇总)）。同 parent 按因果时间选择最新观察，跨桶、未消费的新观察也使旧执行证据失效。同一主机其他 peer 不得升级本 episode。案件可以合并多个 episode，动作仍绑定单一证据与目标。

运行时 episode 桶只用于索引，离线评价按[验证与验收](验证与验收.md)的连接与活动口径计算。安全预算使用单独的稳定 budgetTargetId，不受 episode、boot、keyEpoch、活动或策略版本切换影响。健康缺口或实际规则未核实时保留额度占用，恢复条件见[统一契约](检测与处置契约.md#92-连续健康与预算恢复)。

K2 的批次路径保留同一事务中的资产锁、最新快照复核和批末判定：T1 按 UUID 与 `(sensor, boot, flow, snapshotIndex)` 两种身份批量去重，冲突仍整批回滚；T2 逐快照执行相同 ONNX，批量写推理、规则与证据事实，每个触及的 episode 在批末判定一次。数据库写入分段只是存储优化，不增加或提前判定。批量新增与复合键点查使用 Spring 事务内同一 JDBC 连接和预编译绑定参数，沿用表列白名单，严格检查写入行数及返回主键，不单独提交。批量更新使用派生键表通过主键连接赋值，避免逐行扫描 CASE 分支。驱动缓存最多 256 条、每条 SQL 至多 64 KiB，启用服务器预编译，避免大批次反复解析参数。跨批缓存仅保存最多 10000 条不可变观察内容，并按内部主键和内容摘要核对；每批仍从 MySQL 查询最新性、证据投影与推理状态，缓存不保存可变资格或替代事实源。窗口排序只处理证据主键，避免完整观察 JSON 进入排序临时表；episode/证据组合键以常量键表驱动唯一索引点查；episode 在每页内对其余十三列完全相同的键复用常量、逐项保留端口，仅在参数和 SQL 均缩小时启用，完整键条件和查询次数不变。最新快照明确使用 parent 索引，避免空库统计导致全表扫描或跨资产锁定。

research 路径已经禁止动作，故可在同一事务批量追加各 episode 的独立决策、案件时间线与 outbox；证据选择审计仍每个 episode、每批各一条并保留资产范围。research T2 使用 READ COMMITTED 消除缺失 episode 的跨资产间隙锁；同资产 T1/T2 仍由同一资产行锁串行化，判定期间不会有该资产的新观察插入或投影并发更新。research 各 episode 以投影完成后的同一数据库时刻判定，案件时间线在批量写入前统一取数据库时间；模型 manifest 在批内解析一次，证据引用保留全部原字段。服务端证据事实对无转义 ASCII、安全整数、布尔与 null 使用与原 JCS 字节一致的窄编码路径；任何非覆盖值或特殊节点整份回退原规范化实现，不改变输入校验或摘要协议。观察校验返回的 RFC8785 原文用于摘要和落库，机器请求摘要只在服务端计算一次并复用于两层幂等校验。已校验模型缓存特征字段路径，但每条观察仍重新读取字段并校验缺失及非有限值。`guard_inference.completed_at` 统一记录本批全部推理结束后的数据库时刻，是逐条推理完成时间的保守上界，不参与分类或证据资格；J1-5 主时延继续以实际持久回执为准。JDBC 批写后清除同事务 MyBatis 一级缓存，数据库时钟查询始终刷新，防止使用旧读结果。正式动作路径仍逐项读取时间并预留预算，后一个动作能看到前一个动作的额度消耗。JFR 计时只在录制时启用，分别记录 T1、ONNX、证据投影、episode 判定和真实提交；spool 回执的持久写盘单独统计，不参与风险判定。

### 3.3 发布与动作

策略为 `draft → reviewed → retired`；发布包为 `candidate → evaluated → approved → active → suspended/retired`，审批与激活分开。模型、特征、策略、决策/评价/健康版本、验收和平台能力按确切哈希绑定，仅改阈值也要新发布包。策略—能力资格唯一落在发布包（`guard_release_bundle` + `guard_bundle_capability` + `guard_asset_binding`），现有 supportedCapabilityIds 与组合清单必须一致；draft策略不能进入活动组合。细则见[统一契约](检测与处置契约.md#81-判定次序与发布绑定)。

动作状态和失败后的实际核对见[检测与处置契约](检测与处置契约.md)。拒绝须提供稳定原因，不能以“高风险”覆盖超时或目标未知。

### 3.4 lab 会话与报告（B4）

M11 增加独立 lab 会话：申请/批准与运行状态分开；V20 仅保存资格，V25 保存运行投影及追加事件。固定时间偏移、同 sensor/boot、同稳定目标和短租约限制由 [lab v1](contracts/lab-validation.md)绑定。GuardEligibility 在已登记 lab sensor 的判定/领取时检查会话是否仍可运行，撤销和超时不会阻止原有清理/回执。

场景结束、命令签发、核验生效和核验清理分别记录。报告工具读取同会话事实，按来源和场景计算、验签后独立导入；不直接授予类别资格、审批或激活发布包。合成输入始终不能产生正式 G3 passed。

## 4. 保留、替换及非目标

- 复用 IAM、资产、会话、MyBatis、outbox、制品校验、审计和研判。
- 替换单一 v4 特征路线、资产级自动关联、影子 G3 放行和无执行器的响应流程。
- 不做前端、全网扫描、攻击生成、漏洞利用、恶意软件运行、通用清洗、在线自训练、任意脚本策略。
- 采集、模型、执行器分别验收再联合发布；未实现能力不能写成支持。

## 5. 完成标准

每个模块具备契约、实现、相关测试、可复算证据和局限。M03 通过不代表 M05 准确，M05 通过不代表 M10 安全，M10 通过不代表模型值得自动执行。最终以[验证与验收](验证与验收.md) 为准。

## 6. B5 查询能力

独立只读查询单元（2026-10-11 已实现并合入 main，隔离验证通过，未部署）覆盖授权/采集配置（resource.read）、审计（audit.read）以及健康窗口/最新心跳/按资产运维事实（ops.read）。权限及范围每次从 IAM 事实复核并写入 SQL 条件，先于分页执行；审计沿用全部关联资源可见规则，列表与详情使用相同范围条件。查询仅投影字段白名单，健康窗口与心跳另给 unknown/stale/unhealthy/healthy 四态展示，不调用审批、续租、健康裁决、处置或预算恢复。路由、参数、游标与字段见[接口设计第 11 节](接口设计.md#11-b5-后端只读查询)；前端与服务部署另行完成。
