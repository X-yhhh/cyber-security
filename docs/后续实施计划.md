### T2 复现拟合（第二轮第 1 次，需要授权）

1. **授权**：用户书面批准第二轮拟合预算，为 1 次，排查时最多再 1 次。登记位置与 P3-B 台账同级，另起第二轮计数。
2. **执行**：在 win-dev 上用 `ablation-no-host-context` 的原配置训练（LightGBM、种子 42、默认超参、`no_host_context` 特征集）。数据、切分、类别映射、标签规则均为 P3-A 冻结的版本，不得变动。
3. **产出**：`model.onnx`（int64 类别输入）、`preprocessing.json`、`native-model.txt`、`framework-{train,validation}.npy`、validation 指标、拟合台账。
4. **一致性**：与 T1.2 的参照输出比较。框架概率和 ONNX 输出按 P3-B 的容差判定。不一致时排查原因（依赖版本、线程数、数据哈希），最多再拟合 1 次；仍不一致就停下来回报，不扩大预算。
5. **接口检查**：模型内部只使用 37+37+3 维，后端 `GuardModelRuntime` 固定接收 43+3 且类别输入为 int64。现行导出包装层对外接收 43+3、图内选出 37 维，`fit` 拒绝非 int64 图；T1.7 已在旧消融制品上验证同一包装方式能被后端加载。T2 产出后仍须用 T1.7 的后端探针复验新图一次，不通过不得进入 T3。

## 7. P7 联合闭环

### J1 V3 回放演练（R7，不需要 lab 授权）

**做法**

1. 从 validation 时段的 CIC PCAP 按类截取只含攻击来源的片段，每类至少 3 段，dos_slow 按 R4 收窄定义选取；再配正常片段，累计 ≥ 30 分钟。不使用 test。片段清单和哈希在回放前登记，回放后不得增删或替换片段。
2. 传感器（S2/S3）按 1 倍速读文件 → 后端真实模型（T7 交付包经 B3 导入）→ 规则 → 决策。环境为 research，执行器不接入。
3. **离线参照**：同一批片段先用 `guardextract` 离线提取，再用同一 ONNX 和同一策略离线计算告警与 `block_candidate`，作为回放结果的比对基准。
4. 只看告警、来源汇总、时延和假想封禁候选，不发封禁命令。
5. R5：同时测量洪泛和慢速来源在 10 秒证据期内能否凑够 `minDistinctFlows` 个质量合格连接。如需关闭 TSO 等系统配置，须另行授权并准备恢复步骤；不放宽 `offloadSuspected` 规则。

**通过标准**

整体项（任一不满足，J1 不通过）：

| 编号 | 项目 | 标准 |
|---|---|---|
| J1-1 | 链路一致性 | 回放观察与离线提取逐字段一致；上传序号连续，丢失 0、重复入库 0；推理失败（`MODEL_*` 错误）0 条，每条观察都有推理结果或明确的 `not_applicable` 记录 |
| J1-2 | 判定一致性 | 回放的连接级告警与离线参照一致率 ≥ 99%；每处不一致都要定位到具体原因（证据过期、到达顺序等时间因素），不能解释的差异视为缺陷 |
| J1-3 | 正常场景 | 正常片段的连接误报率 ≤ 2%（与 G1 同口径）；假想封禁候选折算 ≤ 1 次/小时（与 G3 第 3 项同口径） |
| J1-4 | 来源汇总 | 攻击片段的告警全部汇总到该片段的攻击来源；不出现把正常来源并入攻击 episode 的情况 |
| J1-5 | 运行开销 | 1 倍速下无持续积压（回放结束后 30 秒内队列归零）；观察产生到决策落库 P95 ≤ 2 秒；推理超时 0；无 `capacityDrop` |
| J1-6 | 安全 | 动作命令表新增 0 条；不产生任何 OS 规则 |
| J1-7 | 可复现 | 同一片段集重放一次，告警集合与类别结果一致 |

分类项（逐类判定）：

| 编号 | 项目 | 标准 |
|---|---|---|
| J1-8 | 告警 | 该类每段片段都对攻击来源产生告警，首次告警类别正确（模型或规则来源均可） |
| J1-9 | 告警时延 | 攻击起点 → 首次告警：port_scan、dos_flood ≤ 10 秒；brute_force、dos_slow ≤ 20 秒，每段都满足 |
| J1-10 | 自动准备度 | 每段片段都在 J1-9 的时延内对攻击来源产生假想 `block_candidate`；洪泛和慢速片段的质量合格快照比例同时报告（R5） |

**判定**

- J1-1 到 J1-7 全部满足，且四类都满足 J1-8、J1-9，J1 才算通过，可以进入 J2。G3 第 1 项要求四类都告警，J1 是它的预演。
- 满足 J1-10 的类别列为“计划 M2 自动封禁”；不满足的类别先按下面的退回规则查根因，查明后仍不满足才在 G3 中按只告警处理，并写明原因。计划 M2 的类别数低于第 9 节的保底线时，先执行第 9 节的保底分支，再进入 J2。
- 退回规则：链路或提取不一致回 S；推理、规则、决策或汇总问题回 B；某类告警或类别错误回 T（只能在 validation 上查，不能针对 J1 片段调阈值，否则这些片段不能再用于 G3）；质量覆盖不足按 R5 处理。
- 结果写入受控 run 目录，报告绑定片段清单、交付包、策略、传感器与后端版本的哈希。

## 9. 交付目标与保底方案

### 9.1 目标与保底线

| 层级 | 内容 |
|---|---|
| 目标 | 新候选通过 G1/G2；G3 中四类全部告警，四类全部取得 `lab_auto` 并完成真实封禁与恢复 |
| **保底线**（最低可接受交付） | 1. 发布组合通过 G1/G2；2. **G3 通过**：四类都经传感器 → 推理/规则 → 决策产生告警，正常场景误封 ≤ 1 次/小时；3. **至少 2 类取得 `lab_auto`**，在 Mac lab 完成真实封禁、TTL 或撤销清理、执行器核验，其中必须包括 brute_force；4. P5 的 Mac 必需场景全部通过；5. 未取得 `lab_auto` 的类别写明原因和后续路径 |

“四类只告警”不是可接受的交付结果，不作为保底。

保底线之所以可达，依据是以下已有事实：

- **规则来源不受主机上下文捷径影响**：四条规则（`host-guard-rules/1`）只使用对端级字段（`peerDistinctServicePorts`、`peerFlowStarts`、`peerBytesInbound`），不读 `host*` 字段。
- **规则在 L1 test 上已有逐类成绩**：首次 P6 评价（`p6-l1-01`）报告的“仅规则”成绩为 port_scan 召回 95.4% / 精确 100%，brute_force 召回 99.9% / 精确 91.2%，都达到类别自动资格线（≥ 80% / ≥ 90%）；dos_flood 召回 24%，dos_slow 召回 70.6% / 精确 78.4%，都不达标。规则阈值在 validation 上选定、读取 test 前冻结，第 2 次评价用的是同一组规则和同一个 test，成绩不变。
- **brute_force 不依赖全入站豁免**：它使用 `peer_service` 作用域，`GuardEligibility` 只在观察端口属于保护端口时才拒绝，所以不受 B1、R6 的阻塞。
- **去主机上下文模型的单对端敏感性为零**（T1.7 已用完整 validation 实测逐位不变）。

### 9.2 按来源判定自动资格（须登记进新评价版本）

**状态**：2026-10-08 用户采纳（A11）。已实施：decision-policy rc.4（`modelAutoEligible`）、决策版本 `2026-10-08.1`、P4 引擎与校验、[验收第 5 节](验证与验收.md#5-类别自动资格) 与契约正文；T1.6 已让 P6 工具按模型与每条规则分别计算和复算资格（合成验证）。待实施：T3.6 登记新评价版本，T4 正式评价后取得新候选资格数值。

[验收第 5 节](验证与验收.md#5-类别自动资格) 现在按类别判定资格，没有区分来源；[契约](检测与处置契约.md) 允许策略把规则显式标为可自动，但前提是该类别 `autoEligible=true`。保底方案需要把资格**按来源分别判定**：

- 模型来源用 P6 报告的 `modelOnly` 逐类成绩，每条规则用 `ruleOnly` 逐类成绩，各自对照 80% / 90%。
- 某类别只要有一个来源达标，该类就可以 `autoEligible=true`，但策略只能把**达标的来源**标为可自动；未达标来源的命中只产生告警。
- 报告分来源列出成绩和最终资格。

影响范围（已对照契约与 `GuardDecisionEngine` 核实）：

- **判定规则不变**：来源 × 类别 × 规则编号的汇总、T1—T9 次序与拒绝代码、`block_candidate` 条件都不改。引擎已经按“类别 + 来源 + 规则编号”逐条路径判定，混合来源直接拒绝；`rulePolicies[].autoEligible` 已能逐条规则开关。
- **评价规则要改**：验收第 5 节改为按来源判定资格，必须在 T3.6 登记新评价版本时写入；不追溯改变 `host-guard-evaluation/2026-10-07.1` 和 candidate-v2 的登记结论。
- **契约有一处缺口**：`familyPolicies` 只有类别级 `autoEligible`。类别设为可自动后，模型来源只要分数达到 `autoThreshold` 就进入自动路径，无法“关掉模型来源、只保留规则来源”。模型达标时不受影响（类别可自动，达标规则另行标记即可）；只有“模型不达标、规则达标”的类别需要补字段：在 `familyPolicies` 增加必填的 `modelAutoEligible`，引擎在模型路径上检查它，不满足时返回新拒绝代码。这是 decision-policy Schema 的修订，须同步契约 8.0 节、P4 校验与测试，并按契约版本规则登记，不能用把 `autoThreshold` 设为 1 之类的办法变相关闭。
- 规则路径不检查 `minDistinctFlows`（契约规定以规则命中代替连接计数），单次命中即可形成候选；这属于“单连接即可封禁”的模式，规则来源的自动封禁须在 G3 中单独验证误封情况。

对已完成阶段的影响：P1—P6 已登记的结论都不改变（candidate-v2 的 `p6-l1-01` 成绩、四类离线资格和 1/3 test 额度仍只按 `2026-10-07.1` 解释）。但 [P6 诊断第 5 节](p6/README.md#5-不改变的已完成结论) 为修复计划登记了“P4 代码、数据库、契约 Schema 不变”，采纳 A11 会改变这一承诺，须同时修订该节，说明这是 P4 的追加增量而非改写已收口结论：decision-policy 作为新增必填字段的不兼容变更单独升版本（观测 rc.2、manifest 与命令 rc.3 不动），旧版本策略保留为历史、不再可激活；数据库只存策略快照，不需要迁移。规则来源的资格数值以 T4 新评价中重新计算的 `ruleOnly` 为准，`p6-l1-01` 的数值只用于判断保底线是否可行，不直接转移。

是否采纳见第 11 节 A11。

### 9.3 保底分支

| 触发情况 | 保底处理 | 保底线是否仍可达 |
|---|---|---|
| T2 两次复现都与参照不一致 | 不再追求逐位复现，把复现出的模型当作新模型：用它自己的 validation 审计重新选阈值、跑单对端检查和 T1.7 探针，旧消融成绩不再引用（与 P3-B 的处理一致）。validation 出口不达标时停下回报 | 可达，不再追加拟合 |
| T4 中 G1/G2 未通过 | 先回 P3 查根因；第 3 次额度只在根因明确、改动已登记后使用。仍未通过时，按[验收第 7 节](验证与验收.md#7-失败处理与测试集使用)收窄支持类别重新登记：不达标类别的模型来源改为只告警，规则来源按 9.2 保留资格 | 可达：port_scan、brute_force 走规则来源 |
| J1 中某类不满足 J1-10 | 查根因后仍不满足，该类在 G3 中按只告警处理；计划 M2 的类别数仍须 ≥ 2 | 只要 brute_force 加另一类可达即可 |
| B1/E3 的 `peer_inbound` 未按时通过 | E3 先用 `peer_service` 作用域跑通真实 P4 联合链路（brute_force 所需），`peer_inbound` 继续推进；port_scan 在全入站通过前不进入 M2 | 可达：brute_force 加 dos_flood 或 dos_slow |
| dos_flood 在 Mac 实时抓包下质量覆盖不足（G3 第 5 项） | 按 R5 申请 A7 测试 TSO 等配置，须有恢复步骤；不放宽 `offloadSuspected` | 不影响保底线 |
| G3 某类自动封禁未通过 | 按失败环节回 P4 或 P5 修复后重跑该类；修复不了的类别降为只告警并写明原因 | 剩余通过类别 ≥ 2 即达保底线 |

保底线也达不到时（例如 brute_force 的模型和规则来源都没能在 G3 封禁成功），停止推进 P8，回报失败环节和证据，由用户决定下一步，不降低标准来宣称完成。

### 9.4 已知风险

- brute_force 规则来源的 L1 精确率 91.2%，离 90% 线只差 1.2 个百分点。主要依靠模型来源，规则来源只作保底。
- 旧审计中规则 `brute_force` 只对 21、22 端口生效，`dos_flood`、`dos_slow` 只对 80、443 端口生效。rc.4 规则无法表达端口条件，按 T3.5a 改由授权 `executionScopes.servicePort` 限定执行端口并重新审计；若去掉端口条件后精确率跌破 90%，规则来源降为只告警。G3 lab 的服务端口须与授权一致，不能为了通过而改授权端口。
- 规则来源的资格来自 CIC 数据。Mac lab 中规则阈值的适配情况由 J1、G3 实测，不足时如实降级。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 复现拟合与参照不一致 | T2 预算耗尽 | 先固定依赖版本和线程数，用 T1.2 参照输出做预检；仍不一致就停下回报，不扩大预算 |
| 导出图与后端输入契约不符（43+3、int64） | 后端拒绝加载或浪费拟合预算 | T1.7 在 A1 前用零拟合探针验证导出包装与后端加载；T2 产出后复验一次 |
| P6 第 2 次评价失败 | test 只剩 1 次 | 按根因修正并预登记后再用；不针对 test 调参 |
| validation 多次使用 | 成绩偏乐观 | 报告写明使用次数和偏差风险；L2、L3′ 作为外部参照 |
| 新候选在 G3 中多类失败 | 交付低于目标 | 第 9 节保底线：至少 2 类 `lab_auto`（含 brute_force），规则来源作为不受模型影响的后备 |
| 洪泛质量覆盖不足 | G3 第 5 项不达标 | J1 中先测 R5；不放宽质量规则，必要时该类降为只告警 |
| 能力绑定误放行 | 真实环境被误封 | B1.3 五条件全满足才放行，authorized 环境继续拒绝；E3 前补齐拒绝测试 |
| 用户已有 PF 规则被改 | 违反安全边界 | E1 逐字节比对；未知归属只暂停不删除 |
| lab 外联 | 违反隔离要求 | 只用回环或经网络层隔离证明的 lab；应用开关不算隔离 |
| 文档与代码漂移 | 误报阶段状态 | 每个任务完成时回写开发路线与对应入口文档 |

- 不训练或微调大语言模型；检测与处置不依赖外部大模型 API。

- 计划能力不写成已实现、已训练或已上线。
