# 数据库设计

## 1. 设计原则

- MySQL 8 保存业务事实、配置和审计；Redis 仅作缓存、临时状态与幂等辅助；RabbitMQ 只作消息传输。
- 业务表统一使用 `BIGINT` 主键、`created_at`/`updated_at` UTC 时间、明确状态字段和逻辑归档策略。API 可用 UUID/ULID 作为外部标识，避免暴露连续主键。
- JSON 仅用于来源扩展字段、manifest 快照和结构化规则参数；核心关系、过滤字段、状态和时间维度采用独立列。
- 原始载荷默认不长期存入业务表；若保留，存入受控对象存储并仅保存对象键、校验和、加密/保留元数据。
- 所有自动处置相关记录保留模型、策略、授权与资产快照，便于历史复核；审计采用追加写入，不提供普通 CRUD 删除能力。

## 2. 表清单

### 2.1 身份与授权

| 表 | 主要字段 | 说明/约束 |
| --- | --- | --- |
| `sys_user` | `id`, `user_key`, `username`, `display_name`, `status`, `password_hash`/`identity_subject` | 用户主体；优先对接可信身份源，密码不明文保存 |
| `sys_role` | `id`, `role_key`, `name`, `status` | 角色定义 |
| `sys_user_role` | `user_id`, `role_id`, `scope_type`, `scope_id` | 用户角色及资源范围；联合唯一键 |

## 3. 关系与关键索引

- `asset 1—N sensor_agent`、`sensor_agent 1—N sensor_config/sensor_health_window`；每个活动传感器必须绑定登记资产。
- `data_source 1—N source_mapping`、`data_source 1—N ingest_batch`、`ingest_batch 1—N ingest_record`。
- `ingest_record 1—N inference_request`；一次记录可用于版本对比，但活动告警需能标识正式判定版本。
- `inference_request 1—N detection_alert`；事件通过 `event_alert_link` 关联告警，通过 `event_asset_link` 关联资产。
- `security_event 1—N event_timeline/approval_task/action_execution`。
- `model_version 1—N model_deployment/inference_request/replay_run/drift_metric_window`；训练任务经审批后产出候选 model_version，发布单独留痕。
- `ingest_record/detection_alert 1—N feedback_sample`；纳入训练集须有人工确认来源及数据集版本。
- 推荐索引：`ingest_record(data_source_id,event_time)`、`ingest_record(batch_id,quality_status)`、`inference_request(status,requested_at)`、`detection_alert(status,severity,detected_at)`、`security_event(status,severity,last_seen_at)`、`event_timeline(event_id,occurred_at)`、`approval_task(status,expires_at)`、`action_execution(status,started_at)`、`audit_log(resource_type,resource_id,occurred_at)`。
- 传感器/迭代索引：`sensor_agent(asset_id,status)`、`sensor_health_window(sensor_id,window_start)`、`drift_metric_window(data_source_id,model_version_id,window_start)`、`feedback_sample(training_eligible,reviewed_at)`、`model_training_job(status,created_at)`。
- 对高增长的事件/审计表按时间归档；是否分区由容量实测后决定，避免首期过早引入复杂分区维护。

## 4. 状态约束

- `ingest_batch`: `received → validating → processing → completed|completed_with_errors|rejected`。
- `inference_request`: `queued → running → succeeded|rejected|failed|timed_out`。
- `security_event`: `open → investigating → contained → resolved|false_positive|closed`；状态变化必须写入时间线。
- `approval_task`: `pending → approved|rejected|expired|cancelled`。
- `action_execution`: `queued → running → succeeded|failed|timed_out → rollback_pending → rolled_back|rollback_failed`。不可回滚动作不得配置为自动执行。
- `model_training_job`: `requested → approved → queued → running → completed|failed|cancelled`。训练输出始终是候选版本，不直接修改活动部署。
- `model_release_record`: `candidate → validated → shadow → approved → active → retired|rolled_back`。不允许候选模型跳过验证和审批成为活动模型。
- 状态迁移由领域服务校验，禁止客户端直接任意更新状态列。

## 5. 一致性、隐私和保留

- 业务变更和 `outbox_event` 在同一 MySQL 事务提交；消费者以消息 ID/幂等键去重，重试超限进入死信及人工处置。
- Redis 不保存唯一审计或授权事实。缓存失效后必须从数据库重新读取当前授权和策略。
- 传感器可缓存最后一份已签名配置和当前批准模型版本；控制面断连时不接受新的远程动作，不自动训练或换权重，并按明确策略进入持续检测/仅记录/安全停止状态。
- 执行时的资产授权、模型部署和策略版本做快照或哈希引用，历史审计不因后续配置修改而改变语义。
- 设定原始载荷、规范事件、告警、审计和导出文件各自的保留期限；删除/脱敏需要审批和留痕。敏感凭据不入库。
- 首期逻辑设计不绑定具体 DDL/分区/容量。实现前依据数据保留量、导入速率和毕设部署容量完成容量评估。
