# 数据库设计

## 1. 设计原则

- MySQL 8 保存业务事实、配置和审计；Redis 仅作缓存、临时状态与幂等辅助；RabbitMQ 只作消息传输。
- 业务表统一使用 `BIGINT` 主键、`created_at`/`updated_at` UTC 时间、明确状态字段和逻辑归档策略。API 可用 UUID/ULID 作为外部标识，避免暴露连续主键。
- JSON 仅用于来源扩展字段、manifest 快照和结构化规则参数；核心关系、过滤字段、状态和时间维度采用独立列。
- 原始载荷默认不长期存入业务表；若保留，存入受控对象存储并仅保存对象键、校验和、加密/保留元数据。
- 所有自动处置相关记录保留模型、策略、授权与资产快照，便于历史复核；审计采用追加写入，不提供普通 CRUD 删除能力。

## 3. 关系与关键索引

- `asset 1—N sensor_agent`、`sensor_agent 1—N sensor_config/sensor_health_window`；每个活动传感器必须绑定登记资产。
- V8 增加 `api_client.sensor_id` sensor 主体外键，以及 `ingest_batch` 的 sensor/config/sequence/contract 追溯列；sensor 序号在 `(sensor_id, config_version)` 范围内唯一，旧 connector 批次保持 NULL 兼容。
- `data_source 1—N source_mapping`、`data_source 1—N ingest_batch`、`ingest_batch 1—N ingest_record`。
- `ingest_record 1—N inference_request`；一次记录可用于版本对比，但活动告警需能标识正式判定版本。
- `inference_request 1—N detection_alert`；事件通过 `event_alert_link` 关联告警，通过 `event_asset_link` 关联资产。
- `security_event 1—N event_timeline/approval_task/action_execution`。
- `model_version 1—N model_deployment/inference_request/replay_run/drift_metric_window`；训练任务经审批后产出候选 model_version，发布单独留痕。
- `ingest_record/detection_alert 1—N feedback_sample`；纳入训练集须有人工确认来源及数据集版本。
- 推荐索引：`ingest_record(data_source_id,event_time)`、`ingest_record(batch_id,quality_status)`、`inference_request(status,requested_at)`、`detection_alert(status,severity,detected_at)`、`security_event(status,severity,last_seen_at)`、`event_timeline(event_id,occurred_at)`、`approval_task(status,expires_at)`、`action_execution(status,started_at)`、`audit_log(resource_type,resource_id,occurred_at)`。Flyway V9 已补充 `ingest_record(created_at,quality_status,asset_id)`、`approval_task(status,created_at,id)` 和 `audit_log(occurred_at,id)`，服务于 24 小时质量汇总、审批台账和时间线排序。
- 传感器/迭代索引：`sensor_agent(asset_id,status)`、`sensor_health_window(sensor_id,window_start)`、`drift_metric_window(data_source_id,model_version_id,window_start)`、`feedback_sample(training_eligible,reviewed_at)`、`uk_feedback_active_alert(active_alert_id)`、`model_training_job(status,created_at)`。
- 对高增长的事件/审计表按时间归档；是否分区由容量实测后决定，避免首期过早引入复杂分区维护。

## 4. 状态约束

- `ingest_batch`: `received → validating → processing → completed|completed_with_errors|rejected`。当前实现接收时直接判为 `received` / `completed_with_errors` / `rejected`；V16 起消费事务推理完成后把 `received` 置为 `completed` 并写 `finished_at`，`completed_with_errors` 只补 `finished_at`。
- `feedback_sample`（V16）: `pending → training_approved|rejected`；复核人不得为标注人，`training_eligible` 只能在 `training_approved` 时为真。
- `inference_request`: `queued → running → succeeded|rejected|failed|timed_out`；V12 增加终态 `not_in_model_scope`（视角/地址族不在模型评估范围，不推理、不算拒绝）。本机推理同步写终态，不经过 `queued/running`；超时为 `timed_out` + `INFERENCE_TIMEOUT`。
- `security_event`: `open → investigating → contained → resolved|false_positive|closed`；状态变化必须写入时间线。
- `approval_task`: `pending → approved|rejected|expired|cancelled`。
- `response_policy`（V15）: `draft → pending → active|rejected`；起草人撤回 draft/pending 记 `retired`；active 被新版本取代或由审批人退役时记 `retired`。`approved` 仅为 V1 历史行保留，服务层不写入。
- `action_execution`: `queued → running → succeeded|failed|timed_out → rollback_pending → rolled_back|rollback_failed`。不可回滚动作不得配置为自动执行。
- `model_training_job`: `requested → approved → queued → running → completed|failed|cancelled`。训练输出始终是候选版本，不直接修改活动部署。
- `model_release_record`: `candidate → validated → shadow → approved → active → retired|rolled_back`。不允许候选模型跳过验证和审批成为活动模型。
- 状态迁移由领域服务校验，禁止客户端直接任意更新状态列。

## 5. 一致性、隐私和保留

- 业务变更和 `outbox_event` 在同一 MySQL 事务提交；消费者以消息 ID/幂等键去重，重试超限进入死信及人工处置。
- V10 增加 `consumed_message`，记录批次事件消费者的处理状态、失败次数和脱敏错误摘要；RabbitMQ ack 仅在消费事务提交后执行。
- V11 为 `sensor_config` 增加 `feature_contract_sha256`，为 `source_mapping` 增加 `feature_contract_version`、`feature_contract_sha256`（路线 B §3.3）。哈希由服务端按契约注册表写入，CHECK 约束要求 64 位小写十六进制（`REGEXP_LIKE(..., 'c')` 强制区分大小写，默认排序规则不区分大小写）。历史行保持 NULL；在线契约要求哈希非空且等于注册表当前值，契约文件变化后旧配置按 `CONFIG_VERSION_STALE` 失效、需重新批准。

- V14 为 `source_mapping` 增加 `requested_by`（外键 `sys_user`）与 CHECK `ck_source_mapping_separation`（批准人≠登记人），新增权限 `source.mapping.approve`（`platform_admin`）。V14 之前的映射 `requested_by` 为 NULL，服务层拒绝经接口批准。
- V15 为 `response_policy` 追加上表所列生命周期列、外键与 CHECK（`ck_response_policy_separation`、`ck_response_policy_review_separation`、`ck_response_policy_active_approved`、`ck_response_policy_content_sha256`），状态 CHECK 增加 `rejected`，唯一键 `uk_response_policy_active` 基于生成列。新增权限 `response.policy.draft`（`security_analyst`）、`response.policy.approve`（`response_approver`），`security_analyst` 追加 `response.policy.read`。V15 之前的策略 `created_by` 为 NULL，服务层拒绝经接口审批。
- V16 为 `drift_metric_window` 追加样本量、基线来源、计算版本、唯一键 `uk_drift_metric_window`、模型外键与状态 CHECK；为 `feedback_sample` 追加说明、复核列、生成列 `active_alert_id` 与唯一键、告警外键及 CHECK（`ck_feedback_review_status`、`ck_feedback_review_separation`、`ck_feedback_review_complete`、`ck_feedback_training_eligible`）。新增权限 `alert.feedback.label`（`security_analyst`）、`feedback.review`（`security_analyst`、`response_approver`）、`shadow.report.read`（`platform_admin`、`security_analyst`、`model_operator`，按 data_source 范围）。`data_source.last_success_at` 由接入事务在有记录通过门禁时写入。
- Redis 不保存唯一审计或授权事实。缓存失效后必须从数据库重新读取当前授权和策略。
- 传感器可缓存最后一份已签名配置和当前批准模型版本；控制面断连时不接受新的远程动作，不自动训练或换权重，并按明确策略进入持续检测/仅记录/安全停止状态。
- 执行时的资产授权、模型部署和策略版本做快照或哈希引用，历史审计不因后续配置修改而改变语义。
- 设定原始载荷、规范事件、告警、审计和导出文件各自的保留期限；删除/脱敏需要审批和留痕。敏感凭据不入库。
- 首期逻辑设计不绑定具体 DDL/分区/容量。实现前依据数据保留量、导入速率和毕设部署容量完成容量评估。

## 6. 首期建库实现

- MySQL 8 初始化脚本为 `database/init.sql`，默认库名 `cyber_security`，采用 InnoDB、`utf8mb4_0900_ai_ci` 和 UTC 时间语义；共创建本设计清单中的 34 张表及对应主键、唯一约束、外键和常用查询索引。
- 脚本只创建 schema，不使用 `DROP`，也不预置角色、资产、数据源、模型、策略或模拟事件。仅在 `sys_user` 插入一个本机联调账号 `admin`，密码 `admin` 以 BCrypt 哈希保存；遇到同名记录时保留既有账号，不覆盖密码。
- 此测试凭据不得用于非本机开发环境。初始化 SQL 只创建用户记录，不授予角色；Flyway 只维护内置角色与权限模板，不创建或提升任何用户。本机开发 profile 在 schema 初始化成功后才可为存在的 `admin` 补充 `platform_admin` 角色关联，并保留现有 BCrypt 哈希。
- 首期脚本以空库初始化为目标。现有库的演进应通过后续版本化迁移完成，不应以重新初始化覆盖已有数据。容量实测后再决定高增长表的归档或分区方式。

## 7. 身份授权与迁移增补

- Flyway V2 seed 31 个用户/控制台权限点及 7 个内置角色固定矩阵；V4 增加只授予机器主体的 `machine.ingest.submit`，V7 增加模型候选校验和本机部署激活权限，V7 时共 34 个权限点（历史快照；V18 当前为 52 个）。`platform_admin` 获 21 个显式管理/只读权限；模型校验/激活仍限定给 `model_operator`，不含响应策略维护、响应审批/执行或模型发布。
- 本机 `admin` 用户记录与 BCrypt 密码哈希必须原样保留；本机 bootstrap 只新增其 `platform_admin` 角色绑定。通用迁移不得改写密码、删除或自动提升现存用户。`admin/admin` 仅由本机开发 profile 初始化，非本机环境不得默认建立该账号。
- 仓库初始化 SQL 的 BCrypt 哈希由 `BootstrapAdminHashTest` 固定校验为可匹配 `admin`；当前既有业务库哈希仍不由启动流程重置，非 `local` profile 仅在检测到初始化口令时输出不含哈希的告警。既有库若需改密，必须确认本机目标后由管理员手工执行，不写入 Flyway。
- 首次接入 Flyway 前业务数据库没有历史表（历史步骤；阶段 1 已迁移至 V17）。迁移前要比对全部列、索引、约束和表选项，完成备份并确认符合 V1 基线后登记 baseline，再应用后续 RBAC/session/audit 向前迁移。发现漂移必须先制定兼容迁移，不得依赖无条件自动 baseline。应用配置明确关闭自动 baseline；隔离 MySQL 测试 schema 已验证空库 V1-V13 顺序迁移及非空无历史 schema 拒绝迁移。
- 会话表由 Flyway 创建。应用运行身份与 schema 迁移身份分离；应用仅得必要 DML 权限，凭据从环境或受控密钥配置读取，不提交 Git。
- 后端查询使用 MyBatis 映射，用户、内置角色、资产和审计查询均由参数绑定；分页/范围条件在 SQL 内执行，不将权限键或范围拼接为表名/列名。资源范围必须与拥有相应功能权限的角色绑定同一授权记录。
- 用户角色替换在事务内删除并重建该用户绑定、撤销其 `SPRING_SESSION` 记录并追加审计；内置角色目录和角色权限关系仅供读取，API 不修改模板。资产/数据源/模型范围授予前验证目标存在；只有 `platform_admin` 可持有 `global/*`，但其实际权限仍受该角色自身权限点集合限制。
- 审计范围通过 `audit_resource_scope` 关联；范围型 SQL 使用双重 `NOT EXISTS`，拒绝空范围和部分可见的多资源记录，再进行排序分页。平台全局读取必须同时满足 `audit.read` 与 `platform_admin/global/*`。
- 本地授权集成测试只写入独立 `cyber_security_backend_*_20260923` 测试 schema；本机业务 schema `cyber_security` 不会由测试或构建自动迁移。
- Flyway V2 增加权限目录、角色权限、机器权限/范围、审计范围和 JDBC session 表；V3 增加登录限速事实表；V4 扩展机器凭据类型/摘要和批次请求摘要，并增加 connector 专用权限；V5 增加机器客户端级数据源—资产配对授权；V6 增加模型发布审查和响应审批台账字段/约束；V7 增加模型候选校验和本机部署激活权限；V8 增加 sensor 主体绑定、批次序号/配置/契约追溯；V9 补齐大表排序与质量汇总索引；V10 增加消费者幂等与失败台账；V11 增加映射/配置的契约文件哈希绑定；V12 增加推理结果快照列、状态不变量与推理台账/dry-run 权限；V13 增加检测策略表、告警/事件追溯列与规则权限，V14 增加映射登记人、职责分离约束与映射批准权限，V15 增加响应策略生命周期列、职责分离与单 active 约束及策略起草/批准权限；V16 增加漂移窗口唯一键与样本量、告警标注第二人复核及影子验证相关权限。V1 的 34 张业务表与初始化 SQL 一致，但迁移不含数据库创建语句及固定用户插入。当前迁移测试验证 V1-V18 顺序、48 张业务/session/互斥锁表、18 条成功历史记录、52 个权限点、V16 漂移窗口与标注复核列及唯一键、V15 策略生命周期列与约束、V11 哈希 CHECK 约束、V12 结果快照 CHECK 约束及 V13 策略唯一 active 与模型告警追溯约束。
- 范围类型为 `global`、`asset`、`data_source` 和 `model_registry`。资产授权由资产/数据源管理员提交为待审批，平台管理员使用独立 `asset.authorization.approve` 权限批准；服务层强制申请人和批准人不同，未审批授权不得用于实网接入或响应。多资源事件要求所有关联对象可见；审计按受控资源关联字段过滤；响应动作还要检查当前资产授权与策略。模型发布记录增加申请人字段，应用服务必须拒绝申请人自批。


## 8. 阶段 1 生命周期迁移（V17）

`V17__entity_lifecycle_crud.sql` 在既有表追加审计列，不删除事实、不修改既存账号口令、不自动迁移开发库。

| 表 | 新增字段/约束 | 服务语义 |
| --- | --- | --- |
| `sys_user` | `password_changed_at` | 冻结/解冻、改密、改角色撤销会话；冻结和角色变更统一先锁 `platform_admin` 角色行，再锁目标用户，避免并发破坏最后管理员约束 |
| `asset_authorization` | `revoked_by/at`、`revoke_reason`，撤销人外键 | pending/active → revoked；不删除历史。只剩无有效授权时拒绝接入/处置；另一有效授权仍可独立授权 |
| `source_mapping` | `reviewed_by/at`、`decision_reason`、`retired_by/at`，职责分离 CHECK | draft/pending → approved/rejected，approved → retired；批准/驳回记审查人，退役记录单独保留 |
| `sensor_config` | `requested_by`、`change_reason`、`reviewed_by/at`、`decision_reason`、`activated_by`、`retired_at`，职责分离 CHECK | pending → approved/rejected → 显式 active；启用时同事务退役旧 active，历史首配置保留 |
| `api_client` | `rotated_at`、`revoked_by/at`、`revoke_reason` | 只轮换 active 传感器凭据；吊销不可恢复；详情和列表不返回摘要/凭据 |

新增 `sensor.config.approve` 授予 `platform_admin`。资产/数据源沿用 active、disabled、retired，retired 为终态。传感器下线沿用 revoked，同时吊销凭据并退役 active 配置。状态冲突 409，越权 403，范围外隐藏为 404。查询和存量测试均已适配新列。

窗口规则不新增表：通过 `idx_ingest_record_asset_time` 读同资产同契约已接收记录；消费事务先按资产 ID 统一排序加锁，窗口记录和已有告警使用当前读，避免 MySQL REPEATABLE READ 旧快照漏见其他事务已提交告警而重复告警。


## 9. 阶段 2 生命周期及信号分层（V18）

`V18__detection_policy_and_phase2_lifecycle.sql` 已在独立 MySQL 8 schema 验证空库初始化和既有测试库向前迁移；开发库仍为 V17。本迁移不删除历史事实、不修改 admin、不批准或启用新策略。新增后总表数 48、权限 52。

| 表 | 新增内容 | 约束/用途 |
| --- | --- | --- |
| `detection_policy_lock` | 三个 policy_type 固定行 | 分级/关联/风险各自串行分配版本、批准和退役；不是业务事实源 |
| `model_lifecycle_lock` | id=1 固定行与 CHECK | 串行发布审查、校验、激活/回退/退役；覆盖部署表为空的情况 |
| `detection_policy` | created_by、based_on_policy_id、change_reason、content_sha256、submitted_at、reviewed_by/at、decision_reason、retired_by/at | author/base/reviewer/retirer 外键，状态 draft/pending/active/rejected/retired，起草人≠审批人 CHECK；保留 V13 单 active 约束 |
| `detection_alert` | alert_layer、correlation_policy_version、promoted_at；层级/时间索引 | 旧行 default alert；signal 必须 model 且 low；升级原行并追加 basis.promotion，不删除/重建事实 |
| `approval_task` | withdrawn_at、withdraw_reason | 申请人仅撤回 pending 为既有 cancelled 终态；不写假审批人 |
| `model_version` | retired_at、retired_by、retire_reason | 退役人外键，模型和历史发布/部署/制品保留 |

新增 `detection.policy.read/manage/approve` 三权限，内置角色授权见接口矩阵。策略转换审计含规范化内容 `after_hash`；历史 seed 作者/hash 为 NULL，不补造审批身份。撤回/批准统一先锁事件再锁审批单，避免相反锁序死锁；模型内存切换以事务登记序号阻止提交回调乱序覆盖。

信号/事件关联复用资产锁，模型命中计数按 ingest_record_id 去重；同资产同契约且同策略版本才参与模型计数。原 G3 报告仍包含模型信号，面向人工处置的列表与态势图只统计 alert。数据库迁移完成不代表分层已经启用，须经 API 起草并独立批准带 modelSignal 的新策略。
