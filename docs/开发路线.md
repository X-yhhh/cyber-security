## 1. 目标与架构

系统持续监测授权主机的入站流量，识别 4 类攻击（端口扫描、暴力破解、洪泛 DoS、慢速 DoS），并对确认的攻击来源实施限时、可撤销的本机防火墙封禁。各组件分工如下：

| 组件 | 只负责 | 主要阶段 |
|---|---|---|
| 传感器（Go） | 抓包、组流、计算特征并上报，不做判断 | P2（已交接） |
| 检测（后端 ONNX 推理） | 对每个快照输出攻击概率与类别，不决定是否封禁 | P3、P4 |
| 规则引擎（后端） | 基于观察字段的阈值规则，作为第二条检测来源 | P3、P4 |
| 决策（后端） | 按来源汇总模型与规则结果，决定告警或封禁候选，检查白名单、授权与预算 | P4 |
| 执行器（Python） | 校验签名命令，安装/清理 PF 或 WFP 规则并回执 | P5 |

验收采用 3 道硬门槛：G1、G2 衡量模型，G3 衡量闭环。另有类别自动资格，定义见 [验证与验收](验证与验收.md)。

### 评价后诊断（2026-10-07）

[P6 诊断](p6/README.md) 在冻结候选上做了零拟合反事实：只读 validation，不读 test，不重读 L3，累计拟合仍为 33/33。结论有三点：

- 当前候选依赖主机侧上下文（`hostDistinctPeers` 等）。只把主机改为“1 个对端”时，validation 中暴力破解检出从 100% 降到 52.15%，洪泛和慢速都降到 0%；端口扫描基本不变，正常误报仍为 0。
- 把慢速类压到 L3 的形态（单对端、≤4 条流）后检出为 0%。冻结的慢速规则要求 30 秒同源新建连接 ≥21 条，在 L3 中按设计不可触发。因此 L3 0/29 由模型捷径和 L3 形态共同造成。当前慢速能力只能表述为“多对端主机环境中的同源高并发 HTTP 连接占用”。
- 候选里的 `decision-policy.json` 是 P3 研究格式，对当前 rc.3 Schema 有 21 处不符；manifest 只有版本号 1 处不符。P7 前需要生成一份合规的契约策略，部署侧字段只能取自 P4 现行配置，取不到时拒绝生成。
