## 0. 摘要

- 问题：P0-1（M1）要求开启在线特征门禁，但契约 `unsw-nb15-flow-v3.1` 的 `ct_state_ttl` 没有可审计的 codebook。训练端直接读取 UNSW-NB15 CSV 中现成的这一列，训练流程从未产生过“原始字段 → 编码值”的映射。
- 根因更深一层：`sttl`、`ct_state_ttl` 是 UNSW 靶场环境特征（EDA 中互信息排名最高），真实网络中不可移植；`ct_*` 窗口特征还依赖 UNSW 的网络级观测点，与“单主机软件传感器”的观测语义不同。
- 决策（本文前提）：采用路线 B，定义可移植特征契约 `unsw-nb15-flow-v4`，离线重训新模型版本，不为 v3.1 补猜测 codebook。v4 字段集为 17 个数值 + 2 个类别（§4.2；2026-09-29 按 §7.1.1 由 19 个再删 2 项），传感器实现规则已在 §4.3 预先定案。
- 结论：这不是项目重构。架构、模块边界、数据库主体、IAM、审计、outbox/M2、模型制品校验与激活流程都保持不变；改动集中在“特征契约 + 特征构造 + 模型运行时的输入维度”这一条线上，另加一次离线重训。
- 训练端已有实测支持：run `feature-20260927-1249` 的 TTL 诊断显示，去掉 `sttl`、`dttl`、`ct_state_ttl` 后 Macro-F1 反而 +0.0022（§4.1）。TTL 是分裂捷径，不是信息来源。
- 最大风险不在 TTL，而在“训练特征定义与在线传感器计算定义的一致性”。因此第一步是传感器可行性探测 + 全量特征审计 + 规格冻结，而不是只删两列。
- 粗估工期（单人）：到影子验证完成约 7～9 周，含响应能力与最终验收约 11～13 周。三个决策门（G1 字段集、G2 传感器一致性、G3 影子验证）决定实际范围。
- 落地约束：契约只冻结一次。阶段 1 先做传感器可行性探测再冻结规格，确保后续用真实数据再训练时只换模型、不改契约（见 §4.4、§4.5）。

## 2. 范围界定

### 2.1 为什么不是重构

项目按“契约版本 + 不可变模型 manifest”解耦，大部分模块只识别版本号，不关心特征列：

| 保持不变 | 需要修改 |
|---|---|
| 模块化单体结构、Spring Boot/MyBatis 基线 | `ingest/contract`：契约由资源文件加载、哈希校验、多版本注册 |
| IAM、会话、资产、授权、审计 | `ingest/feature`：契约驱动的 Feature Builder，窗口参数来自契约 |
| 批次接入、幂等、outbox、M2 消费链路 | `model/runtime`：输入维度与字段顺序读取 manifest，不再用常量 |
| 模型登记、候选校验、发布审批、本机激活台账 | `ingest/replay`：UNSW CSV → v4 字段映射 |
| 响应申请、审批、策略快照 | 训练端：新增 v4 特征视图、重训、导出新交付包 |
| 数据库主体 schema（仅追加 V11 契约哈希列） | 设计文档：M1/M3/M5 的契约描述和依赖关系 |

### 2.2 不在本路线范围内

- 不修改、不删除 v3.1 契约和 `unsw-binary-2026.09.0`；二者保持不可变，只作为 UNSW CSV 离线回放与历史对照。
- 不为 v3.1 编造或推导 `ct_state_ttl` codebook，v3.1 永不开启在线门禁。
- 不训练或微调大语言模型，不在线自训练，不自动更换权重。
- 不宣称全网覆盖、原始包检测、攻击阶段预测或通用 DDoS 防护。
- 不扩展前端视觉设计范围（UI 规范未完成确认前）。

## 3. v4 特征契约设计

### 3.1 契约文件结构（草案）

后端资源文件 `backend/src/main/resources/feature-contract/unsw-nb15-flow-v4.json`，字段在阶段 1 冻结后填写：

```json
{
  "version": "unsw-nb15-flow-v4",
  "specDocument": "docs/特征规格-unsw-nb15-flow-v4.md",
  "specSha256": "<特征规格文档 SHA-256>",
  "task": "binary_flow_classification",
  "manifest": "unsw-binary-2026.10.0",
  "directionBasis": "initiator_to_responder",
  "viewpoints": ["responder", "initiator"],
  "window": { "kind": "last_n_completed_flows", "size": 100, "scope": "per_sensor_per_address_family", "allowedLatenessSeconds": 0 },
  "addressFamilies": ["ipv4", "ipv6"],
  "packetNormalization": { "basis": "on_wire_segments", "oversizeRule": "split_by_mss" },
  "excludedFlows": ["multicast_destination", "broadcast_destination", "loopback"],
  "numericFields": [
    { "name": "dur", "unit": "second", "nullable": false, "min": 0, "unitVerified": true }
  ],
  "categoricalFields": [
    { "name": "proto", "rule": "iana_protocol_number_to_lowercase_name", "vocabularySource": "active_model_preprocessing" },
    { "name": "service", "rule": "serviceRules", "vocabularySource": "active_model_preprocessing" }
  ],
  "removedFromV31": ["sttl", "ct_state_ttl", "sloss", "sjit", "djit", "dinpkt", "ct_flw_http_mthd"],
  "serviceRules": { "basis": "responder_port", "portMap": { "tcp/80": "http", "udp/53": "dns" }, "default": "-" },
  "flowClosure": { "tcpIdleSeconds": 60, "udpIdleSeconds": 30, "maxLifetimeSeconds": 60 },
  "goldenFixtures": { "path": "feature-contract/fixtures/unsw-nb15-flow-v4/", "sha256": "<目录清单哈希>" },
  "onlineEnabled": false,
  "onlineGateEvidence": { "fixtureReport": "<golden fixture 比对报告路径与 SHA-256>" }
}
```

约定：

1. 字段顺序即 ONNX `flow_numeric` 的列顺序，必须与 manifest `feature_contract.inputs` 逐项一致。
2. 每个数值字段带 `unit` 和 `unitVerified`；任一必需字段 `unitVerified=false` 时，契约加载成功但 `onlineEnabled` 不得为 `true`。
3. 契约文件发布后不可变，不能事后原位把 `onlineEnabled` 从 `false` 改为 `true`（否则会重演 v3.1 的问题）。因此 v4 契约文件只在阶段 3 的 golden fixtures 全部通过后才首次入库，届时 `onlineEnabled=true` 的含义限定为“契约本身可用于在线特征构造”。某个传感器能否真正上线，由既有的三道运行时门控制：传感器配置已批准且绑定 v4、模型已激活且契约一致、部署模式为 `shadow` 或正式。阶段 6 一致性验证通过前，不批准任何绑定 v4 的真实传感器配置。上面草案中的 `false` 仅表示阶段 1～2 的工作稿状态，不入库。
4. 契约只规定类别字段的**识别规则**；**词表**属于模型，由激活模型交付包中的 `preprocessing.json` 提供，加载时核对哈希（见 §4.4）。Java 中不再硬编码词表。
5. 契约文件本身的 SHA-256 登记在 manifest 与数据库契约快照引用中，运行时加载后比对。

### 3.2 契约与模型的绑定规则

- 推理前必须同时满足：激活模型 manifest 的 `feature_contract.version` = 记录的 `feature_contract_version` = 传感器已批准配置的 `feature_contract_version`。任一不一致直接拒绝，写 `inference_request.status=rejected` 并附稳定错误码，不切换模型。
- v3.1 记录只允许进入离线回放路径，在线接入仍按现状 fail-closed。
- 同时存在 v3.1 与 v4 两个已登记模型时，激活互斥规则沿用现有部署台账，不新增“按契约自动选模型”的逻辑。

### 3.3 数据库影响评估

- `sensor_config.feature_contract_version`、`ingest_batch.feature_contract_version`、`inference_request.contract_version` 都是 `VARCHAR(64)`，没有版本枚举约束，v4 可直接写入，不需要为“允许 v4”单独做 schema 迁移。
- `docs/项目待开发模块文档.md` M1 第 4 步写的“迁移 V9：`source_mapping` 允许绑定契约 v3.2”已过期：V9 已被 `V9__query_supporting_indexes.sql` 占用，V10 为 M2 消费台账，且 `source_mapping` 当前没有契约列。
- 已决定执行迁移 `V11`（§19.1）：为 `source_mapping` 与 `sensor_config` 追加 `feature_contract_sha256`，让“映射 ↔ 契约版本 ↔ 契约哈希”成为数据库级约束，便于审计。只向前追加，不改历史数据；须在 MySQL 8 上验证顺序与兼容性。

## 4. 特征可移植性初判

本节先给出分类框架（§4 表），再用训练端已有实测数据佐证（§4.1），然后给出字段裁决（§4.2）和传感器实现决策（§4.3）。§4.2、§4.3 是定案，阶段 1 只做验证，不重新讨论取舍。

下表基于 `preprocessing.json` 字段说明、训练计划 EDA 结论和 UNSW-NB15 公开特征说明。

分类定义：

- A：可移植。定义清晰，单主机传感器能按同一公式复现。
- B：环境依赖。取值主要反映 UNSW 靶场拓扑或主机配置，真实网络不可移植，v4 删除。
- C：可计算但定义有歧义。需要在规格中写死算法（通常是 Argus 的具体实现细节），并用 golden fixture 证明一致，否则删除。
- D：观测点依赖。能算，但 UNSW 是网络级观测点，单主机传感器只能看到本机流量，统计分布会系统性偏移。

| # | 字段 | 单位 | 初判 | 说明与待核实点 |
|---:|---|---|---|---|
| 0 | `dur` | 秒 | A | 流首包到末包时间；需写死封流规则（空闲超时、FIN/RST） |
| 1 | `sbytes` | 字节 | A | 需明确按 IP 总长还是传输层载荷计 |
| 2 | `dbytes` | 字节 | A | 同上 |
| 3 | `sttl` | 跳数 | B | 靶场环境特征，删除 |
| 4 | `sload` | 比特/秒 | A（待核） | 需确认公式（是否为 `sbytes*8/dur`、`dur=0` 的处理） |
| 5 | `dload` | 比特/秒 | A（待核） | 同上 |
| 6 | `sloss` | 包 | C | Argus 基于 TCP 序号判定重传/丢包，非 TCP 语义需明确 |
| 7 | `dinpkt` | 毫秒 | C | 需确认是均值还是其他统计量、单包流取值 |
| 8 | `sjit` | 毫秒 | C | Argus 抖动算法细节需写死 |
| 9 | `djit` | 毫秒 | C | 同上 |
| 10 | `tcprtt` | 秒 | C | 仅 TCP 三次握手可得；非 TCP 或握手不完整时的取值需明确 |
| 11 | `ackdat` | 秒 | C | 同上 |
| 12 | `smean` | 字节 | A | 需与 `sbytes` 口径一致 |
| 13 | `dmean` | 字节 | A | 同上 |
| 14 | `ct_srv_src` | 计数 | D | 最近 100 条连接窗口 |
| 15 | `ct_state_ttl` | 计数 | B | 依赖 TTL，删除 |
| 16 | `ct_dst_ltm` | 计数 | D | 同窗口 |
| 17 | `ct_src_dport_ltm` | 计数 | D | 同窗口 |
| 18 | `ct_dst_sport_ltm` | 计数 | D | 同窗口 |
| 19 | `ct_dst_src_ltm` | 计数 | D | 同窗口 |
| 20 | `ct_flw_http_mthd` | 计数 | C | 需解析 HTTP 请求行；HTTPS 下不可得，v3.1 中为 nullable |
| 21 | `ct_src_ltm` | 计数 | D | 主机视角下，出站流的源地址几乎总是本机，取值可能长期接近 100 |
| 22 | `ct_srv_dst` | 计数 | D | 同窗口 |
| 23 | `spkts` | 包 | A | |
| 24 | `dpkts` | 包 | A | |
| 25 | `synack` | 秒 | C | 同 `tcprtt` |
| — | `proto` | 类别 | A | 词表来自训练集；需约定协议号到名称的映射 |
| — | `service` | 类别 | C | UNSW 由 Bro 协议识别得到，`-` 表示未识别；传感器若只按端口识别会产生分布偏移 |

两点关键判断：

1. D 类是比 TTL 更隐蔽的风险。UNSW 的 `ct_*` 是在整个靶场出口观测点上、跨所有主机统计的；单主机传感器的窗口里只有本机流量。训练端须用自己的参考实现，在原始数据上按“单主机视角”重新计算 `ct_*`（按每个端点分组后各自取最近 100 条），再和 CSV 自带列对比。这样训练特征和线上特征由同一份规格、同一类实现产生。
2. C 类能否保留，取决于能否拿到“原始包 → 特征”的对照证据。当前训练只用 Kaggle CSV，没有 UNSW 原始 pcap，无法验证 Argus 的 jitter、loss 等实现细节。本路线的处理方式见 §4.2 的 C 类裁决。

| Macro-F1 | 0.9314 | 0.9336 | +0.0022 |
| PR-AUC | 0.9609 | 0.9616 | +0.0007 |
| F1（攻击类） | 0.8680 | 0.8723 | +0.0043 |
| Precision | 0.8471 | 0.8602 | +0.0131 |
| Recall | 0.8901 | 0.8846 | −0.0055 |
| FNR | 10.99% | 11.54% | +0.55pp |
| FPR | 0.63% | 0.56% | −0.07pp |

V4 = V3 去掉 `sttl`、`dttl`、`ct_state_ttl`。同一 run 的 `v2-importance.csv` 中，`sttl` 的 LightGBM gain 为 473,396、`ct_state_ttl` 为 397,485，而第三名 `sbytes` 仅 15,513。

结论：TTL 类特征是**分裂捷径**而非**信息来源**。树模型极度偏好它们（gain 高出一个数量级），但删除后综合指标不降反升，说明其余特征已携带足够的可区分信息。这从数据上支持路线 B——删掉捷径后，模型被迫使用可移植特征，泛化结论更可信。

必须同时澄清，这份诊断不能直接当作 v4 的交付结论：

- 它是诊断视图，未走调优、多种子复现、锁定评估；模型为 LightGBM，而交付候选是 XGBoost。
- 它只删了 TTL，未触及 D 类问题（7 个 `ct_*` 仍是 UNSW 网络级观测点的统计量）。
- FNR 11.54% 是固定阈值 0.5 下的值，与训练计划 §1 的 FNR ≤ 5% 门槛不可直接比较。交付模型按训练计划 §7.3 在验证集上重选阈值（`2026.09.0` 选定 0.308）。
- V3/V4 的 30～32 维含图内派生特征；后端契约 v3.1 的 26 个数值字段是原始输入维度。两个数字不可混用。

### 4.2 本路线的字段裁决

基于 §4.1 的实测结论与“规格可实现、可验证”的原则，v4 字段集按下表裁决。阶段 1 只做验证与规格化，不重新讨论取舍。

| 处理 | 字段 | 依据 |
|---|---|---|
| 删除（B 类） | `sttl`、`ct_state_ttl` | §4.1 实测：删除后指标不降；靶场环境特征不可移植 |
| 删除（C 类，不可验证） | `sloss`、`sjit`、`djit`、`dinpkt` | 取值取决于 Argus 内部实现（重传判定、抖动算法、间隔统计口径），无原始 pcap 无法证明一致。传感器自行实现必然与训练数据口径不同，属于静默造值 |
| 保留（C 类，可规格化） | `tcprtt`、`ackdat`、`synack` | 语义由 TCP 握手唯一确定（`synack` = SYN→SYN-ACK，`ackdat` = SYN-ACK→ACK，`tcprtt` = 两者之和），可在规格中写死并用 fixtures 验证。非 TCP 或握手不完整时取 0（与 UNSW 一致，其非 TCP 流这三列为 0） |
| 删除（C 类，需载荷解析） | `ct_flw_http_mthd` | 见 §4.3 决策 D3 |
| 保留（D 类，按单主机视角重算） | 7 个 `ct_*` 计数 | 见 §4.3 决策 D2 |
| 保留（A 类） | `dur`、`sbytes`、`dbytes`、`sload`、`dload`、`smean`、`dmean`、`spkts`、`dpkts`、`proto` | 定义清晰，可复现 |
| 保留（口径重定义） | `service` | 见 §4.3 决策 D4 |

据此，v4 候选原始输入为 **17 个数值字段 + 2 个类别字段**（v3.1 的 26 个数值字段删去 `sttl`、`ct_state_ttl`、`sloss`、`sjit`、`djit`、`dinpkt`、`ct_flw_http_mthd` 七项；2026-09-29 按 §7.0.6、§7.1.1 再删 `ct_dst_sport_ltm`（单主机视角下退化）与 `ct_dst_src_ltm`（与 `ct_src_ltm` 结构等价））：

`dur`、`sbytes`、`dbytes`、`sload`、`dload`、`tcprtt`、`ackdat`、`synack`、`smean`、`dmean`、`spkts`、`dpkts`、`ct_srv_src`、`ct_srv_dst`、`ct_dst_ltm`、`ct_src_ltm`、`ct_src_dport_ltm`；类别字段 `proto`、`service`。

v4 没有可为 null 的数值字段（v3.1 唯一的 nullable 字段 `ct_flw_http_mthd` 已删除），所有边界情况都由确定的取值规则覆盖。

其中 7 个窗口计数为 `ct_srv_src`、`ct_srv_dst`、`ct_dst_ltm`、`ct_src_ltm`、`ct_src_dport_ltm`、`ct_dst_sport_ltm`、`ct_dst_src_ltm`，与后端 `FeatureBuilder` 现有的七个 LTM 计数一一对应。最终字段集在阶段 1 的传感器实测与消融验证后冻结。

`sinpkt`、`dloss`、`swin`、`dwin`、`stcpb`、`dtcpb`、`state`、`trans_depth`、`response_body_len`、`is_ftp_login`、`ct_ftp_cmd`、`is_sm_ips_ports` 等 V0 字段本来就不在 v3.1 契约内，v4 同样不引入。

### 4.3 传感器实现决策（预先定案，不作为待决项）

以下决策直接构成 `docs/特征规格-unsw-nb15-flow-v4.md` 的正文骨架，阶段 1 只做数值验证与文字细化。

**D1：不引入 UNSW 原始 pcap。**
理由：官方 pcap 约 100 GB，来源为 UNSW 研究页面（非 Kaggle），下载与许可需单独核实，且引入后仍需逆向 Argus 实现才能对拍，投入产出比过低。代价是无法验证 Argus 实现细节字段，已通过 §4.2 删除这些字段来消除风险。“包 → 流记录”这一层的正确性改用自有隔离靶场录制的 pcap 验证（阶段 6）。

**D2：`ct_*` 采用单主机视角，由传感器与训练端用同一定义计算。**

- 窗口定义：每个传感器维护自己最近 100 条**已完成**流，按流结束时间（`flowEndAt`）排序，与后端 `FeatureWindow` 完全一致（不足 100 条不推理；迟到与重复记录拒绝）。
- 窗口成员：传感器部署在主机 h 上时，窗口包含 h 作为源或目的的全部已完成流（即本机可见的全部流）。
- 训练端重算视角：每条流以**响应方（`dstip`）主机**为传感器视角计算 7 个计数。理由：部署目标是被保护主机，UNSW 中的攻击均由攻击子网发起、指向受害主机，传感器在受害主机上看到的是入站流。窗口成员按上一条规则，在全时间轴上按 `stime`/`ltime` 排序维护。
- 窗口在切分前的完整时间轴上计算。窗口计数只使用此前流量的元数据，不使用标签，因此验证/测试流的窗口中包含训练流不构成标签泄漏；切分仍按端点组进行，保证同一端点对不跨分区。
- 7 个计数的语义保持 UNSW 原定义不变（例如 `ct_src_ltm` = 窗口内与当前流源地址相同的流数），只改变观测范围。不做语义重定义，避免训练端与传感器对「新语义」理解不一致。
- 单主机视角下部分计数可能退化（例如被保护主机几乎只做服务端时，`ct_dst_ltm` 接近窗口长度）。以 §7.0 实测方差和训练端重算方差共同判定，方差接近 0 的字段从 v4 删除。
- `ct_srv_src`、`ct_srv_dst` 依赖 `service`，按 D4 口径计算。
- 视角字段：每条记录附带元数据 `viewpoint`，取值 `responder`（本机是响应方，即入站）或 `initiator`（本机是发起方，即出站）。窗口成员与视角无关，入站、出站流都进窗口。
- 视角进契约，适用范围进 manifest：`viewpoint` 的定义与取值属于契约，冻结；模型支持哪些视角由 manifest 的 `supported_viewpoints` 声明。首个 v4 模型只用 `responder` 视角训练，声明为 `["responder"]`。出站流照常进入窗口，但不送推理，记录状态为 `not_in_model_scope`（不是拒绝，也不是造值）。
- 以后若用真实数据训练出站模型，只需发布声明 `["responder", "initiator"]` 的新 manifest，契约、传感器、后端 Builder 都不改。

**D3：删除 `ct_flw_http_mthd`，不做 HTTP 内容解析。**

- 该字段是 HTTP 请求方法计数，传感器必须解析 HTTP 请求行才能得到，与 D8「不处理载荷」冲突；HTTPS 流量下也根本不可得。
- 曾考虑降级为二值 `http_like_flow`，但若按 `service == http` 定义，它与 `service` 类别字段完全冗余；若按 `ct_flw_http_mthd > 0` 定义，传感器又无法计算。两种定义都不成立，因此直接删除。
- 删除代价由 §7.1 消融的 F4 组量化。

**D4：`service` 只按响应方端口做固定映射，不读取任何载荷。**

- 规则：取响应方（responder）端口，命中固定映射表则取对应值，否则取 `-`。协议为 TCP 或 UDP 以外时一律取 `-`。
- 映射表固定为 v3.1 词表的 13 个取值：`dhcp`(UDP 67/68)、`dns`(53)、`ftp`(21)、`ftp-data`(20)、`http`(80、8080)、`irc`(6667)、`pop3`(110)、`radius`(UDP 1812/1813)、`smtp`(25)、`snmp`(UDP 161/162)、`ssh`(22)、`ssl`(443)、`-`（其他）。映射表写入契约 `serviceRules.portMap`，随契约冻结。
- 为什么不做载荷指纹：训练端只有 CSV，没有载荷，无法执行指纹规则。只要指纹在传感器端命中过一次，同一条流在训练端和线上就会得到不同的 `service`，恰好违反「训练与线上同一定义」这条底线。纯端口映射在两端可以逐位一致地实现。
- 训练端按同一规则从 CSV 的 `dsport` 与 `proto` 重算，替换 CSV 原有的 Bro 识别值；同时报告重算值与原值的一致率，只作记录，不作为是否采用的条件。
- 代价：跑在非标准端口上的服务会被识别为 `-`，这一点写入能力边界。它对训练和线上是同样的限制，不产生偏差。

**D5：`proto` 统一为 IANA 协议号到小写名称的固定映射，词表随契约版本化。**
未命中词表的协议取值按现有逻辑记为 `CATEGORY_OUT_OF_VOCABULARY` 遥测，由 ONNX 图编码为 -1，不拒绝记录。

**D6：字节与包计数口径。**

- `sbytes`/`dbytes`：按 IP 数据报总长累加（含 IP 头），与 Argus 默认口径一致；不含链路层帧头。
- `spkts`/`dpkts`：按方向的 IP 数据报计数，重传包计入，分片按分片数计。
- `smean`/`dmean`：`round(sbytes/spkts)`、`round(dbytes/dpkts)`，四舍五入到整数字节（§7.1.1：CSV 上 97.6%～98.6% 逐行相等，100% 在 1 字节内）；对应包数为 0 时取 0。
- 该口径须在阶段 1 用 CSV 抽样验证 `smean ≈ sbytes/spkts` 是否成立；不成立则以对拍结果修正规格。

**D7：封流规则。**

- 流键：`(proto, 低端点地址, 低端点端口, 高端点地址, 高端点端口)` 的规范化五元组；方向由首包确定 initiator，后续永不翻转（与后端 `BidirectionalFlowEngine` 一致）。
- 结束条件：TCP 见 FIN 双向完成或 RST 后立即导出；其余情况按空闲超时导出，TCP 空闲 60 秒、UDP 与 ICMP 30 秒；单流最长存活 60 秒后强制切段导出，后续段继承首段方向（UNSW 训练数据的 `dur` 上限即 60 秒，§7.1.1）。
- `dur` = 末包时间 − 首包时间，单位秒，保留微秒精度；单包流 `dur = 0`。
- `sload`/`dload` = `方向字节数 × 8 × (方向包数 − 1) / 方向包数 / dur`，即不计首包，与 Argus 一致（§7.1.1：CSV 上 99.94% 在 1% 误差内）；方向包数 ≤ 1 或 `dur = 0` 时取 0（不取 NaN，避免与图内插补语义混淆）。

**D8：只解析到传输层头部，不读取载荷。**
传感器只解析到传输层头部（IP 头、TCP/UDP 头、TCP 标志位与时间戳），不读取任何载荷字节；内存中只保留流表、最近流窗口与队列所需元数据。BPF 抓包长度（snaplen）设为只覆盖头部的最小值（例如 128 字节），从抓包源头限制载荷进入进程。这一点在阶段 6 的代码评审中逐项核对。

**D9：契约预留扩展位，避免为新增字段重训。**

- v4 契约的 `numericFields` 顺序一经冻结不再变动；新增字段只能追加到末尾，且必须伴随新的模型版本。
- 为降低「发现遗漏字段就得重训」的概率，阶段 1 的探测（§7.0）须一次性确认全部候选字段可采集，而不是边做边发现。
- 传感器上报的批次允许携带契约字段之外的 `diagnostics` 附加块（例如丢包计数、识别命中率、窗口预热状态）。该块不进入模型输入、不参与哈希校验，只写入质量遥测。这样后续需要新指标时无需改契约。

**D10：地址族分窗，契约覆盖 IPv4 与 IPv6，模型范围由 manifest 声明。**

- 背景：本机 en0 同时有多个 IPv6 地址（2026-09-29 核对），而 UNSW 训练数据只有 IPv4。
- 规则：窗口按地址族分开维护，即每个传感器一个 IPv4 窗口、一个 IPv6 窗口，互不混入。这样 IPv4 窗口的 `ct_*` 统计口径与训练端重算口径一致。
- 契约同时定义两种地址族的字段计算方式（例如 `sbytes` 取 IPv6 固定头 40 字节 + 载荷长度），但首个 v4 模型的 manifest 只声明 `supported_address_families: ["ipv4"]`。IPv6 流照常进入 IPv6 窗口并上报，状态记为 `not_in_model_scope`。
- 以后用真实 IPv6 元数据训练出模型，只需发布新 manifest，契约不变。

**D11：卸载分段归一化（TSO/LSO 与 LRO/RSC）。**

- 背景：本机 `net.inet.tcp.tso = 1`（2026-09-29 核对）。开启 TSO 时，BPF 在出站方向看到的是网卡分段前的超大 TCP 包；Windows 的 LSO（出站）和 RSC（入站合并）也有同类问题。训练数据来自线上抓包，是实际上线路的分段。
- 规则：契约口径是「线路上的分段」。IP 总长度超过接口 MTU 的 TCP 包，按 `ceil(TCP 载荷长度 / MSS)` 折算为多个分段，MSS 取该流握手协商值，未观测到握手时取 `MTU − IP 头长 − TCP 头长`。折算后 `spkts` 加上分段数，`sbytes` 加上「载荷 + 分段数 × (IP 头长 + TCP 头长)」。
- 该规则只依赖包头，与平台无关，Windows 可以直接复用，不需要为 Windows 另改契约。
- 不采用「关闭 TSO」方案：那需要修改系统网络配置、会影响主机性能，也不在被动观测的授权范围内。
- 超大包折算的次数写入 `diagnostics`，便于核查。

**D12：排除多播、广播与回环流。**

- 目的地址为多播或广播的流、以及回环接口上的流，不进入窗口、不送推理，只在 `diagnostics` 中计数。
- 理由：这类流没有明确的单播响应方，视角无法定义；UNSW 训练数据中也基本没有。本机局域网发现类流量（mDNS、SSDP 等）会由此排除。
- 抓包只针对授权的物理接口（本机为 en0），不抓 `lo0`、虚拟网桥和 VPN 隧道接口。

**D13：抓包提权方式。**

- 背景：本机 `/dev/bpf*` 权限为 `root:wheel 0600`，且没有 `access_bpf` 组（2026-09-29 核对）。
- 正式传感器：由 launchd 以 root 身份启动一个抓包辅助进程。它只负责打开 BPF 设备、设置过滤器和 snaplen，然后立即降权到专用低权限用户，由该用户完成流聚合与上报。这与 tcpdump `-Z` 的降权方式相同。
- 探测阶段：由用户在终端用 `sudo` 手动运行一次性探测脚本，脚本同样在打开设备后立即降权。不安装 ChmodBPF，也不永久修改 `/dev/bpf*` 权限。
- 适配器（M7 防火墙）与抓包进程分开，不共享权限。

### 4.4 落地性约束：契约只冻结一次

本路线的硬性目标是**契约只定一次**。v4 冻结后，后续用真实网络元数据做的再训练（M8/M9 闭环）都在同一契约下进行，只更换模型权重与 manifest，不改契约、不改后端代码、不改传感器字段计算。

这条区分很重要：

| 允许，且已有既成通道 | 必须避免 |
|---|---|
| 在 v4 契约下用真实数据再训练，发布 `unsw-binary-2026.11.0`、`2027.x` 等新模型版本 | 修订契约字段集或字段语义，产生 v5、v6 |
| 阈值重选、预处理参数重新拟合（都在 manifest 内） | 改窗口定义、封流规则、识别口径 |
| 补充训练数据来源、调整类别权重、换算法 | 新增或删除契约字段 |

再训练走的是既有流程，不触及契约：候选登记 → 制品校验（`ModelArtifactStore` 比对 `feature_contract.version`）→ Java 回放 → 影子验证 → 审批 → 激活。因为契约版本不变，后端的 `FeatureContractRegistry`、`FeatureBuilder`、传感器 `feature` 模块完全不动。这也是 §3.2 那条「契约版本三方一致」门禁的价值所在：它让「换模型」和「改契约」彻底分离。

为此，下列条件必须在契约冻结前（阶段 1 结束前）全部确定，之后不得变更：

| 必须先定 | 为什么不能事后改 |
|---|---|
| 字段集与字段顺序 | 改动即改 ONNX 输入维度，必须重训 |
| 每个字段的计算公式与单位 | 训练数据与线上数据口径不一致，模型失效 |
| 窗口定义（长度、排序、分组视角） | 7 个 `ct_*` 的取值全部改变 |
| 封流规则（超时、结束条件） | 所有流级字段的取值改变 |
| `service`/`proto` 的识别规则（端口映射表、协议号映射） | 同一条流会得到不同类别值，训练与线上不一致 |
| 缺失与边界取值规则（`dur=0`、非 TCP 等） | 图内插补参数由训练分区拟合，改规则即改分布 |
| 标签定义与阈值策略 | 阈值写入 manifest |

契约冻结后可以调整、不需要改契约的部分：

- 模型权重、阈值、预处理拟合参数、类别词表（均在 manifest 与 ONNX 图内，随模型版本发布）；
- 告警分级映射、事件关联窗口、规则引擎规则集（配置化、版本化）；
- 响应策略、动作白名单、TTL 上限；
- 前端展示、查询接口、审计字段；
- 传感器的采集网卡、BPF 过滤、批次大小、队列容量等运行参数；
- `diagnostics` 附加块的内容（见 D9）。

类别词表特别说明：`proto`、`service` 的**识别规则**（D4 的端口映射表、D5 的协议号映射）属于契约，冻结；**词表**（哪些取值被模型见过）属于模型，随 manifest 变化。后端校验器从已激活模型的 `preprocessing.json` 读取词表，而非从契约读取。这样真实数据再训练后出现的新取值，只需换模型即可被模型接纳。

为保证契约一次成型，阶段顺序调整为：**先做传感器可行性探测（§7.0），再冻结规格，再训练**。不按这个顺序，就会在阶段 6 才发现某个字段在真实主机上算不出来，届时唯一出路是改契约。

### 4.5 契约冻结后仍出现问题时的处理

即便做了 §7.0 的探测，仍可能在影子验证中发现个别字段在真实流量上质量差（例如某个 `ct_*` 在某平台长期为常数）。处理原则是**在契约内解决，不改契约**：

| 问题 | 契约内的处理 |
|---|---|
| 某字段在真实流量上几乎无区分度 | 再训练时模型自然降低其权重；字段仍按契约采集上报，不删除 |
| 某字段在某平台偶发不可得 | 契约已规定的边界取值规则生效（如非 TCP 的握手字段取 0）；若规则未覆盖，记录拒绝并上报 `diagnostics`，不静默造值 |
| 真实流量分布与训练集差异大 | 走 M8 漂移监测 → M9 用真实元数据离线再训练，契约不变 |
| 新攻击类型检测不到 | 在 M4 规则引擎中补确定性规则；或在再训练中纳入新标注样本，契约不变 |

只有当某个字段的**计算定义本身被证明错误**（例如公式与传感器实现无法对齐），才允许发布新契约。这被视为缺陷修复而非迭代，必须在 §21 登记根因，并复盘 §7.0 为何没能提前发现。

#### 7.0.4 首个模型的视角：定为 `responder`（入站）

笔记本以出站流为主，按 `responder` 视角训练的首个模型，在本机上能评估的流会很少。仍然选择 `responder`，理由如下：

1. 与响应设计一致：M7 的处置动作是在被保护主机上阻断远端对端地址，针对的正是外部对本机发起的访问。
2. 与 UNSW 的数据结构一致：UNSW 的攻击由攻击子网发起，指向受害服务器；用 `responder` 视角重算 `ct_*` 时，被观测主机就是受害主机，训练样本的语义最清楚。
3. 出站视角（例如主机失陷后对外发起的访问）已在契约中定义（D2）。以后用真实元数据训练出站模型，只需发布新 manifest，不改契约。

能力边界中写明：首个模型只评估入站流；在以出站为主的终端上，模型覆盖的流量比例较低，此时规则研判（M4）是主要的检测手段。

**对规格的影响（阶段 1 冻结前须写入规格）**：

1. `ct_dst_sport_ltm`：若 G1 决定删除，契约为 18 数值 + 2 类别；若训练端证明其在重算口径下仍有区分度，则保留，并在能力边界中写明「终端视角下近似常数」。
2. 视角判定：「方向由首包确定」会把本机出站长连接的片段（空闲超时后恢复、抓包前已建立，看不到 SYN）错判成入站。对入站模型，这会让不以 SYN 开始的 TCP 段混进评估范围。建议规格补一条：TCP 流的 initiator 在能看到握手时取 SYN 发送方；最长存活切出的后续段继承首段方向（探测脚本已实现，但 34% 的后续段仍被判为入站，说明首段本身已错判）；空闲超时后恢复或抓包前已建立、看不到 SYN 的连接，按首包确定方向，并在记录元数据标记 `handshake_seen=false`，由模型评估范围决定是否排除。这是在现有字段集内的规格细化，不改字段。
3. D11：本机未出现超大包，折算规则的真实验证推迟到 Windows 补测（§7.0.5）。

**能力边界（写入规格与 README）**：探测期间本机以出站流量为主，没有真实入站 TCP 连接；首个 `responder` 模型在这台 Mac 上的影子验证样本会非常少（§7.0.4 已预判），阶段 7 需准备入站场景（例如在授权靶场中对本机服务发起的访问），否则 G3 无法评估。

- 直接加目的主机编码反而比 F2 低（0.9253）。重算值只保留主机层面信息（主机均值）或只保留每台主机的取值分布（组内置换）时，提升全部消失，回到「去掉全部 `ct_*`」的水平（0.9288 ≈ 0.9285）。

- 残余风险（写入能力边界）：计数信号的强度取决于攻击流量的突发程度。UNSW 攻击由 IXIA 工具集中生成，真实环境中低频、分散的攻击会让这几项 `ct_*` 的贡献明显变小。
- 泛化对照（D1 训练、阈值 0.5、只作报告）：D2 验证上含 TTL Macro-F1 0.512 / AUC 0.681，不含 TTL 0.316 / 0.547。两者都接近不可用，跨数据集结论意义有限；去 TTL 并未改善对 D2 的迁移，如实记录。

**影子报告口径**（报告版本 `shadow-report-v1`，阈值版本 `g3-2026-09-29`）

- 时间：批次按 `ingest_batch.started_at`，告警按 `detected_at`，均为 UTC；自然日与工作日按请求时区划分（本机报告用 `Asia/Shanghai`），只按周六、周日区分，未考虑法定节假日调休。
- 运行时长与覆盖：覆盖取传感器健康窗口，相邻窗口间隔 > 5 分钟记为停机段。观测日 = 当天覆盖 ≥ 12 小时。范围 ≥ 7 天、覆盖率 ≥ 90%、工作日与非工作日各有观测日时判定通过；不足 7 天为 `pending`，其余不满足为 `not_evaluable`（其他指标的样本不代表完整一周）。
- 告警量：均值 = 模型告警数 / (传感器数 × 覆盖天数)，单日最大按自然日。
- 人工抽检：模型告警不超过 20 条时全部复核；超过时按 SHA-256(`alert_key`) 升序确定性抽取 max(20, ⌈10%⌉) 条，可复现。误报率只按抽检样本中的有效标注（待复核或已批准）计算，样本未全部标注前为 `pending`。
- 模型范围内误报流比例：判为 `Attack` 的推理成功流 / 推理成功流。
- 契约拒绝率：(接入拒绝 + 推理契约拒绝) / 全部上报记录。分母含模型范围外记录；传感器不上报预热期记录。无激活模型、超时等运行故障单列，不计入。
- PSI：报告按范围内全部推理成功记录重算整段分布，不依赖小时窗口。只合并使用同一 ONNX 制品（`artifact_sha256`）的模型版本，基线取该制品下最新带基线的版本；混用不同制品时 `not_evaluable`。样本 < 200 为 `not_evaluable`。
- 延迟：批次 `started_at` → 该批最后一条推理完成，只计含推理成功记录的批次，最近秩分位。
- 死信：outbox `dead_letter` 或消费台账 `dead_lettered`。
- 结论：任一项 `fail` 为未通过；否则任一项 `pending/not_evaluable` 为未完成；全部通过才为通过。

#### 13.8.1 第一轮结论：提前判定不通过

第一轮影子验证（模型 `2026.10.1`，本机数据源 #2，北京时间 9 月 30 日 16:02 起）提前判定 **G3 不通过**，不再等到 10 月 14 日。截至北京时间 9 月 30 日约 19:00 的影子报告：

提前结束的依据：首日单日告警已是任一天上限（30 条）的 3 倍，误报流比例是阈值的约 60 倍，剩余 13 天无论流量如何变化，7 天均值和逐日上限都不可能再满足。继续等待只会推迟修正。

已查明的原因（§13.6 与 §13.7 实验）：

1. **评估口径**：本机模型范围内的 TCP 流几乎全是没抓到握手的片段（`handshakeSeen=false`），方向由首包推断，其中大量是本机外连被判成入站。这类流在训练集只占约 0.4%。`FeatureContractModelGate` 只按视角和地址族划范围，不读 `handshakeSeen`，这些片段照样送去推理。
2. **模型泛化缺陷**：单包 UDP 应答（约 72 字节进、450–480 字节出）在两台主机上都被稳定判为攻击（p 约 0.6–0.77）。UNSW-NB15 的正常流量没有覆盖这类流量，收窄范围解决不了，需要再训练。
3. **正面证据（初步）**：§13.7 受控实验中，实现者生成的握手完整的正常入站 TCP，攻击概率均低于 0.09，未见误报。样本少，以 §13.7 实验报告为准。

#### 13.8.2 第二轮影子验证的设计

用户平时不使用局域网 Intel Mac，那里没有真实业务入站流量；本机 Mac 真实流量多，但几乎没有入站连接。第二轮因此由两个来源合并评估，各自回答不同的问题：

| 来源 | 流量 | 回答的问题 |
|---|---|---|
| 本机 Mac（传感器 #2） | 真实流量，被动抓取 | 真实主机上的告警量、PSI、工程指标 |
| 局域网 Intel Mac（传感器 #3） | 实现者生成、带场景标注的受控流量（良性 + 轻微攻击特征，同 §13.7） | 已知真值下的误报流比例、对攻击特征的反应 |

- **模型版本 `2026.10.2`**：权重与 `2026.10.1` 相同；manifest 评估范围收窄为 `responder` + IPv4 + TCP + `handshakeSeen=true`。UDP、ICMP、无握手片段标为 `not_in_model_scope`，由规则引擎覆盖。门禁代码改为读取 `handshakeSeen`，不改契约。

### 19.3 G1 未达门槛时的处理（Q2 定案）

按 §7.1 的消融结果分三种情况，依次判断：

1. **F5 与门槛差距 ≤ 0.02（Macro-F1），或只有 FNR/FPR 其中一项略超**：进入阶段 2，在调优中解决（只看验证集）。允许的手段：超参搜索、类别权重、阈值策略。不允许的手段：恢复任何已删除字段。
2. **调优后仍未达门槛，且落差主要来自 F2→F3（`ct_*` 口径变化）**：说明原模型的能力依赖网络级观测点。处理方式：
   - 门槛按「F0 与 F5 在验证集上的实测落差」有依据地下调，但不得低于下列底线：Macro-F1 ≥ 0.85、FNR ≤ 10%、FPR ≤ 2%、PR-AUC ≥ 0.85；
   - 修订后的门槛在读取 holdout 之前写入 §21，读取 holdout 之后不得再改；
   - 能力边界中写明「单主机视角下的判别力低于公开数据集的报告值」，并给出 F0 与 F5 的对比；
   - M4 规则引擎的规则集按 §11 加强，作为入站检测的主要补充。
3. **连底线都达不到**：停止交付该模型，不进入阶段 2 的锁定评估。此时 R1 只用规则引擎演示检测闭环，模型部分回到训练端重新设计（例如换算法或调整窗口长度，窗口长度仍可改，因为规格尚未冻结），并在 §21 记录。

无论哪种情况，都不得通过恢复 TTL、CSV 原始 `ct_*` 或其他不可移植特征来凑指标。
