# 远端 Linux 持续采集传感器任务单（RS，BE-23）

更新于 2026-10-21。状态：**R0 已完成（只读勘察），B2 已预演（构建与测试通过，见 B2），其余待开始**；D-R1—D-R4 已由用户同意，前提见下方“硬前提”。本单不构成授权；标“需授权”的卡片按第 8 节逐项申请，一次批准只覆盖对应卡片或运行号。

## 0. 目标与口径

**目标**：在用户自有的远端 Ubuntu 服务器上**持续运行**传感器（开机自启、异常自动恢复），采集该主机的全部入站 TCP，经 mTLS 上传到本机后端。后端用 r6′ 只告警组合产生观察、推理、规则事实与告警，在控制台可见。

**范围**：
- **只采集、只告警**。不开发 Linux 执行器，不登记任何执行能力，不做拦截。真实拦截要等模型训练完善后，另行开发 Linux 执行器、完成验收并重新授权，不在本单范围。
- 远端主机按**真实资产**登记：`platform=linux`、`environment=authorized`、采集范围 `all_inbound_tcp`。组合复用 Mac 真实资产当前使用的 r6′，不新建策略，不改模型、阈值和规则。
- 公网流量上的模型结果只是现场观察，**不作为准确率、误报率或 G1—G3 证据**。已知风险：外网背景扫描是 L2 误报的主要来源，CIC 训练分布与公网差异大，预计会有大量告警或 `MODEL_NOT_APPLICABLE`。

**只新增，不修改既有 Mac 链路**：
- 以下内容一律不改：`sensor/` 的 Go 源码、`scripts/p8/`（`sensor_service.py`、`enroll.py`、`status.py`、`observer_executor.py`、`launchd.py`、`capture_permission.sh`）、`executor/`、后端 `ManagedSensorLifecycle` 与机器接口、Mac 的常驻服务配置、en0 传感器的二进制与配置。
- Linux 部分全部是新文件，放在新目录 `scripts/linux/`。远端使用的 `guardlive` 是**同一份 Go 源码**在 Ubuntu 上的 cgo 构建，`sensor_service.py` 和 `observer_executor.py` 原样复用。
- 只有两处既有代码不得不动（用户 2026-10-21 均已确认接受）。第一处是 A1：后端登记资产、传感器、执行器时只接受 `macos`、`windows`，Linux 无法登记，而又不能把 Linux 冒充成 macOS 登记。A1 只在允许值中**追加** `linux`，macOS 与 Windows 的处理逻辑不变；能力登记和自动化资格仍然只接受 `macos`/`windows`，保证 Linux 资产拿不到拦截能力。前端只补一个平台显示名。
- 第二处是 A0：`sensor/go.mod`、`go.sum` 追加间接依赖 `golang.org/x/net v0.55.0`。gopacket 的 `pcapgo` 有一个只在 Linux 下编译的文件依赖 `x/net/bpf`，现有 `go.sum` 缺这一项，Linux 上无法编译。补上后 Mac 的 `guardlive` 二进制 SHA-256 不变（B2 预演已核对）。Go 源码仍然一行不改。
- 后端需要发布一次含 A1 的版本，并信任远端的 IPC CA，合计重启常驻后端一次（B3）。Mac 传感器的二进制、配置和授权不变，不需要重新审批。

**硬前提：不得影响远端现有 NewAPI 服务**（用户 2026-10-21 同意 D-R2、D-R3 时提出，优先于本单其他所有要求）：
- 不重启、不重载、不修改 `newapi`、`nginx`、`mysql`、`ssh` 服务及其配置；不改 ufw/nftables、sysctl、网卡 offload；不执行 `apt upgrade`，不整机重启。
- 远端不编译、不跑测试（见 B2），只安装运行时库 `libpcap0.8t64` 及其依赖（清单见 B1）。
- 传感器与观察执行器都以受限 systemd 单元运行，有内存、CPU、IO 上限，且 OOM 时优先被杀（见 A4）；托管进程在主机可用内存过低时自行停止（见 A2）。
- 采集是被动的（libpcap、非混杂模式、内核 BPF 过滤），不注入、不修改、不延迟任何报文。
- 每次远端变更前后都核对 NewAPI 基线（见 B1）；任何可见影响都立即停止传感器（第 7 节），不以“继续观察”为由保留。

**R0 勘察结论**（2026-10-21，只读；完整报告在 Mac 私有目录 `remote-sensor/r0-survey-20261021.md`，主机地址不写入仓库）：
- Ubuntu 24.04.1 LTS，x86_64，2 vCPU，内存约 2 GB（可用约 1 GB），**无 swap**；磁盘可用约 52 GB；NTP 已同步。
- 唯一业务接口 `ens17`，IPv4 是私网地址，公网地址由云厂商 NAT 映射；没有全局 IPv6，因此只登记 IPv4 不留 IPv6 盲区。TSO/GSO/GRO 开启，预计 `offloadSuspected` 标记偏多，只记录不修改。
- 对外只有 ufw 放行的 22、80、443；NewAPI 监听 3000，由 nginx 经回环代理，回环流量不在采集范围。远端 `127.0.0.1:18082` 空闲。
- 入站负载很低：60 秒内新增入站连接 22 条（约 0.37 条/秒），开机以来均值约 0.24 条/秒。
- 资源：mysqld 约 545 MB、new-api 约 110 MB（单元 `MemoryMax` 约 1.07 GiB）。Mac 上 `guardlive` 参照值约 108 MB RSS、CPU 2.6%。
- sshd 允许 TCP 转发，未全局限制监听地址，因此按公钥限制 `permitlisten` 可行，不需要改 sshd 全局配置。
- 远端没有 Go 和 libpcap，已有 Python 3.12、`python3-venv`、`ethtool`；`cybersensor`、`cybertunnel` 用户不存在。
- r6′ 经 API 只读确认：组合 `d89e7b99-ea61-40b1-b376-dbb90f004ef6`（authorized、active、revision 4），`subjectSha256` 为 `9eacff2a9945dfbc150dc9fd5753bbe88897e6401d823c90f84aecf2723fba91`，策略 `68a57070-df9f-51fe-9837-daa0858f68c1`（alert_only、reviewed）。Mac 真实资产绑定 `54dd1707-d7f9-4ce7-8a9d-8f4955f4546a`（active、revision 1），作为 A3 巡检“Mac 绑定不变”的基准。
- 另记一处差异，只记录不修改：Mac 观察执行器配置中的 `bundleIds` 仍是 r6 `aa35ae6e…`。

## 1. 设计依据（代码事实）

| # | 事实 | 采用的做法 |
|---|---|---|
| F1 | `guardlive` 的持续模式（`-duration 0`）要求一个真实的直接父进程通过 `-parent-pid` 托管（[managed.go](../../sensor/cmd/guardlive/managed.go)）。Mac 上这个父进程是后端（`ManagedSensorLifecycle` → `sensor_service.py --parent-pid` → exec `guardlive`） | Linux 上新增一个**常驻托管进程** `scripts/linux/supervisor.py`，由 systemd 拉起，扮演 Mac 后端的父进程角色，原样调用 `sensor_service.py --parent-pid <自身 PID> --backend-url https://127.0.0.1:18082`。`guardlive` 与 `sensor_service.py` 不用改 |
| F2 | `sensor_service.py` 只在 `localAddressSource=interface` 时读接口地址，用的是 `/sbin/ifconfig`，Ubuntu 默认没有 | 远端配置使用静态 `localAddresses`（R0 确认服务器地址固定），不设 `localAddressSource`，因此不会走到 ifconfig。地址变化时由 Linux 托管进程检测并停止，需重新登记配置 |
| F3 | `--backend-url` 和 `observer_executor.py` 都只接受回环 HTTPS（`127.0.0.1`） | 远端通过 **SSH 反向隧道**把服务器的 `127.0.0.1:18082` 转发到 Mac 的 `127.0.0.1:18082`。回环约束和服务端证书的 IP SAN 都不用改，后端也不暴露到网络 |
| F4 | 上传器在连接失败时按退避重试；健康窗口每秒一个，内存队列上限 4096（约 68 分钟），超过就以 `HEALTH_QUEUE_OVERFLOW` 致命退出；观察批次写入按 bootId 隔离的磁盘 spool；`guardlive -drain` 可续传某个 bootId 未确认的批次（[uploader.go](../../sensor/internal/guardup/uploader.go)、[main.go](../../sensor/cmd/guardlive/main.go)） | 隧道或 Mac 离线不超过约 68 分钟时自动补传。更长时间离线，`guardlive` 会退出，托管进程换新 bootId 重启；旧 bootId 的未确认批次在后端可达后用 `-drain` 补传。只在托管进程里实现，不改 Go |
| F5 | 上传遇到不可重试错误（身份、范围、授权）时 `guardlive` 退出，`report.json` 的 `upload.fatalCode` 记录原因 | 托管进程读取 `fatalCode`：属于授权或身份类时停止且不重启（退出码 3，systemd 单元配置 `RestartPreventExitStatus=3`）；其他故障与 Mac 后端一样，30 秒退避后重启 |
| F6 | 后端资产、传感器、执行器登记只接受 `macos`/`windows`（`guard/GuardAdministration.java` 的 `asset()`、`machine()`）；能力登记与 `peer_inbound` 资格只接受 `macos`（`GuardCatalog`、`GuardEligibility`） | A1 只在前者追加 `linux`；后者不动 |
| F7 | `enroll.py` 写死 `platform='macos'` 和旧 r6 组合常量；`status.py` 会检查本机 launchd 与 PF | 新写 `scripts/linux/enroll.py` 与 `scripts/linux/status.py`，调用同一组 v2 接口；旧脚本不动 |
| F8 | 组合激活按资产处理，只挂起**所列资产**原有的 active 绑定（`GuardCatalog.activate`） | 为新资产单独激活 r6′，理论上不影响 Mac 绑定；仍须克隆演练证明（B4） |
| F9 | `all_inbound_tcp` 的 BPF 保留一端为登记地址的全部 TCP，不接受端口白名单（[live.go](../../sensor/internal/hostguard/live.go)） | 远端 22（含隧道）和 443（NewAPI 客户）流量都会被采集，见 D-R2 |
| F10 | `lab_peer_tcp` 才有 `utun` 与 Tailscale 地址限制；采集文件锁已支持 `linux`（[lock_unix.go](../../sensor/cmd/guardlive/lock_unix.go)）；实时采集入口的构建条件是 `cgo` | 在 Linux 容器中装 `libpcap-dev` 后用 cgo 构建。B2 预演发现唯一的平台问题是 `go.sum` 缺 `x/net`，由 A0 解决；其余问题停止并报告，不顺手修改共享代码 |

## 4. A 阶段：代码（离线，不碰服务、业务库和远端）

通用要求：
- 在独立 worktree、分支 `Xyhhh/rs-a` 上开发，每张卡单独提交（中文提交信息），合成一个 PR。
- 除 A0、A1 列出的文件外，只新增 `scripts/linux/` 下的文件和文档。`git diff main -- sensor/ scripts/p8/ executor/` 只允许出现 `sensor/go.mod`、`sensor/go.sum`（A0）和 `sensor/README.md` 的追加段落（A5）。

### A0 `sensor/go.mod`、`go.sum` 追加 `golang.org/x/net` 间接依赖（第二处例外）

- **做法**：在 `sensor/` 下执行 `GOFLAGS=-mod=mod go get golang.org/x/net@v0.55.0`。结果应当只有：`go.mod` 的 `require` 块多一行 `golang.org/x/net v0.55.0 // indirect`（`x/sys` 仍为 v0.45.0），`go.sum` 多两行 `golang.org/x/net v0.55.0` 的 `h1:` 与 `/go.mod h1:`。其他依赖版本有任何变化，停止并报告。
- **验收**：Mac 上用同一 Go 版本，在补丁前后各构建一次 `CGO_ENABLED=1 go build -trimpath -o <out> ./cmd/guardlive`，两个二进制 SHA-256 必须一致（预演值为 `56a6e55b…`，以实际为准，前后一致即可）；`go test ./cmd/guardlive/... ./internal/guardup/... ./internal/hostguard/...` 在 Mac 上通过。
- **禁止**：改任何 `.go` 文件；升级其他依赖；执行 `go mod tidy`（可能改动其他行）。
- Python 测试统一放在 `scripts/linux/test_*.py`，用假进程、假命令和假后端，不打开网卡、不联网。

### A1 后端与前端追加 `linux` 平台值（唯一改动的既有代码）

- **位置**：`backend/.../guard/GuardAdministration.java`（`asset()` 与 `machine()` 中的平台集合）及其测试；`frontend/src/api/v2/assets.ts` 的 `Platform` 类型与 `platformLabel`；`frontend/src/views/assets/DeviceFormDrawer.vue` 的平台选项。
- **做法**：只在允许值中追加 `linux`，前端补 `linux: 'Linux'`。`GuardCatalog`、`GuardEligibility`、`CapabilityFormDrawer.vue` 不动。
- **验收**：
  - 单测：`linux` 资产、传感器、零能力执行器登记成功；`linux` 能力登记返回 `CAPABILITY_NOT_SUPPORTED`；`linux` 资产可激活 `alert_only` 组合，激活非 `alert_only` 组合因缺少能力而失败；既有 macOS/Windows 用例全部不变且通过。
  - 前端执行 `npm run typecheck`。
  - 不需要 Flyway 迁移：资产平台存在 `labels_json` 中，传感器与执行器的 `platform` 列为 `VARCHAR(32)`，没有枚举或 CHECK 约束。如果测试发现其他约束，停止并报告。
- **禁止**：给 Linux 开放任何执行能力或自动化资格；顺手修改其他后端逻辑。

### A2 Linux 托管进程 `scripts/linux/supervisor.py`

职责与 Mac 后端的 `ManagedSensorLifecycle` 对等，并补上远端独有的补传和自检。

1. **启动自检**：`sys.platform == 'linux'`；以 `cybersensor` 运行；配置为 `authorized/all_inbound_tcp`，`allowedInterfaces == [interface]`；授权未过期；没有 `localAddressSource`；接口当前地址集合等于配置中的 `localAddresses`（用 `ip -o addr show dev <接口>` 读取）。任一项不满足就以退出码 2 结束，不重启。
2. **单实例**：在 `<私有根>/ledger/sensor.supervisor.lock` 上加独占文件锁。
3. **补传**：每次启动新采集前，以及运行中每 5 分钟，扫描 `ledger/sensor/<bootId>/` 中有未确认批次的旧 bootId，逐个执行 `guardlive -config <该 boot 的 config.json> -drain -drain-timeout 60s`。补传失败只记日志并留待下次重试，不阻止新采集。
4. **启动采集**：`exec` 链与 Mac 相同：`<venv python> scripts/p8/sensor_service.py --root <私有根> --release <release> --parent-pid <自身 PID> --backend-url https://127.0.0.1:18082`，`stdout`/`stderr` 追加到 `logs/`（0600）。
5. **退出处理**：子进程退出后读取该 bootId 的 `report.json`：
   - `upload.fatalCode` 属于授权或身份类（具体取值由 Codex 从后端机器接口的错误码中列出，写进测试与 README）：托管进程以退出码 3 结束，systemd 不再重启；
   - 地址变化：退出码 2；
   - 其他情况：30 秒后换新 bootId 重启，与 Mac 后端的退避一致。
6. **停止**：收到 SIGTERM 时向子进程转发 SIGTERM，最多等待 8 秒再 SIGKILL，与 Mac 一致。`guardlive` 自带的父进程检查保证托管进程被强杀时采集也会停止。
7. **清理**：已全部确认且超过 7 天的 bootId 目录只保留 `report.json`，删除轨迹与 spool；未确认的一律保留。`ledger` 总量超过配置上限（默认 5 GiB）时停止新采集并以退出码 4 结束（不重启），保留全部数据等待人工处理。
8. **保护主机**：每 10 秒读取 `/proc/meminfo` 的 `MemAvailable`，低于 300 MB 时停止采集并以退出码 5 结束（不重启）；根分区可用空间低于 10 GB 时同样处理。这两项是为了让传感器先于 NewAPI 让出资源。

- **验收**：用假 `guardlive` 和假 `ip` 覆盖：父子 PID 关系与命令行逐项断言；fatalCode 分支的退出码；30 秒退避；SIGTERM 转发与 8 秒超时；补传在有、无未确认批次时的行为；清理只删已确认且过期的目录；超过 `ledger` 上限时退出码 4；可用内存或磁盘低于阈值时退出码 5；单实例锁冲突。
- **禁止**：修改 `sensor_service.py` 或 `guardlive`；在托管进程里放宽父进程、范围或回环约束。

5. **撤销**：在控制台撤销远端授权，确认 `guardlive` 退出、托管进程以退出码 3 结束、systemd 不再重启；记录从撤销到停止的秒数。随后按 D-R4 重新登记授权并手动 `systemctl start`，恢复持续运行。

在系统实施记录新增一节，内容包括 R0 摘要（打码）、提交与哈希、C0—C2 的数字、未验证项与局限。同步本任务单总览表、`docs/任务/后端.md` 的 BE-23 状态、开发路线和[能力与局限说明](../能力与局限说明.md)。以 PR 合入。

## 7. 停止条件与回退

| 情况 | 处理 |
|---|---|
| NewAPI 任何可见影响：服务 PID 或启动时间变化、不可用、错误率或延迟明显上升；或远端 CPU、内存、磁盘异常 | 立即 `systemctl stop cyber-sensor cyber-observer`，报告用户；在用户确认原因前不重新启动 |
| 托管进程因内存或磁盘不足退出（退出码 5） | 保持停止，评估资源上限后再决定 |
| Mac 真实资产任何对象变化（r6′ 绑定、en0 配置、授权） | 停止远端，回到 B3/B4 核对 |
| 远端 18082 监听到非回环地址 | 立即停隧道，检查 `permitlisten` |
| 任一端的防火墙、PF 或 sysctl 出现变化 | 立即停止；只告警运行不应发生 |
| 业务库写入前的备份或恢复核验失败 | 不进入写操作 |
| 上传被拒或身份错误 | 托管进程已停止（退出码 3），先分析，不换凭据重试 |
| `ledger` 超上限（退出码 4），或业务库增长超出 R0 预留 | 保持停止，重新评估范围与容量 |
| 模型大量告警或不适用 | 不停止，如实记录 |

| 对象 | 回退方式 |
|---|---|
| 远端运行 | `systemctl disable --now cyber-sensor cyber-observer`；证据先拷回 Mac |
| B1 远端改动 | 按变更清单删除单元文件、两个系统用户和私有根，卸载 `libpcap0.8t64`、`libibverbs1`、`libnl-route-3-200`（同样暂停 needrestart）；`libnl-3-200`、`libnl-genl-3-200` 的小版本升级不回退；回退后复测 NewAPI 基线 |
| B3 服务变更 | 恢复原 `deploy.properties` 和原 release，然后重启 |
| B4 业务库对象 | 不删除；撤销授权、挂起绑定、吊销机器凭据，保留审计事实 |
| B6 隧道 | `launchctl bootout` 删除 LaunchAgent，删除远端公钥 |

## 8. 授权清单与交接格式

| 授权 | 覆盖卡片 | 用户需要做的事 |
|---|---|---|
