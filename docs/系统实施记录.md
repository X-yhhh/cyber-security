### 3.1 P4 本地实现与验证（2026-10-07）

JDK 25 下的 v2 控制面和机器接口、机器身份与范围校验、不可变观察/推理/规则/决策/案件事实、策略和发布组合、稳定目标预算、撤销、命令领取与回执/核对台账。episode 与选中快照是可变投影，替换留追加审计。`V19`—`V21` 已在隔离 MySQL 8 schema 验证，含 V20→V21 升级与账号哈希保留；本机业务库也已完成该升级，本机 RabbitMQ 专用测试 vhost 验证通过，服务尚未切换。

## 5. 传感器

代码在 `sensor/`（Go 版本以 `sensor/go.mod` 为准）。改动 `sensor/internal/hostguard` 后必须重编译 `guardtargets`，否则执行器的 mTLS 测试会返回 403。

| 编号 | 工作 | 现状 | 要点 |
|---|---|---|---|
| S1 | 全部入站 TCP 范围 | `internal/hostguard/live.go` 的 Scope 只绑定单个 `servicePort` 加登记对端 | 新增“本机全部入站 TCP”范围，BPF 只捕获目的为本机登记地址的入站 TCP；仍只观测授权接口 |
| S2 | 1 倍速文件回放 | `-replay` 只能重放自己录下的头部轨迹 | 读取冻结 PCAP，时间只平移一次，保持包间隔；原事件时间与墙钟分开记录；只读文件，不向网卡注入报文 |
| S3 | v2 观察上传 | `guardlive` 环境写死为 research，只写本地 JSONL | 用 sensor 机器身份经 mTLS 上传到 `/api/v2/machine/sensors/{id}/observation-batches`；支持 research、lab、authorized 环境；序号、去重和重试遵守接口设计 |
| S4 | 健康窗口 | `scripts/p3/capture_health_observer.py` 只是面向 Npcap 回环的 L3 原型 | 在 Go 侧实现 `host-guard-capture-health/1.0.0` 窗口（≤5 秒，计数单调，未知填 null），上报 `health-windows` |

**验收**：用冻结 PCAP 片段做双端复算，观测与 `guardextract` 离线结果逐字段一致；上传中断后重连不丢不重；Go 测试与契约检查（`python3 -B scripts/p2/validate_contracts.py`）通过。

## 6. P7 联合闭环

### 6.1 J1 V3 回放演练的定义（R7）

**做法**

1. 从 validation 时段的 CIC PCAP 按类截取只含攻击来源的片段，每类至少 3 段，dos_slow 按 R4 收窄定义选取；再配正常片段，累计 ≥ 30 分钟。不使用 test。片段清单和哈希在回放前登记，回放后不得增删或替换片段。
2. 传感器（S2/S3）按 1 倍速读文件 → 后端真实模型（T7 交付包经 B3 导入）→ 规则 → 决策。环境为 research，执行器不接入。
3. **离线参照**：同一批片段先用 `guardextract` 离线提取，再用同一 ONNX 和同一策略离线计算告警与 `block_candidate`，作为回放结果的比对基准。
4. 只看告警、来源汇总、时延和假想封禁候选，不发封禁命令。
5. R5：同时测量洪泛和慢速来源在 10 秒证据期内能否凑够 `minDistinctFlows` 个质量合格连接。如需关闭 TSO 等系统配置，须另行授权并准备恢复步骤；不放宽 `offloadSuspected` 规则。
6. R3：按冻结策略实测纯 prefix、prefix/final 混组和同 parent 从 prefix 更新为 final，记录告警、候选拒绝原因及覆盖。离线参照须复现最新快照替换与整组 capability 拒绝，不能用 prefix-only 机会报告代替；G3 同步核验这些情形，并补测领取时快照更新，报告实际影响。

**通过标准**

整体项（任一不满足，J1 不通过）：

| 编号 | 项目 | 标准 |
|---|---|---|
| J1-1 | 链路一致性 | 回放观察与离线提取逐字段一致；上传序号连续，丢失 0、重复入库 0；推理失败（`MODEL_*` 错误）0 条，每条观察都有推理结果或明确的 `not_applicable` 记录 |
| J1-2 | 判定一致性 | 回放的连接级告警与离线参照一致率 ≥ 99%；每处不一致都要定位到具体原因（证据过期、到达顺序等时间因素），不能解释的差异视为缺陷 |
| J1-3 | 正常场景 | 正常片段的连接误报率 ≤ 2%（与 G1 同口径）；假想封禁候选折算 ≤ 1 次/小时（与 G3 第 3 项同口径） |
| J1-4 | 来源汇总 | 攻击片段的告警全部汇总到该片段的攻击来源；不出现把正常来源并入攻击 episode 的情况 |
| J1-5 | 运行开销 | 1 倍速下无持续积压（回放结束后 30 秒内队列归零）；观察产生到决策落库 P95 ≤ 2 秒；推理超时 0；无 `capacityDrop` |
| J1-6 | 安全 | 动作命令表新增 0 条；不产生任何 OS 规则 |
| J1-7 | 可复现 | 同一片段集重放一次，告警集合与类别结果一致 |

分类项（逐类判定）：

| 编号 | 项目 | 标准 |
|---|---|---|
| J1-8 | 告警 | 该类每段片段都对攻击来源产生告警，首次告警类别正确（模型或规则来源均可）。首次类别按该来源合资格路径的首个告警批次判定：低精度只告警规则（如 `brute-starts`）的错类早报保留记录，但不计为首次类别（2026-10-11 用户授权执行方选定读法，v8 起适用） |
| J1-9 | 告警时延 | 攻击起点 → 首次告警：port_scan、dos_flood ≤ 10 秒；brute_force、dos_slow ≤ 20 秒，每段都满足。带上下文预热的片段以评分窗口首包为攻击起点，预热期触发的判定不计入 J1-8—J1-10（2026-10-11 用户决策，v9 起适用） |
| J1-10 | 自动准备度 | 每段片段都在 J1-9 的时延内对攻击来源产生假想 `block_candidate`；洪泛和慢速片段的质量合格快照比例同时报告（R5） |

**判定**

- J1-1 到 J1-7 全部满足，且四类都满足 J1-8、J1-9，J1 才算通过，可以进入 J2。G3 第 1 项要求四类都告警，J1 是它的预演。
- 满足 J1-10 的类别列为“计划 M2 自动封禁”；不满足的类别先按下面的退回规则查根因，查明后仍不满足才在 G3 中按只告警处理，并写明原因。计划 M2 的类别数低于保底线时，先执行[开发路线第 5 节](开发路线.md#5-交付目标与保底线)的保底分支，再进入 J2。
- 退回规则：链路或提取不一致回 S；推理、规则、决策或汇总问题回 B；某类告警或类别错误回 T（只能在 validation 上查，不能针对 J1 片段调阈值，否则这些片段不能再用于 G3）；质量覆盖不足按 R5 处理。
- 结果写入受控 run 目录，报告绑定片段清单、交付包、策略、传感器与后端版本的哈希。
