### 2.1 P1R-5：只告警形态的 D2 重启验收

本次 D2 对象是五个用户 LaunchAgent（`backend/targets/recovery/executor/sensor`），没有 PF executor/recovery LaunchDaemon。验收时点为**整机重启并由原用户登录后**；重载服务、换 PID 或重启应用均不能代替整机重启。系统域 PF 模式的“先清旧规则再收新命令”继续适用原恢复流程，本次 observer 不领取命令，不能据此声明该 PF 恢复能力通过。

| 检查 | 本部署形态的通过条件 |
|---|---|
| 主机与启动 | 重启前后绑定同一本机；`kern.bootsessionuuid` 改变，`kern.boottime` 晚于重启前封存时刻；保存实际启动时间与证据摘要 |
| 服务自动恢复 | 五个定义完整且与重启前封存字节一致；登录后 backend、targets、recovery、executor 自动运行，PID、程序路径与发布摘要对应；验收器不得 bootstrap/kickstart 这些服务掩盖失败 |
| sensor 不续采 | 定义保持 `RunAtLoad=false/KeepAlive=false`，登录后未运行、`runs=0`；没有新采集子进程、boot/spool、观察批次或现场心跳/健康窗口。保留已撤销授权与 suspended 绑定，不延长采集期限 |
| observer | 配套部署 P1R-3 recovery/run 后，两个新鲜脉冲的身份和 PID 与 launchd 一致；进程 bootId 均改变，后端唯一 observer 的 bootId 与 run 相同且心跳新鲜。只证明存活，后端原始 unknown 与 PF 未检查状态照实保留 |
| 后端与依赖 | 原 JDK 25、JAR、托管前端和外部配置摘要不变；仅监听回环 18082，私有 CA 验证的 TLS 1.3、live/ready/actuator 均通过，MySQL/RabbitMQ 就绪；relay/consumer 开启，automation 关闭 |
| 无旧规则 | 重启前后分别以系统授权只读核对 PF 状态、根/Apple/用户/hostguard 锚点及 lab 回环别名；没有本项目残留规则、PF 账本或 root 执行器，也不安装 PF 守护进程、不启用 PF、不新建阻断 |
| 数据与恢复 | 保留精确恢复证明及原生效/生成 plist；admin、凭据、权限、模型/阈值/策略/组合、Flyway 与已有业务事实不变。仅允许启动审计、登录会话、observer 心跳/幂等等运行投影变化；真实资产命令仍为 0 |

重启前封存私有证据、程序与配置摘要、数据库备份及恢复入口，准备一次性登录验收器，先验证其当前 boot 下不会误判通过。验收器只读等待依赖，不启动采集、不修正服务状态；失败留下日志和待验收状态，不自动回退业务库、不宣称通过。通过后才回写状态及执行已授权的中文提交/推送，并核对远端 SHA。一次性验收入口完成后移除，原配置、账本、发布、备份和运行证据保留。

## 4. 业务库备份和恢复演练

### 4.1 每次切换前

1. 确认准确主机、schema=`cyber_security`、MySQL 8、现有 admin/用户、当前 Flyway 版本（2026-10-16 已 V27）和对应发布组合；记录进程/监听，不把预览 schema 当成业务库。
2. 暂停本次服务的写入入口、relay、consumer 和采集上传，处理已接收但未完成的任务；确认无本次或其他客户端连接业务库。不能证明停写时暂停切换。
3. 在仓库根运行：

   ```sh
   sh executor/python.sh -B scripts/p8/backup_restore.py
   ```

4. 脚本从 Keychain 读取本机 DB 凭据，不回显；`mysqldump --single-transaction --routines --triggers --events --hex-blob --set-gtid-purged=OFF --no-tablespaces` 保存完整库。
5. 恢复到本次随机 schema，比较所有表的有效结构、行数及按主键对应的逐行 SHA；dump 前后业务库也须一致。DOUBLE/FLOAT 按 IEEE 位检查。MySQL 8.0.42 的 JSON 文本解析可能改变浮点末位：脚本同时生成 `json-double-fidelity.sql`，在恢复库以 SQL DOUBLE + JSON_SET 还原原精度；源库不改，逐行校验不放宽。结构摘要仅归一化冗余字符集声明和 AUTO_INCREMENT 下一个序号。
6. 全部通过后只删除该随机库，保留 `database.sql`、`json-double-fidelity.sql`、`source-before.json`、`restored.json`、`restore-proof.json` 和 `result.json`。要求 `passed=true`、`temporarySchemaDeleted=true`；用 `shasum -a 256` 分别核对两份 SQL 与恢复证明中的哈希。失败不得进入业务切换。

DB-9 的 `register_alert_only.py` 内置相同备份/恢复流程，另要求业务开始状态、输入和最终表增量与演练相同。已 approved 的 r6 不重复登记。命令见 [脚本说明](../scripts/p8/README.md)。

### 4.2 实际恢复（另一次有目标的操作）

1. 先停写并停止准确服务，保存失败现场的独立备份和日志；选定已验证 dump、源 schema、时间点和恢复目的。明确恢复会丢失该时间点之后的业务状态；获得对应恢复授权后才执行。
2. 先再次恢复到新随机库验证，再决定覆盖原库或切换到恢复库；当前工具只提供随机库演练，不提供一键覆盖业务库。不得把 DROP/TRUNCATE 直接用于业务库试错。
3. 恢复时密码通过受控环境或文件供 mysql 客户端使用，不使用 `-p明文`。先导入 `database.sql`，再向同一目标库导入已校验的 `json-double-fidelity.sql`；缺失补充 SQL 时该备份不满足精确恢复要求。恢复完成后核对所有表、Flyway 校验和、admin 哈希、审批链、组合/能力/报告引用、幂等记录、待处理消息和动作恢复事实。

4. 真实资产授权撤销或 r6 停用按已有受控 API 追加审计；不直接删除策略、组合或审批行。若需要整库恢复，保存故障点新备份，按 4.2 节申请并验证后执行；不反向改 Flyway、不清共享消息来消除冲突。
5. 本次不配置真机动作服务，因此不以试运行 PF 作为回退步骤。如发现历史未清规则，只记录并中止切换，依原 lab 授权/恢复流程处理，不能扩大本申请权限。
6. 回退完成后记录恢复的版本、服务状态、未完成项与重新申请条件。程序回退原则上无需再次整机重启；不能证明安全时保持停用，第二次重启另行确认。

**批准入口**：用户需确认上述目标/服务清单、精确采集范围与期限、1 次整机重启窗口，以及允许的系统采集权限变更。批准后才进入 P8；本次仅完成申请材料和准备代码合入。
